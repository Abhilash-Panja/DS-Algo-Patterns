# Meet in the Middle — Pattern 4

# Pair-Space / Variable-Group MITM

> **Meet in the Middle does not require one array with `40` take/skip decisions. More generally, whenever a search has several independent dimensions, we can divide those dimensions into groups, enumerate each group's combined states, and make those states meet.**

Canonical transformation:

```text
A + B + C + D = target
```

becomes:

```text
(A + B) + (C + D) = target
```

Therefore:

```text
C + D = target - (A + B)
```

This changes the way we should think about MITM.

---

# 1. What This Pattern Actually Is

Until now, MITM looked like this:

```text
One array

take / skip each element

↓

2^N possibilities

↓

split N decisions into N/2 + N/2
```

Pattern 4 is different.

Suppose we have four independent arrays:

```text
A
B
C
D
```

and must choose:

```text
one value from A
one value from B
one value from C
one value from D
```

The naive search is:

```text
n × n × n × n
=
n^4
```

There is no:

```text
2^N
```

subset search.

But we can still ask:

> Can I divide the independent decision dimensions into two groups?

Yes:

```text
(A, B)
+
(C, D)
```

Generate every:

```text
A[i] + B[j]
```

and every:

```text
C[k] + D[l]
```

Then efficiently match them.

That is still the **Meet in the Middle philosophy**.

---

# 2. The Deeper MITM Definition

This pattern reveals why the definition:

> "MITM means split an array into two halves."

is too narrow.

A better definition is:

> **Split a large combinatorial search into two smaller independent search spaces, represent each side by partial results, and efficiently combine compatible partial results.**

The search space could come from:

```text
subset decisions
```

or:

```text
multiple independent variables
```

or:

```text
several groups of choices
```

MITM is about the **search space**, not the physical array.

---

# 3. The Classic Example

Suppose:

```text
a + b + c + d = 0
```

with:

```text
a ∈ A
b ∈ B
c ∈ C
d ∈ D
```

and each array has:

```text
n
```

elements.

Naive:

```text
for a in A
    for b in B
        for c in C
            for d in D
```

Complexity:

```text
O(n^4)
```

For:

```text
n = 200
```

that means:

```text
200^4
=
1,600,000,000
```

candidate tuples.

Far too much work for a simple counting problem.

LeetCode 454 uses exactly this setup with four arrays of equal length and `n <= 200`.

---

# 4. Ask the Right Question

Instead of:

> How do I optimize four nested loops?

ask:

> **Can I rewrite the condition so that two groups independently produce partial values?**

Original:

```text
a + b + c + d = 0
```

Group:

```text
(a + b) + (c + d) = 0
```

Now define:

```text
L = a + b
R = c + d
```

The condition becomes:

```text
L + R = 0
```

Therefore:

```text
R = -L
```

Wait.

That is exactly the same complement equation from Pattern 1.

So Pattern 4 is essentially:

```text
reduce a high-dimensional search
into two lower-dimensional state spaces

↓

then apply Pattern 1 / Pattern 2
```

---

# 5. Complexity Transformation

Each pair group contains:

```text
n × n
=
n^2
```

possible states.

So:

```text
A + B
→ n^2 states

C + D
→ n^2 states
```

Then use hashing or sorting to join them.

Instead of:

```text
O(n^4)
```

we get roughly:

```text
O(n^2)
```

expected time with hashing.

Space:

```text
O(n^2)
```

The standard LeetCode 454 solution stores frequencies of all `A+B` sums and then scans all `C+D` pairs, giving `O(n²)` time and `O(n²)` space.


## Q4 — Can each group be enumerated independently?

Can we compute:


```text

```

?

If yes, good.

## Q5 — Can group states be joined efficiently?

Examples:

```text

→ exact complement lookup

L + R <= X
→ ordered complement search

minimize |L + R - X|
→ nearest complement search
```

At this point our earlier MITM patterns become reusable.

# 8. Search-Space View

This is the best way to understand Pattern 4.

Naive search:

```text
A
│
├── every B
│    │
│    ├── every C
│    │    │
│    │    └── every D
```

Produces:

```text
n^4
```

leaves.

Instead group dimensions:

```text
        Full Search
           │
     ┌─────┴─────┐
     │           │
   A × B       C × D
     │           │
   n² states   n² states
     │           │
     └─────┬─────┘
           │
      complement join
```

We replaced:

```text
enumerate complete tuples
```

with:

```text
enumerate partial tuples
+
join partial results
```

That is pure MITM thinking.

---

# 9. The Core Invariant

Suppose:

```text
leftState = A[i] + B[j]
```

and:

```text
rightState = C[k] + D[l]
```

Then every complete tuple:

```text
(i, j, k, l)
```

corresponds to exactly one:

```text
left pair (i,j)
```

and exactly one:

```text
right pair (k,l)
```

Therefore:

```text
full sum
=
leftState + rightState
```

Nothing is lost by grouping.

---

# 10. Counting Invariant

Suppose:

```text
freq[s]
```

stores:

> the number of `(i,j)` pairs from arrays A and B whose sum equals `s`.

Then for one right pair with:

```text
r = C[k] + D[l]
```

we require:

```text
s + r = target
```

so:

```text
s = target - r
```

Therefore this right pair forms exactly:

```text
freq[target - r]
```

valid full tuples.

Sum that contribution for every right pair.

That is the entire correctness argument.

---

# 11. Why Frequency Matters Again

Suppose:

```text
A+B pair sums =
[4, 4, 4, 7]
```

There are three different index pairs producing:

```text
4
```

If the required complement is:

```text
4
```

we have:

```text
3
```

different left pair choices.

A:

```java
HashSet<Integer>
```

would preserve only:

```text
4 exists
```

and destroy the count.

So for tuple counting:

```text
sum → frequency
```

is necessary.

This is exactly the same multiplicity lesson from Pattern 1.

# 12. Derive the Algorithm Slowly

Suppose the interviewer gives:

```text
A, B, C, D
```

and asks:

> Count tuples where one element from each array sums to zero.

Don't jump to pair sums immediately.

Walk through it.

---

## Step 1 — What Is Brute Force?

Choose:

```text
a from A
b from B
c from C
d from D
```

All independent.

So:

```text
n^4
```

combinations.

---

## Step 2 — What Becomes Expensive?

For every:

```text
(a,b)
```

we repeatedly try every:

```text
(c,d)
```

pair.

We're recomputing the same partial pair sums again and again.

This is the bottleneck.

---

## Step 3 — What Information Do We Actually Need?

The condition is:

```text
a + b + c + d = 0
```

Once:

```text
a+b
```

is known, the individual values of `a` and `b` do not matter for counting future complements.

Similarly:

```text
c+d
```

summarizes the right group.

So partial states are:

```text
leftState = a+b
rightState = c+d
```

---

## Step 4 — What Relationship Must They Satisfy?

```text
leftState + rightState = 0
```

therefore:

```text
leftState = -rightState
```

Exact complement.

---

## Step 5 — What Operation Repeats?

For every:

```text
(c,d)
```

pair:

```text
find number of A+B pairs
whose sum = -(c+d)
```

This screams:

```text
frequency map
```

---

# 13. Core Java Template

```java
import java.util.*;

class Solution {

    public int fourSumCount(
        int[] nums1,
        int[] nums2,
        int[] nums3,
        int[] nums4
    ) {

        Map<Long, Integer> pairFrequency =
            new HashMap<>();

        // Enumerate first half of dimensions.
        for (int a : nums1) {
            for (int b : nums2) {

                long sum =
                    (long) a + b;

                pairFrequency.merge(
                    sum,
                    1,
                    Integer::sum
                );
            }
        }

        long answer = 0;

        // Enumerate second half and
        // look for exact complements.
        for (int c : nums3) {
            for (int d : nums4) {

                long rightSum =
                    (long) c + d;

                long need =
                    -rightSum;

                answer +=
                    pairFrequency.getOrDefault(
                        need,
                        0
                    );
            }
        }

        return (int) answer;
    }
}
```

The most important lines are:

```java
pairFrequency.merge(
    (long) a + b,
    1,
    Integer::sum
);
```

and:

```java
answer +=
    pairFrequency.getOrDefault(
        -(long) c - d,
        0
    );
```

That is the pattern.

# 19. Complexity

Each first-group pair:

```text
A × B
```

creates:

```text
n²
```

states.

Generation:

```text
O(n²)
```

Second-group enumeration:

```text
O(n²)
```

Each hash lookup is expected:

```text
O(1)
```

So total expected time:

```text
O(n²)
```

Space:

```text
O(n²)
```

in the worst case when every first-group sum is distinct.

This matches the standard published solution for LeetCode 454.

# 21. Why This Is Still MITM

Some resources may simply describe LC454 as:

```text
HashMap + pair sums
```

which is perfectly valid.

But from a pattern-learning perspective, the deeper reasoning is:

```text
4-dimensional search
        ↓
split dimensions 2 + 2
        ↓
enumerate each partial space
        ↓
match complementary states
```

That is the same structural idea as Meet in the Middle.

The data structure:

```text
HashMap
```

is merely the join mechanism.

# 23. The Parallel With Classical MITM

Subset MITM:

```text
2^N
↓
2^(N/2)
```

Variable-group MITM:

```text
n^K
↓
roughly n^(K/2)
```

The exact mathematical shapes differ.

The philosophy is identical:

> **Balance the independent decision dimensions so the largest partial search space becomes much smaller.**

# 24. Why Balanced Grouping Matters

Suppose there are six arrays.

Possible split:

```text
3 + 3
```

gives:

```text
n³
and
n³
```

Good.

But:

```text
1 + 5
```

gives:

```text
n
and
n⁵
```

The second side is still enormous.

Just like subset MITM:

```text
20 + 20
```

is better than:

```text
5 + 35
```

for `40` decisions.

The general rule is:

> **Balance the number of independent dimensions assigned to each side whenever their branching factors are similar.**

---

# 25. But Equal Number of Variables Is Not Always Best

Suppose choice-set sizes differ dramatically:

```text
|A| = 10
|B| = 10
|C| = 1000
|D| = 1000
```

Grouping solely by variable count might not minimize actual state counts.

For example:

```text
A × B
=
100
```

while:

```text
C × D
=
1,000,000
```

Highly unbalanced.

Alternative grouping:

```text
A × C
=
10,000

B × D
=
10,000
```

is much better.

So the deeper balancing rule is:

> **Balance the product of branching factors, not merely the number of variables.**

This is the variable-group equivalent of balancing subset halves.

# 26. A General Grouping Formula

Suppose independent variables have domain sizes:

```text
s1, s2, s3, ..., sk
```

Full search:

```text
s1 × s2 × ... × sk
```

If we divide variables into groups:

```text
G1
G2
```

then their state counts are:

```text
M1 =
product of sizes in G1

M2 =
product of sizes in G2
```

We generally want:

```text
M1
≈
M2
```

subject to:

```text
memory
join strategy
state size
```

This minimizes the largest partial search.

# 27. Hashing vs Sorting

Exactly like Pattern 1, exact complements can be joined using different structures.

---

## Option A — Hash Frequency Map

Generate one side:

```text
sum → frequency
```

Then stream the other side and perform:

```text
target - state
```

lookup.

Expected:

```text
O(M1 + M2)
```

time.

Space:

```text
O(M1)
```

if only one side is stored.

This is ideal for LC454.

---

## Option B — Sort Both Sides

Generate:

```text
leftStates[]
rightStates[]
```

Sort them.

Then either:

```text
binary search complements
```

or:

```text
two pointers
```

Useful when:

```text
memory layout matters
deterministic behavior desired
ordered queries needed
```

---

# 28. Memory Optimization — Store Only One Side

Notice something useful in LC454.

We don't actually need:

```text
all C+D sums
```

stored.

We can:

```text
1. store frequencies of A+B
2. generate C+D one pair at a time
3. immediately query its complement
```

So space remains:

```text
O(n²)
```

rather than storing two `n²` arrays.

General MITM principle:

> **If one side can be streamed during the join, don't store it unnecessarily.**

This becomes important when partial-state sets are large.

# 29. Why HashMap Beats HashSet Here

Again, question type matters.

If the problem asks:

```text
Does ANY tuple exist?
```

a:

```text
HashSet
```

can work.

If it asks:

```text
How many tuples?
```

we need:

```text
HashMap<sum, frequency>
```

because many different pairs may produce the same sum.

# 30. Important Pattern Boundary — 4Sum II vs Ordinary 4Sum

This distinction is critical.

LeetCode 454 — **4Sum II** gives four separate arrays. We select one index independently from each array.

Therefore:

```text
(A index, B index)
```

and:

```text
(C index, D index)
```

never conflict.

Every left pair can safely combine with every complementary right pair.

Perfect MITM.

---

# 31. Ordinary 4Sum Is Different

LeetCode 18 — **4Sum** gives one array and requires four distinct indices while returning unique quadruplets.

If we generate arbitrary pair sums:

```text
(i,j)
```

and:

```text
(k,l)
```

we must additionally ensure:

```text
i,j,k,l
```

are all distinct.

We also have duplicate-output issues.

So the simple equation:

```text
pairSum1 + pairSum2 = target
```

does NOT capture the entire legality condition.

Metadata now includes:

```text
indices
```

and duplicate handling becomes more complicated.

For ordinary 4Sum, sorting + nested loops + two pointers is usually the cleaner interview approach.

# 32. State-Sufficiency Lesson Again

Why is LC454 easy to split?

Because:

```text
leftState = sum
```

contains everything the other side needs.

Index choices from different arrays can never overlap.

Why is ordinary 4Sum harder to treat this way?

Because:

```text
sum
```

does NOT tell us whether pair indices overlap.

So state would need additional metadata:

```text
(sum, i, j)
```

and compatibility must verify disjoint indices.

That is Pattern 3 thinking appearing inside Pattern 4.

Patterns compose.

# 35. Pattern 4 as a General Equation Technique

Suppose:

```text
f(a,b)
=
g(c,d)
```

We can enumerate:

```text
all f(a,b)
```

and:

```text
all g(c,d)
```

then match equal values.

It doesn't have to literally be addition.

Possible forms:

```text
a + b = c + d
```

```text
a - b = c - d
```

```text
f(a,b) + g(c,d) = X
```

The key condition is:

> each side can be calculated independently.

# 36. What Makes an Equation Splittable?

Good:

```text
a + b + c + d = X
```

because:

```text
f(a,b) = a+b

g(c,d) = c+d
```

and:

```text
f + g = X
```

---

Potentially good:

```text
a*b + c*d = X
```

because:

```text
f(a,b) = a*b
g(c,d) = c*d
```

still independent.

---

Not automatically good:

```text
a*c + b*d = X
```

if we group:

```text
(a,b)
and
(c,d)
```

because each term crosses groups.

We might need a different grouping or richer state.

So ask:

> **Can the equation be rewritten so each group produces its own independent summary?**

# 37. When NOT to Force Variable-Group MITM

## Negative Signal 1 — Dimensions Interact Heavily

If:

```text
choice from group 1
```

changes which options are legal in:

```text
group 2
```

and that dependency cannot be summarized compactly, independent enumeration breaks.

---

## Negative Signal 2 — Ordinary Polynomial Method Is Better

If:

```text
n = 10,000
```

then:

```text
n²
```

pair-state storage may already be impossible.

Maybe there is:

```text
sorting
two pointers
frequency counting
algebra
```

that avoids explicit pair enumeration.

MITM isn't automatically good because it improves the exponent.

---

## Negative Signal 3 — Memory Explosion

Suppose:

```text
n = 100,000
```

Then:

```text
n²
=
10^10
```

partial states.

Impossible.

Always calculate partial-state size.

---

## Negative Signal 4 — Grouping Does Not Capture Legality

Ordinary 4Sum illustrates this.

If pairs can overlap in indices, sum alone is insufficient.

# 39. Java Overflow Considerations

Even if individual values fit inside:

```java

```

a partial grouped state might not.

Example:

```text

```

Then:

```text
a+b
```

may exceed `int`.

Use:

```java
long pairSum =
    (long) a + b;
```

Also think about the answer count.

For `k` dimensions, number of valid tuples could theoretically approach:

```text
n^k
```

So internal counting often deserves:

```java
long answer;
```

even when a particular platform guarantees the returned result fits `int`.

# 40. Common Mistake — Storing Only Unique Pair Sums

Suppose:

```text
A+B
```

produces:

```text
[5, 5, 5]
```

and the right complement requires:

```text
5
```

Those represent:

```text
3
```

distinct pair choices.

A:

```text
Set
```

reduces them to one.

Wrong for counting.

### Prevention Rule

Ask:

```text
Do repeated partial values
represent different valid complete choices?
```

If yes:

```text
preserve frequency.
```

# 41. Common Mistake — Still Using Four Nested Loops After Precomputation

Bad:

```java
for (a)
    for (b)
        for (c)
            for (d)
                ...
```

with some map on the side.

You have not changed the search architecture.

Correct structure:

```text
enumerate AB once

then

enumerate CD once
```

The grouped search spaces must replace the original Cartesian product.

# 42. Common Mistake — Generating Both Sides Then Nested-Joining Them

Suppose:

```text
left size = n²
right size = n²
```

Then:

```java
for (left)
    for (right)
```

costs:

```text
n² × n²
=
n^4
```

You recreated brute force.

Exactly the same MITM mistake we saw in subset problems.

### Prevention Rule

After splitting, always ask:

> How will I join without multiplying the two partial state counts?

# 43. Common Mistake — Grouping Without Checking State Size

You see:

```text
8 arrays
```

and say:

```text
4 + 4 MITM!
```

But if each contains:

```text
1000
```

values:

```text
1000^4
=
10^12
```

states per half.

Impossible.

Halving an exponent does not guarantee feasibility.

Always calculate.

# 44. Common Mistake — Bad Grouping

Suppose domains are:

```text
A = 10
B = 10
C = 1000
D = 1000
```

Grouping:

```text
A+B
C+D
```

produces:

```text
100
and
1,000,000
```

Grouping:

```text
A+C
B+D
```

produces:

```text
10,000
and
10,000
```

Much more balanced.

### Rule

> Minimize the largest partial-state product.

# 45. Common Mistake — Confusing This With Pairwise Two Sum

Suppose the original problem is simply:

```text
find a+b = X
```

There are already only:

```text
n²
```

naive combinations, and hashing can solve it in:

```text
O(n)
```

There is no need to say MITM.

Pattern 4 becomes valuable when **several independent dimensions create a high-order Cartesian search**.

# 46. Common Mistake — Calling Every Pair-Sum Trick MITM

Not every precomputed pair-sum problem deserves the MITM label.

The useful classification is:

```text
Was there a larger combinatorial search?

Did we split its independent dimensions?

Did each side become a partial search space?

Did we then join those spaces?
```

If yes, the MITM mental model is useful.

If not, it may simply be ordinary precomputation.

# 47. HashMap vs Sorted Arrays

### HashMap

Good for:

```text
streaming one side
```

Fingerprint:

```java
freq.merge(state, 1, Integer::sum);

    freq.getOrDefault(
        target - otherState,

```

### Sorted Arrays

Good for:

```text
ordered inequality
closest value
memory-efficient primitives
two-pointer joins
```

Fingerprint:

```java
Arrays.sort(states);

upperBound(...)
```

Again:

> MITM determines the search architecture.

> The objective determines the join structure.

# 48. Can We Use Two Pointers for Exact Counting?

Yes.

Suppose:

```text
left[]
right[]
```

contain all grouped sums and both are sorted.

Start:

```text
i = 0
j = right.length - 1
```

Compare:

```text
left[i] + right[j]
```

If:

```text
< target
```

increase:

```text
i
```

If:

```text
> target
```

decrease:

```text
j
```

If equal, count duplicate runs:

```text
countLeft
×
countRight
```

and add them.

This is equivalent to the exact-counting two-pointer join from Pattern 1.

# 49. Hashing vs Two Pointers for LC454

For LC454, HashMap is usually simplest:

```text
generate AB frequencies
+
stream CD
```

Benefits:

```text
no second n² array
no sorting
clean counting
```

Expected complexity:

```text
O(n²)
```

The official/common solution follows this structure.

Two pointers would require:

```text
store AB
store CD
sort both
```

giving roughly:

```text
O(n² log n)
```

due to sorting.

So hashing is the cleaner choice here.

# 50. Generic K-Group Reasoning

Suppose there are:

```text
K
```

independent groups, each of size:

```text
n
```

Full search:

```text
n^K
```

Split roughly:

```text
K/2
+
K/2
```

Each side contains roughly:

```text
n^(K/2)
```

states.

Exact complement matching can potentially reduce complexity toward:

```text
O(n^(K/2))
```

expected with hashing, although constants, state construction, memory, and unequal group sizes matter.

The parallel is beautiful:

```text
Subset MITM:

2^N
→
2^(N/2)


Variable MITM:

n^K
→
n^(K/2)
```

# 51. What If K Is Odd?

Suppose there are five arrays:

```text
A B C D E
```

Split:

```text
2 + 3
```

State counts:

```text
n²
and
n³
```

The larger side dominates.

So complexity is roughly:

```text
O(n³)
```

rather than:

```text
O(n⁵)
```

Still a huge improvement.

You cannot perfectly halve an odd number of dimensions, but you make the groups as balanced as possible.

# 52. Variable-Group MITM vs Divide and Conquer

Again, they may visually resemble:

```text
variables
 /     \
group1 group2
```

But we are not recursively solving smaller copies of the original problem.

We are:

```text
enumerating partial assignments
```

and finding:

```text
compatible assignments from the other group.
```

The "meeting" remains the essential step.

# 53. Pattern Decision Test

When you see several nested choice dimensions:

```text
1. Write the naive Cartesian-product complexity.

2. Ask whether the dimensions are independent.

3. Write the equation/constraint mathematically.

4. Try to separate it into:

   f(first group)
   relationship
   g(second group)

5. Estimate state counts for candidate groupings.

6. Choose a balanced grouping.

7. Decide the smallest sufficient partial state.

8. Determine the join relation:

   exact?
   inequality?
   closest?
   metadata constrained?

9. Pick hashing / sorting / binary search / two pointers.

10. Verify that the join does NOT multiply both
    partial-state counts again.
```

# 61. Interview Explanation — LC454

A strong concise explanation:

> The direct solution has four nested loops, so it takes `O(n^4)`. Since the four index choices are independent and the condition is additive, I can rewrite it as `(a+b) + (c+d) = 0`.
>
> I'll enumerate every `a+b` pair once and store how many times each sum occurs. There are `n²` such pairs. Then I'll enumerate every `c+d` pair and look up how many left pairs have sum `-(c+d)`. Every complete tuple corresponds uniquely to one left pair and one right pair, so adding those frequencies counts every valid tuple exactly once.
>
> That reduces the expected time from `O(n^4)` to `O(n²)` with `O(n²)` extra space.

That demonstrates the reasoning without merely saying:

> "Use a HashMap."

---

# 62. Interview Explanation — Generic Pattern

> The naive search is the Cartesian product of several independent decision groups, which is too large. Since the objective can be separated into a contribution from one set of variables and a contribution from the remaining variables, I'll enumerate those partial state spaces independently. Then I'll organize one side so I can efficiently find compatible states from the other side rather than multiplying the two partial spaces again. The grouping should be chosen to keep the partial state counts as balanced as possible.

That is the generalized Pattern 4 explanation.

# 66. The One-Line Pattern Memory

> **When a combinatorial search has several independent decision dimensions, split those dimensions into balanced groups, enumerate each group's partial results, and efficiently match compatible group states instead of exploring the full Cartesian product.**

Code memory:

```java
for (int a : A) {
    for (int b : B) {
        freq.merge(
            (long) a + b,
            1,
            Integer::sum
        );
    }
}

for (int c : C) {
    for (int d : D) {
        long need =
            target - (long) c - d;

        answer +=
            freq.getOrDefault(
                need,
                0
            );
    }
}
```

Reasoning memory:

```text
Don't ask only:

"Can I split the ARRAY?"

Ask:

"Can I split the DIMENSIONS
of the search space?"
```

That is Pattern 4.
