# Meet in the Middle — Pattern 2

# Best Compatible State / Ordered Complement Matching

> **I can independently generate possible states from two halves, but instead of needing one exact complementary state, I need the best state from the other half that satisfies a boundary or minimizes some distance.**

Canonical forms:

```text
maximize L + R
such that
L + R <= X
```

or:

```text
minimize |L + R - X|
```

This is the major upgrade from Pattern 1.

---

# 1. What This Pattern Actually Is

Strip away the story.

This pattern is:

> **Generate partial states from two independent groups, sort at least one side, and for every state from the other side search for the best compatible value according to an inequality or closeness objective.**

Pattern 1 asked:

```text
Does exactly X - L exist?
```

Pattern 2 asks things like:

```text
What is the largest R <= X - L?
```

or:

```text
Which R is closest to X - L?
```

That difference is everything.

---

# 2. Why Pattern 1 Is No Longer Enough

Suppose our target is:

```text
X = 20
```

and we currently have:

```text
L = 7
```

Pattern 1 would calculate:

```text
need = 20 - 7
     = 13
```

and ask:

```text
Does R = 13 exist?
```

Suppose the right-side states are:

```text
[0, 3, 5, 9, 12, 17]
```

There is no `13`.

For an exact-target problem:

```text
no 13
→ this L produces no solution
```

But suppose the problem asks:

> Find the maximum subset sum not exceeding `20`.

Then:

```text
R = 12
```

is extremely useful.

Because:

```text
7 + 12 = 19
```

which may be optimal.

So exact lookup throws away a perfectly good candidate.

---

# 3. The Core Transition From Pattern 1

Pattern 1:

```text
L + R = X
```

so:

```text
R = X - L
```

Pattern 2:

```text
L + R <= X
```

so:

```text
R <= X - L
```

Notice what changed.

We no longer want:

```text
one exact value
```

We want:

```text
the BEST value inside a range
```

Specifically:

```text
largest R <= X - L
```

That is why ordering becomes useful.

---

# 4. Why Sorting Suddenly Becomes Important

Suppose right states are unsorted:

```text
[14, 2, 9, 6, 20, 3, 11]
```

For every left state, if I ask:

```text
largest R <= limit
```

I may need to scan the entire right list.

If both halves contain about:

```text
2^(N/2)
```

states, repeated scanning gives:

```text
2^(N/2) × 2^(N/2)
=
2^N
```

We lose the entire MITM advantage.

But after sorting:

```text
[2, 3, 6, 9, 11, 14, 20]
```

the predicate:

```text
R <= limit
```

has structure:

```text
true true true true false false false
```

There is a boundary.

That means:

```text
binary search
```

can locate the final valid state.

So the reasoning is:

```text
Need best state satisfying inequality
        ↓
States currently unordered
        ↓
Repeated search would be linear
        ↓
Sort states
        ↓
Validity becomes monotonic by index
        ↓
Binary search the boundary
```

Do not memorize:

> MITM → sort + binary search.

Derive it from:

> **I need the extreme valid state inside an ordered candidate set.**

---

# 5. The Core Invariant

There are really two invariants in this pattern.

---

## MITM Invariant

Exactly as in Pattern 1:

> **Every complete subset can be decomposed into one subset from the left half and one subset from the right half.**

Therefore:

```text
totalSum
=
leftSum + rightSum
```

---

## Ordered-Search Invariant

After sorting the right states:

```text
R[0] <= R[1] <= ... <= R[m - 1]
```

for a fixed left state `L`, define:

```text
limit = X - L
```

Then all right states satisfying:

```text
R[i] <= limit
```

form a prefix:

```text
valid valid valid valid invalid invalid ...
```

Therefore:

> **The optimal right state for this fixed `L` is the final valid state in that prefix.**

This is the reason binary search is correct.

# 6. Recognition Signals

When you encounter an unseen problem, ask these questions.

---

## Q1 — Does brute force enumerate combinations?

Typical decisions:

```text
take / skip
choose / ignore
assign one of a few possibilities
```

giving something like:

```text
2^N
```

or:

```text
b^N
```

---

## Q2 — Is full enumeration too large but half-enumeration feasible?

Example:

```text
N = 40

2^40
→ too large

2^20
→ manageable
```

Same first MITM test as Pattern 1.

---

## Q3 — Can a complete result be written using two partial states?

Example:

```text
total
=
L + R
```

If no compact combination exists, ordinary MITM may not fit.

---

## Q4 — Is the objective an optimization rather than exact equality?

Look for structural forms like:

```text
maximum value <= X

minimum value >= X

closest value to X

minimum |value - X|

best feasible combination
```

This strongly differentiates Pattern 2 from Pattern 1.

---

## Q5 — For a fixed state on one side, can I describe exactly what I need from the other side?

Examples:

```text
largest R <= X - L
```

or:

```text
smallest R >= X - L
```

or:

```text
R closest to X - L
```

If yes, you have reduced the problem to an ordered-search query.

---

## Q6 — Does sorting make valid candidates monotonic?

If sorted candidates look like:

```text
valid valid valid invalid invalid
```

then binary search is probably natural.

Common language includes:

```text

minimum difference

```

But do not learn:

```text
"at most"

```

because many problems with `at most` are solved with:

```text
sliding window

```

The real structural condition is:

> **An exponential choice space can be split into independently enumerable halves, and for one half-state I need an extremal/nearest state from the other half rather than one exact state.**

# 8. Pattern 2 Has Two Major Forms

I would keep these under **one pattern**, because the MITM architecture is identical.

---

## Form A — Boundary Optimization

Example:

```text
maximize L + R
subject to
L + R <= X
```

For each `L`:

```text
R <= X - L
```

Need:

```text
largest possible R
```

Typical tool:

```text
upper bound
```

---

## Form B — Closest Complement

Example:

```text
minimize |L + R - goal|
```

For each `L`, ideal would be:

```text
R = goal - L
```

but exact may not exist.

Need:

```text
R closest to goal - L
```

Typical tool:

```text
lower bound
+
check neighbors
```

These are the two essential variations.

Do not create separate MITM patterns for them.

---

# 9. Form A — Maximum Feasible State

Suppose:

```text
L + R <= X
```

and we want to maximize:

```text
L + R
```

Fix `L`.

Now `L` is constant.

Maximizing:

```text
L + R
```

is equivalent to maximizing:

```text
R
```

subject to:

```text
R <= X - L
```

So the entire problem for this `L` reduces to:

> Find the largest right state not greater than `X - L`.

This is a predecessor query.

---

# 10. Why `upperBound` Is the Natural Operation

Suppose sorted right states are:

```text
[0, 3, 6, 8, 11, 15]
```

and:

```text
limit = 10
```

We need:

```text
largest value <= 10
```

The answer is:

```text
8
```

A convenient binary-search formulation is:

> Find the first value `> limit`.

That is:

```text
upperBound(limit)
```

Suppose it returns index:

```text
4
```

pointing to:

```text
11
```

Then the answer is immediately before it:

```text
index = 4 - 1
```

therefore:

```text
8
```

So the code shape becomes:

```java
int idx = upperBound(right, limit) - 1;

if (idx >= 0) {
    candidate = left + right[idx];
}
```

That is the fingerprint of Form A.

---

# 11. `lowerBound` vs `upperBound`

This is worth making permanent in your notes.

---

## `lowerBound(x)`

Returns the first index where:

```text
value >= x
```

Shape:

```text
values < x | values >= x
```

---

## `upperBound(x)`

Returns the first index where:

```text
value > x
```

Shape:

```text
values <= x | values > x
```

---

## When We Need Largest `<= x`

The cleanest operation is:

```text
upperBound(x) - 1
```

because:

```text
upperBound(x)
```

points to the first invalid element.

The previous element is therefore the final valid one.

---

# 12. Core Java `upperBound` Template

```java
private static int upperBound(long[] arr, long target) {
    int low = 0;
    int high = arr.length;

    while (low < high) {
        int mid = low + (high - low) / 2;

        if (arr[mid] <= target) {
            low = mid + 1;
        } else {
            high = mid;
        }
    }

    return low;
}
```

Invariant:

```text
[0, low)
→ values <= target may exist

[high, n)
→ values > target
```

At the end:

```text
low == high
```

and it is the first position containing:

```text
> target
```

Therefore:

```text
largest <= target
=
arr[low - 1]
```

if:

```text
low > 0
```

---

# 13. Why Not Use Hashing Here?

Hashing is excellent when we know the exact key:

```text
R = X - L
```

because:

```text
contains(key)
```

is natural.

But here we ask:

```text
largest R <= X - L
```

A normal `HashSet` cannot tell us:

```text
What is the largest stored key below 13?
```

without scanning everything.

We need order.

Possible ordered structures include:

```text
sorted array + binary search
TreeSet.floor()
```

but for MITM:

```text
generate everything once
then query many times
```

so:

```text
sort once + binary search many times
```

is usually simple and efficient.

---

# 14. Why Not Use `TreeSet`?

A `TreeSet` supports:

```java
set.floor(limit);
```

which seems perfect.

But there are trade-offs.

For static MITM states:

```text
generate all
then never modify them
```

a sorted primitive array usually gives:

```text
less memory overhead
better cache locality
simple binary search
duplicates preserved if needed
```

A `TreeSet`:

```text
boxes long → Long
allocates tree nodes
deduplicates equal values
has larger constant factors
```

So while conceptually valid, it is usually not the first choice here.

---

# 15. Why Not Sort the Original Array?

Again, we are not searching among individual input values.

We are searching among:

```text
subset states
```

For example:

```text
nums = [2, 5, 8]
```

sorting the numbers tells us nothing directly about achievable sums:

```text
0
2
5
7
8
10
13
15
```

The useful ordered search space is:

```text
generated partial sums
```

not the original elements.

# 16. Core Java Skeleton — Maximum Sum `<= X`

```java
import java.util.*;

class Solution {

    private void generate(
        long[] nums,
        int index,
        int end,
        long sum,
        List<Long> states
    ) {
        if (index == end) {
            states.add(sum);
            return;
        }

        // Skip
        generate(
            nums,
            index + 1,
            end,
            sum,
            states
        );

        // Take
        generate(
            nums,
            index + 1,
            end,
            sum + nums[index],
            states
        );
    }

    private int upperBound(
        List<Long> arr,
        long target
    ) {
        int low = 0;
        int high = arr.size();

        while (low < high) {
            int mid =
                low + (high - low) / 2;

            if (arr.get(mid) <= target) {
                low = mid + 1;
            } else {
                high = mid;
            }
        }

        return low;
    }

    public long maxSubsetSum(
        long[] nums,
        long limit
    ) {
        int n = nums.length;
        int mid = n / 2;

        List<Long> left = new ArrayList<>();
        List<Long> right = new ArrayList<>();

        generate(nums, 0, mid, 0L, left);
        generate(nums, mid, n, 0L, right);

        Collections.sort(right);

        long best = Long.MIN_VALUE;

        for (long leftSum : left) {

            long remaining =
                limit - leftSum;

            int index =
                upperBound(
                    right,
                    remaining
                ) - 1;

            if (index >= 0) {
                best = Math.max(
                    best,
                    leftSum + right.get(index)
                );
            }
        }

        return best;
    }
}
```

The important code fingerprint is:

```java
long remaining = limit - leftSum;

int index =
    upperBound(right, remaining) - 1;
```

Everything else supports those lines.

# 18. Deep Worked Example — AtCoder ABC184 F

## Problem

You have `N` tasks.

Task `i` requires:

```text
A[i]
```

minutes.

You have:

```text
T
```

minutes.

Choose any subset of tasks so that total time does not exceed `T`.

Maximize the total used time.

Constraints include:

```text
N <= 40

A[i] <= 10^9
```

This is an excellent Pattern 2 anchor.

---

# Step 1 — Strip the Story

Forget programming contests and tasks.

We have:

```text
N positive numbers
```

Choose any subset.

Objective:

```text
maximize subsetSum
```

subject to:

```text
subsetSum <= T
```

Mathematically:

```text
maximize Σ A[i]

such that

Σ A[i] <= T
```

---

# Step 2 — Brute Force

Each value:

```text
take
skip
```

so:

```text
2^N
```

subsets.

At:

```text
N = 40
```

roughly:

```text
10^12
```

Too large.

---

# Step 3 — Could Knapsack DP Work?

A typical knapsack state could depend on:

```text
T
```

But:

```text
T <= 10^9
```

so:

```text
dp[T]
```

would be too large.

Therefore:

```text
2^N
→ too large

O(N × T)
→ too large
```

But:

```text
N = 40
```

is still moderate.

This strongly suggests exploiting the `N` dimension.

---

# Step 4 — Split the Decisions

Divide:

```text
Left  ≈ 20 elements
Right ≈ 20 elements
```

Generate:

```text
all LeftSums

all RightSums
```

Each side has at most:

```text
2^20
≈ 10^6
```

states.

Feasible.

---

# Step 5 — What Does the Objective Become?

Every complete subset corresponds to:

```text
L + R
```

We need:

```text
L + R <= T
```

while maximizing:

```text
L + R
```

Now fix one:

```text
L
```

The condition becomes:

```text
R <= T - L
```

Since `L` is fixed, maximizing total means choosing the largest possible:

```text
R
```

under that boundary.

So we need:

```text
largest R <= T - L
```

This is the exact moment Pattern 2 appears.

---

# Step 6 — Why Not Exact Lookup?

Suppose:

```text
T = 17
L = 5
```

Then ideal right contribution is:

```text
12
```

Suppose right states are:

```text
[0, 3, 7, 11, 14]
```

There is no:

```text
12
```

But:

```text
11
```

gives:

```text
5 + 11 = 16
```

which is valid and potentially optimal.

Pattern 1 would say:

```text
12 not found
→ fail
```

Pattern 2 says:

```text
12 not found
→ give me the largest value BELOW 12
```

That is the conceptual upgrade.

valid states are:

```text
[0, 3, 7, 11]
```

invalid states:

```text
[14]
```

So validity becomes:

```text
true true true true false
```

Binary search can locate the boundary.

# Step 9 — Why Can We Evaluate Every `L` Independently?

For each fixed `L`, binary search gives the best possible compatible `R`.

So we are solving:

```text
bestRight(L)
```

for every possible left state.

The global optimum must use some particular left state:

```text
L*
```

When our loop reaches:

```text
L*
```

we compute the best possible compatible right state for it.

Therefore the global optimum cannot be missed.

This is the correctness argument.

# 19. Java Solution — ABC184 F Style

Because all `A[i]` are positive, we can optionally avoid storing states exceeding `T`, although this pruning depends on that positivity precondition.

```java
import java.io.*;
import java.util.*;

public class Main {

    static void generate(
        long[] nums,
        int index,
        int end,
        long sum,
        long limit,
        List<Long> states
    ) {
        // Safe here only because all values are positive.
        if (sum > limit) {
            return;
        }

        if (index == end) {
            states.add(sum);
            return;
        }

        generate(
            nums,
            index + 1,
            end,
            sum,
            limit,
            states
        );

        generate(
            nums,
            index + 1,
            end,
            sum + nums[index],
            limit,
            states
        );
    }

    static int upperBound(
        List<Long> arr,
        long target
    ) {
        int low = 0;
        int high = arr.size();

        while (low < high) {
            int mid =
                low + (high - low) / 2;

            if (arr.get(mid) <= target) {
                low = mid + 1;
            } else {
                high = mid;
            }
        }

        return low;
    }

    public static void main(String[] args)
        throws Exception {

        BufferedReader br =
            new BufferedReader(
                new InputStreamReader(System.in)
            );

        StringTokenizer st =
            new StringTokenizer(br.readLine());

        int n = Integer.parseInt(
            st.nextToken()
        );

        long limit = Long.parseLong(
            st.nextToken()
        );

        long[] nums = new long[n];

        st =
            new StringTokenizer(br.readLine());

        for (int i = 0; i < n; i++) {
            nums[i] =
                Long.parseLong(
                    st.nextToken()
                );
        }

        int mid = n / 2;

        List<Long> left =
            new ArrayList<>();

        List<Long> right =
            new ArrayList<>();

        generate(
            nums,
            0,
            mid,
            0L,
            limit,
            left
        );

        generate(
            nums,
            mid,
            n,
            0L,
            limit,
            right
        );

        Collections.sort(right);

        long best = 0;

        for (long leftSum : left) {

            long remaining =
                limit - leftSum;

            int idx =
                upperBound(
                    right,
                    remaining
                ) - 1;

            if (idx >= 0) {
                best = Math.max(
                    best,
                    leftSum + right.get(idx)
                );
            }
        }

        System.out.println(best);
    }
}
```

# 20. Important Pruning Precondition

The previous solution used:

```java
if (sum > limit) {
    return;
}
```

Why is this safe?

Because the AtCoder problem guarantees:

```text
A[i] > 0
```

Once:

```text
sum > limit
```

adding additional elements can only make it larger.

So the branch can never become valid again.

But consider:

```text
nums = [20, -15]
limit = 10
```

At:

```text
sum = 20
```

we might incorrectly prune.

But later:

```text
20 + (-15) = 5
```

which is valid.

So:

> **Pruning is based on monotonicity of future changes, not on MITM itself.**

Do not copy this pruning into problems containing negative values.

# 21. Form B — Closest Complement

Now change the objective.

Instead of:

```text
maximum sum <= X
```

suppose we want:

```text
minimum |sum - goal|
```

Again:

```text
sum = L + R
```

So:

```text
minimize
|L + R - goal|
```

For fixed `L`:

```text
minimize
|R - (goal - L)|
```

Therefore the ideal right value is:

```text
goal - L
```

but it may not exist.

So we need:

> **the right-side state closest to `goal - L`.**

---

# 22. Why `lowerBound` Fits Closest Complement

Suppose right states are:

```text
[0, 4, 9, 15]
```

and ideal value is:

```text
11
```

`lowerBound(11)` returns:

```text
15
```

because that is the first value:

```text
>= 11
```

But the closest value might also be immediately before it:

```text
9
```

Therefore we check:

```text
lowerBound position
```

and:

```text
position - 1
```

Those are the only two candidates needed.

Why?

Because everything further left is:

```text
<= 9
```

and therefore at least as far from `11` as `9`.

Everything further right is:

```text
>= 15
```

and therefore at least as far from `11` as `15`.

This is the ordered-search invariant.

# 23. Core Java `lowerBound`

```java

    long target

    int low = 0;

```

Result:

```text
first index whose value >= target
```

For closest-value search:

```java
int idx = lowerBound(right, need);

if (idx < right.length) {
    check(right[idx]);
}

if (idx > 0) {
    check(right[idx - 1]);
}
```

```java
        answer,
        Math.abs(
            left + right[idx - 1] - goal
        )
    );
}
```

If you see this shape:

```text
target complement
+
lower bound
+
check both neighbors
```

you are usually looking at:

```text
MITM closest-state matching
```

# 25. Strong Variation — LeetCode 1755

**Closest Subsequence Sum** asks for a subsequence whose sum is as close as possible to a given goal. The array length is at most `40`, values may be negative, and the goal may also be negative.

This is a very valuable Pattern 2 problem because it removes several conveniences from the AtCoder anchor.

---

## What Changes?

AtCoder:

```text
maximize sum <= T

all values positive
```

LeetCode 1755:

```text
minimize |sum - goal|

values may be negative
```

So we cannot use:

```text
sum > goal
→ prune
```

and we no longer need only a predecessor.

Instead:

```text
ideal R = goal - L
```

and we search for the nearest right state.

---

# 26. Deriving LeetCode 1755

Suppose:

```text
nums.length <= 40
```

Brute force:

```text
2^40
```

too large.

Split:

```text
20 + 20
```

Generate:

```text
~2^20
```

sums per side.

For every `L`, we want to minimize:

```text
|L + R - goal|
```

Rewrite:

```text
|R - (goal - L)|
```

Therefore:

```text
need = goal - L
```

and we need the `R` nearest to `need`.

Sort right sums.

Binary search:

```text
lowerBound(need)
```

Check:

```text
idx
idx - 1
```

Take the better one.

Notice how the algorithm comes entirely from algebra.

We never needed the sentence:

> "Closest Subsequence Sum is a MITM problem."

# 27. Java Skeleton — Closest Sum

```java
import java.util.*;

class Solution {

    private void generate(
        int[] nums,
        int index,
        int end,
        long sum,
        List<Long> states
    ) {
        if (index == end) {
            states.add(sum);
            return;
        }

        generate(
            nums,
            index + 1,
            end,
            sum,
            states
        );

        generate(
            nums,
            index + 1,
            end,
            sum + nums[index],
            states
        );
    }

    private int lowerBound(
        List<Long> arr,
        long target
    ) {
        int low = 0;
        int high = arr.size();

        while (low < high) {
            int mid =
                low + (high - low) / 2;

            if (arr.get(mid) < target) {
                low = mid + 1;
            } else {
                high = mid;
            }
        }

        return low;
    }

    public int minAbsDifference(
        int[] nums,
        int goal
    ) {
        int n = nums.length;
        int mid = n / 2;

        List<Long> left =
            new ArrayList<>();

        List<Long> right =
            new ArrayList<>();

        generate(
            nums,
            0,
            mid,
            0L,
            left
        );

        generate(
            nums,
            mid,
            n,
            0L,
            right
        );

        Collections.sort(right);

        long best =
            Math.abs((long) goal);

        for (long leftSum : left) {

            long need =
                (long) goal - leftSum;

            int idx =
                lowerBound(
                    right,
                    need
                );

            if (idx < right.size()) {
                best = Math.min(
                    best,
                    Math.abs(
                        leftSum
                        + right.get(idx)
                        - goal
                    )
                );
            }

            if (idx > 0) {
                best = Math.min(
                    best,
                    Math.abs(
                        leftSum
                        + right.get(idx - 1)
                        - goal
                    )
                );
            }

            if (best == 0) {
                return 0;
            }
        }

        return (int) best;
    }
}
```

# 28. Why Only Two Neighboring Values?

This is worth proving rather than memorizing.

Suppose sorted right states are:

```text
... a, b, c, d ...
```

and:

```text
b < need <= c
```

`lowerBound(need)` points to:

```text
c
```

Any value before `b` satisfies:

```text
x <= b < need
```

therefore:

```text
need - x
>=
need - b
```

so none can beat `b`.

Any value after `c` satisfies:

```text
x >= c >= need
```

therefore:

```text
x - need
>=
c - need
```

so none can beat `c`.

Hence only:

```text
b
c
```

need inspection.

That is why:

```text
idx
idx - 1
```

is sufficient.

# 29. Can We Use Two Pointers Instead?

Sometimes yes.

Suppose both generated arrays are sorted.

For the boundary problem:

```text
maximize L + R <= X
```

we can use:

```text
i = smallest left
j = largest right
```

Then:

```text
if L[i] + R[j] <= X
    candidate is feasible
    increase i

else
    decrease j
```

This may reduce the join from:

```text
O(M log M)
```

binary-search queries to:

```text
O(M)
```

after both arrays are sorted.

But both methods have overall sorting cost:

```text
O(M log M)
```

anyway.

# 30. Binary Search vs Two Pointers

| Question                           | Binary Search      | Two Pointers                                 |
| ---------------------------------- | ------------------ | -------------------------------------------- |
| Need both arrays sorted?           | only searched side | usually both                                 |
| Search each left independently?    | yes                | no                                           |
| Join complexity                    | `O(L log R)`       | `O(L + R)`                                   |
| Easy to extend to enriched states? | often easier       | sometimes harder                             |
| Natural for closest lookup?        | very natural       | also possible                                |
| Interview clarity                  | excellent          | excellent when monotonic movement is obvious |

Both belong to the same pattern.

Do not create separate MITM patterns for them.

# 31. Two-Pointer Invariant for `Maximum <= X`

Suppose:

```text
left ascending
right ascending
```

Start:

```text
i = 0
j = right.length - 1
```

At state:

```text
left[i] + right[j]
```

---

## If Sum Is Too Large

```text
sum > X
```

Any larger left value with the same `right[j]` will also be too large.

Therefore:

```text
right[j]
```

cannot pair validly with current or future left states.

So:

```text
j--
```

is safe.

---

## If Sum Is Valid

```text
sum <= X
```

For current `left[i]`, because `right[j]` is the largest currently available right state, this is its best feasible pair.

Record the candidate.

Then:

```text
i++
```

because no smaller right value can improve the answer for the same left state.

That is the invariant.

# 32. Pattern Boundary — Exact vs Ordered Complement

| Question            | Pattern 1       | Pattern 2                             |
| ------------------- | --------------- | ------------------------------------- |
| Relation            | `L + R == X`    | inequality / closeness                |
| Required `R`        | exact `X-L`     | best around `X-L`                     |
| Exact state missing | candidate fails | nearby candidate may still be optimal |
| HashSet useful?     | yes             | generally no                          |
| Ordering valuable?  | optional        | central                               |
| Typical search      | hash lookup     | predecessor / successor / nearest     |
| Common DS           | HashMap/Set     | sorted array                          |
| Fingerprint         | `contains(X-L)` | `upperBound/lowerBound(X-L)`          |

The question to ask yourself is:

> **Do I need an exact complement, or an extremal complement?**

That separates the patterns.

# 33. Pattern Boundary — Binary Search on States vs Binary Search on Answer

These are very different.

Pattern 2 does:

```text
generate candidate states

sort them

binary-search inside the states
```

The target:

```text
X - L
```

changes for each `L`.

---

Binary Search on Answer instead does:

```text
guess answer M
↓
run feasibility(M)
↓
use monotonic true/false predicate
```

No partial-state MITM structure is required.

Do not confuse the two simply because both contain binary search.

# 34. Pattern Boundary — Two Sum / Two Pointers

If the original input is merely:

```text
find two numbers whose sum ...
```

there is no reason to generate `2^(N/2)` subset states.

Pattern 2 applies when each half itself represents a **combinatorial choice space**.

Ask:

```text
What exactly am I enumerating?
```

If the answer is:

```text
individual array elements
```

this may just be ordinary Two Sum / two pointers.

If the answer is:

```text
all possible partial solutions
```

MITM is much more plausible.

# 36. Important Mistake — Binary Searching the Wrong Quantity

Suppose:

```text
L + R <= X
```

For fixed `L`, we need:

```text
R <= X - L
```

A common mistake is binary-searching:

```text
X
```

inside the right states.

That ignores what the left half has already contributed.

Always derive the residual capacity:

```java
long remaining =
    X - leftSum;
```

The query is about:

```text
remaining
```

not the original target.

---

# 37. Important Mistake — Returning `upperBound` Directly

Suppose:

```text
right = [1, 4, 6, 9]
limit = 6
```

`upperBound(6)` returns the position of:

```text
9
```

because `9` is the first value:

```text
> 6
```

But `9` is invalid.

The answer is the previous element:

```text
6
```

Therefore:

```java
int idx =
    upperBound(right, limit) - 1;
```

not:

```java
int idx =
    upperBound(right, limit);
```

Classic off-by-one bug.

---

# 38. Important Mistake — Using Only `lowerBound` Candidate for Closest

Suppose:

```text
right =
[1, 4, 10]

need = 6
```

`lowerBound(6)` gives:

```text
10
```

Distance:

```text
4
```

But previous value:

```text
4
```

has distance:

```text
2
```

So for closest search:

```text
check idx
and
idx - 1
```

unless one is out of range.

# 39. Important Mistake — Pruning With Negative Numbers

Do not assume:

```text
sum > target
→ useless
```

for Pattern 2.

That only works when future contributions cannot decrease the sum.

For LeetCode 1755, values may be negative.

Therefore branches that temporarily overshoot the goal may later return near it.

# 40. Important Mistake — Initializing the Answer Incorrectly

For:

```text
maximum subset sum <= X
```

if the empty subset is allowed and values are non-negative:

```java
long best = 0;
```

is sensible.

But with arbitrary negative values or different requirements, `0` may not represent a valid/default optimum.

Understand:

```text
Is empty subset allowed?
Can answer be negative?
```

before initializing.

# 43. Interview Explanation — Boundary Version

For ABC184 F style problems, a good explanation is:

> Every item has a take-or-skip decision, so direct enumeration is `2^N`, which is too large for `N = 40`. A capacity-based knapsack DP is also unattractive because the capacity can be around `10^9`.
>
> I can split the elements into two halves and enumerate every subset sum from each half, giving about `2^(N/2)` states per side. Every complete subset sum is one left sum plus one right sum.
>
> For a fixed left sum `L`, I need the largest right sum satisfying `R <= T - L`. So I'll sort the right-side sums and binary-search for the last value not exceeding the remaining capacity. Repeating that for every left state considers the best possible right partner for every left choice.
>
> The complexity is roughly `O(N * 2^(N/2))` because of sorting and binary search over the half-state space.

That is enough before coding.

---

# 44. Interview Explanation — Closest Version

For LeetCode 1755 style:

> Direct subset enumeration is `2^N`, which is too large for up to `40` elements. I can split the array and enumerate all subset sums from each half, giving about `2^20` states per side.
>
> Any complete subsequence sum is `L + R`. For a fixed left sum, minimizing `|L + R - goal|` means finding a right sum closest to `goal - L`.
>
> I'll sort the right sums, lower-bound `goal - L`, and only need to check that position and the previous one because those are the nearest values on either side of the target. Taking the minimum over every left state gives the global optimum.

Again:

```text
derive first
name technique second
```

# 47. Follow-Up Training

## Follow-Up 1 — "What if I need the minimum sum >= X?"

For fixed `L`:

```text
R >= X - L
```

Now we want:

```text
smallest R satisfying boundary
```

That is directly:

```text
lowerBound(X - L)
```

The MITM pattern remains the same.

Only the side of the boundary changes.

## Follow-Up 2 — "What if I need both maximum <= X and minimum >= X?"

For fixed `L`:

```text
need = X - L
```

Use:

```text
lowerBound(need)
```

Then inspect:

```text

```

Exactly like closest-complement search.

## Follow-Up 3 — "What if data contains negative numbers?"

MITM still works.

Sorting and binary search still work.

But positivity-based pruning may disappear.

Ask:

```text
Which optimization relied on monotonic sums?
```

not:

```text
Does MITM still work?
```

## Follow-Up 4 — "What if I need to return the chosen subset?"

Now each state must preserve reconstruction information.

Possible state:

```text

```

Search remains the same.

After finding:

```text
bestLeftState
bestRightState
```

## Follow-Up 5 — "What if exactly K elements must be chosen?"

Our current state:

```text
sum
```

is no longer sufficient.

A left sum generated using:

```text
2 elements
```

cannot necessarily pair with the same right states as one generated using:

```text
8 elements
```

Now state needs:

```text
(count, sum)
```

```text
leftCount + rightCount = K
```

## Follow-Up 6 — "What if right states change dynamically?"

```text

sort once
```


The invariant survives.

The data structure changes.

> **If half-enumeration is feasible and the other half does not need to match an exact complement but instead must provide the best value below, above, or nearest to a boundary, sort the partial states and search for that extremal compatible state.**

```java
remaining = limit - left;

    upperBound(right, remaining) - 1;
```

```java
need = goal - left;

idx =
    lowerBound(right, need);

check(idx);
check(idx - 1);
```

```text
Exact complement missing
does NOT mean failure.

Ask:

"What is the best compatible
state around that complement?"
```

That is Pattern 2.
