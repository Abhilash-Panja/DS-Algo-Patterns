# Meet in the Middle — Pattern 3

# Constraint-Aware / Enriched-State MITM

> **Sometimes the partial result itself is not enough. Two states with the same value may behave differently later because they were created using different choices. In that case, preserve the extra information future compatibility depends on.**

Canonical state:

```text
(sum)
```

becomes:

```text
(countChosen, sum)
```

or more generally:

```text
(metadata, objectiveState)
```

This is the most important conceptual upgrade after basic MITM.

---

# 1. What This Pattern Actually Is

Pattern 1 taught:

```text
Generate left sums
Generate right sums
Match exact complements
```

Pattern 2 taught:

```text
Generate left sums
Generate right sums
Find best compatible sum
```

Both assumed:

```text
state = sum
```

was enough.

But consider:

```text
subset A:
sum = 15
elements chosen = 2

subset B:
sum = 15
elements chosen = 5
```

If the final problem says:

> Choose exactly `K` elements.

these two states are **not interchangeable**.

Their sums are equal.

But their future compatibility is different.

So:

```text
sum = 15
```

has lost important information.

We need:

```text
(countChosen = 2, sum = 15)
```

and:

```text
(countChosen = 5, sum = 15)
```

as different state classes.

---

# 2. The Core Lesson

The important question is no longer only:

> What value has this partial solution produced?

Ask:

> **What information about this partial solution will determine which states from the other half it is allowed to combine with?**

That information must survive.

This is **state design**.

---

# 3. Why This Pattern Exists

Suppose the original problem says:

```text
Choose exactly K elements
and optimize their sum.
```

A full solution satisfies two conditions:

```text
1. chosenCount = K

2. objective based on chosenSum
```

If we split the decisions:

```text
Left
+
Right
```

then a complete solution must satisfy:

```text
leftCount + rightCount = K
```

and:

```text
chosenSum =
leftSum + rightSum
```

So the final answer depends on **two pieces of information**:

```text
count
sum
```

Therefore each half must preserve both.

---

# 4. The Recognition Question

Whenever you generate MITM states, stop before writing:

```java
List<Long> sums;
```

and ask:

> **If two partial solutions produce the same sum, are they always interchangeable for every possible future combination?**

If yes:

```text
state = sum
```

may be sufficient.

If no:

```text
state must contain more information.
```

That one question prevents a huge number of incorrect MITM solutions.

---

# 5. The State-Sufficiency Test

Imagine two partial solutions:

```text
State A
State B
```

Ask:

> If their currently stored state values are identical, can I replace A with B in every possible future continuation without changing legality or optimality?

If yes:

```text
your state representation is probably sufficient
```

If no:

```text
you compressed too aggressively
```

This idea applies far beyond MITM.

It is also fundamental in:

```text
Dynamic Programming
Dijkstra state design
BFS with extra constraints
bitmask DP
memoization
```

# 6. Canonical Example — LeetCode 2035

**Partition Array Into Two Arrays to Minimize Sum Difference**

We are given:

```text
2n numbers
```

and must divide them into:

```text
Group A → exactly n elements

Group B → exactly n elements
```

while minimizing:

```text
|sum(A) - sum(B)|
```

The problem has:

```text
n <= 15

therefore total elements <= 30
```

and values may be negative.

This is nearly perfect for Pattern 3.

---

# 7. Strip the Story First

Suppose total sum is:

```text
TOTAL
```

If we choose exactly `n` elements for Group A and their sum is:

```text
S
```

then Group B automatically has:

```text
TOTAL - S
```

So the difference becomes:

```text
|S - (TOTAL - S)|
```

Simplify:

```text
|2S - TOTAL|
```

Therefore the real problem is:

> **Choose exactly `n` elements whose sum `S` makes `2S` as close as possible to `TOTAL`.**

Or intuitively:

```text
S should be as close as possible to TOTAL / 2
```

Now the partition story is gone.

---

# 8. First Brute Force

There are:

```text
2n <= 30
```

elements.

But we cannot choose arbitrary subsets.

We must choose exactly:

```text
n
```

elements.

The number of possibilities is approximately:

```text
C(30, 15)
≈ 155 million
```

which is already uncomfortable for an interview-style exact enumeration.

Generic subset enumeration would consider:

```text
2^30
≈ 1 billion
```

states.

Too large.

# 9. What Happens If We Split?

The original array contains:

```text
2n
```

elements.

Split it into two halves:

```text
Left  → n elements
Right → n elements
```

Since:

```text
n <= 15
```

each half has at most:

```text
2^15
=
32,768
```

subsets.

Very manageable.

So MITM immediately becomes interesting.

# 10. The Trap — Storing Only Sum

Suppose we generate:

```text
all left subset sums
all right subset sums
```

and search for:

```text
leftSum + rightSum
≈ TOTAL / 2
```

Looks reasonable.

But it is wrong.

Why?

Because the selected group must contain exactly:

```text
n
```

elements.

Suppose:

```text
leftSum = 20
```

came from:

```text
4 left elements
```

Then the right side MUST contribute:

```text
n - 4
```

elements.

It cannot use an arbitrary right subset whose sum happens to be good.

Therefore:

```text
sum
```

alone does not define compatibility.

---

# 11. The Correct State

Generate states as:

```text
(countChosen, sum)
```

Conceptually:

```text
Left:

count 0 → all sums using exactly 0 elements
count 1 → all sums using exactly 1 element
count 2 → all sums using exactly 2 elements
...
count n → all sums using exactly n elements
```

Same for the right half.

So instead of:

```java
List<Long> left;
```

we need something like:

```java
List<Long>[] leftByCount;
```

---

# 12. The Compatibility Invariant

Suppose a left state selects:

```text
k
```

elements.

The complete chosen group must contain:

```text
n
```

elements.

Therefore the right side must contribute exactly:

```text
n - k
```

elements.

This is the most important invariant of Pattern 3:

> **States may only combine if their metadata satisfies the global constraint.**

For LC2035:

```text
leftCount + rightCount = n
```

Therefore:

```text
leftBucket[k]
```

may only search inside:

```text
rightBucket[n - k]
```

Not every right state.

---

# 13. Why Bucketing Is Better Than Storing Pairs Everywhere

One representation is:

```text
(count, sum)
(count, sum)
(count, sum)
...
```

and repeatedly check counts.

But because:

```text
count
```

takes only:

```text
0 ... n
```

we can group states immediately:

```text
bucket[count]
```

This makes compatibility structural.

Instead of asking:

```text
Is this right state legal?
```

we search only inside the legal bucket.

That is much cleaner.

Suppose the final requirement is:

```text

+

```

Then generate:

```text
statesByMetadata
```

Examples:


The underlying strategy is:

```text
generate
↓

search only compatible classes
```

# 15. Deriving LC2035 Slowly

Let:

```text
TOTAL = sum(nums)
```

We choose one group with exactly:

```text
n
```

elements.

Suppose its chosen sum is:

```text
S
```

Other group:

```text
TOTAL - S
```

Objective:

```text
|S - (TOTAL - S)|
```

therefore:

```text
|2S - TOTAL|
```

We want this minimum.

Now split:

```text
S = L + R
```

So objective becomes:

```text
|2(L + R) - TOTAL|
```

For a fixed:

```text
L
```

we ideally want:

```text
L + R ≈ TOTAL / 2
```

therefore:

```text
R ≈ TOTAL / 2 - L
```

This looks exactly like Pattern 2.

But now the extra constraint says:

```text
if L used k elements

R must use n-k elements
```

So Pattern 3 is really:

```text
Pattern 2 ordered complement search
+
metadata compatibility
```

That is a powerful way to understand it.

---

# 16. The Two-Layer Decision

For every left state:

```text
(count = k, sum = L)
```

we perform two decisions.

### Layer 1 — Which right states are legal?

Only:

```text
rightByCount[n - k]
```

### Layer 2 — Which legal right state is best?

Among that bucket, find:

```text
R
```

making:

```text
L + R
```

closest to:

```text
TOTAL / 2
```

So:

```text
metadata
decides WHERE to search

objective
decides WHAT to search for
```

This sentence is worth remembering.

---

# 17. State Design vs Search Strategy

Keep these separate.

### State Design

```text
(countChosen, sum)
```

answers:

> What information must survive?

### Search Strategy

```text
sort bucket
+
binary search
```

answers:

> Once I know which states are compatible, how do I find the best one?

These solve different problems.

# 26. Generating States by Count

A clean recursive template:

```java
private static void generate(
    int[] nums,
    int index,
    int end,
    int count,
    long sum,
    List<Long>[] buckets
) {
    if (index == end) {
        buckets[count].add(sum);
        return;
    }

    // Skip
    generate(
        nums,
        index + 1,
        end,
        count,
        sum,
        buckets
    );

    // Take
    generate(
        nums,
        index + 1,
        end,
        count + 1,
        sum + nums[index],
        buckets
    );
}
```

The important upgrade from Pattern 2 is:

```java
count + 1
```

and:

```java
buckets[count].add(sum);
```

# 28. Binary Search Target Without Floating Point

We want to minimize:

```text
|2(L + R) - TOTAL|
```

We could think:

```text
R ≈ TOTAL / 2 - L
```

but:

```text
TOTAL / 2
```

might not be an integer.

Using `double` is possible, but unnecessary.

We can instead reason directly with integers.

We need:

```text
2R ≈ TOTAL - 2L
```

Define:

```text
target = TOTAL - 2L
```

and seek an `R` whose:

```text
2R
```

is closest to:

```text
target
```

However, because the right sums themselves are sorted, it is still convenient to binary-search near:

```text
floorDiv(TOTAL, 2) - L
```

and check neighboring candidates.

A simpler interview implementation can use:

```text
TOTAL / 2.0 - L
```

only for deciding the search position, while computing the final answer using integer arithmetic:

```text
Math.abs(
    TOTAL - 2 * (L + R)
)
```

But avoiding floating point entirely is cleaner.

---

# 29. Integer Binary-Search Strategy

For each:

```text
L
```

we need `R` near the point where:

```text
2(L + R)
=
TOTAL
```

Rearrange:

```text
2R
=
TOTAL - 2L
```

Instead of comparing:

```text
R < targetDouble
```

compare:

```text
2 * R < TOTAL - 2 * L
```

This avoids floating-point precision completely.

# 30. Java Helper for Closest Position

Suppose right bucket is sorted.

We want the first `R` such that:

```text
2R >= TOTAL - 2L
```

```java
private static int lowerBoundForHalf(
    List<Long> arr,
    long requiredTwice
) {
    int low = 0;
    int high = arr.size();

    while (low < high) {
        int mid =
            low + (high - low) / 2;

        if (2L * arr.get(mid) < requiredTwice) {
            low = mid + 1;
        } else {
            high = mid;
        }
    }

    return low;
}
```

Then check:

```text
idx
idx - 1
```

just like Pattern 2.

# 31. Full Java Solution — LC2035 Style

```java
import java.util.*;

class Solution {

    private void generate(
        int[] nums,
        int index,
        int end,
        int count,
        long sum,
        List<Long>[] buckets
    ) {
        if (index == end) {
            buckets[count].add(sum);
            return;
        }

        // Skip current element
        generate(
            nums,
            index + 1,
            end,
            count,
            sum,
            buckets
        );

        // Take current element
        generate(
            nums,
            index + 1,
            end,
            count + 1,
            sum + nums[index],
            buckets
        );
    }

    private int lowerBoundForHalf(
        List<Long> arr,
        long requiredTwice
    ) {
        int low = 0;
        int high = arr.size();

        while (low < high) {
            int mid =
                low + (high - low) / 2;

            if (2L * arr.get(mid)
                < requiredTwice) {

                low = mid + 1;
            } else {
                high = mid;
            }
        }

        return low;
    }

    public int minimumDifference(int[] nums) {

        int totalElements = nums.length;
        int n = totalElements / 2;

        long total = 0;

        for (int num : nums) {
            total += num;
        }

        List<Long>[] left =
            new ArrayList[n + 1];

        List<Long>[] right =
            new ArrayList[n + 1];

        for (int i = 0; i <= n; i++) {
            left[i] = new ArrayList<>();
            right[i] = new ArrayList<>();
        }

        generate(
            nums,
            0,
            n,
            0,
            0L,
            left
        );

        generate(
            nums,
            n,
            totalElements,
            0,
            0L,
            right
        );

        for (int count = 0;
             count <= n;
             count++) {

            Collections.sort(right[count]);
        }

        long best = Long.MAX_VALUE;

        for (int leftCount = 0;
             leftCount <= n;
             leftCount++) {

            int rightCount =
                n - leftCount;

            List<Long> rightBucket =
                right[rightCount];

            for (long leftSum :
                 left[leftCount]) {

                // We want:
                // 2 * (leftSum + rightSum)
                // to be as close as possible to total.

                long requiredTwice =
                    total - 2L * leftSum;

                int idx =
                    lowerBoundForHalf(
                        rightBucket,
                        requiredTwice
                    );

                if (idx < rightBucket.size()) {
                    long selected =
                        leftSum
                        + rightBucket.get(idx);

                    best = Math.min(
                        best,
                        Math.abs(
                            2L * selected - total
                        )
                    );
                }

                if (idx > 0) {
                    long selected =
                        leftSum
                        + rightBucket.get(idx - 1);

                    best = Math.min(
                        best,
                        Math.abs(
                            2L * selected - total
                        )
                    );
                }
            }
        }

        return (int) best;
    }
}
```

# 32. The Three Most Important Lines

Do not memorize the whole code.

Understand these lines:

```java
int rightCount =
    n - leftCount;
```

because:

```text
metadata compatibility
```

determines the legal bucket.

Then:

```java
long requiredTwice =
    total - 2L * leftSum;
```

because:

```text
2 * rightSum
```

should compensate for what the left side contributed.

Then:

```java
lowerBoundForHalf(
    rightBucket,
    requiredTwice
);
```

because we want the numerically closest legal state.

That is the complete architecture.

# 33. The Core Invariant

Throughout the algorithm:

> **Every candidate considered selects exactly `n` elements because a state from `left[k]` is only paired with a state from `right[n-k]`.**

And within that legal class:

> **Binary search finds the right-side sum nearest to the value that would make the selected-group sum equal to half the total.**

There are therefore two correctness layers:

```text
legality invariant
+
optimization invariant
```

# 35. Pattern 3 Is Often Built on Top of Pattern 1 or 2

This is important.

Constraint-Aware MITM is not necessarily a completely separate joining mechanism.

Often it means:

```text
first filter by metadata compatibility
```

then perform:

```text
Pattern 1 exact complement
```

or:

```text
Pattern 2 best complement
```

inside that compatible group.

Think:

```text
Pattern 1:
exact value compatibility

Pattern 2:
ordered value compatibility

Pattern 3:
metadata compatibility
+
Pattern 1 or Pattern 2
```

That is a much cleaner mental model than treating everything as unrelated patterns.

# 37. When Does `sum` Stop Being Enough?

Here are some signals.

### Exact number of selected elements

```text
state =
(count, sum)
```

### Limited number of special operations

```text
state =
(operationsUsed, score)
```

### Need a particular parity

```text
state =
(parity, sum)
```

### Multiple categories have quotas

Possible state:

```text
(categoryCountA,
 categoryCountB,
 value)
```

### Need reconstruction

Possible state:

```text
(sum, mask)
```

although reconstruction metadata may not affect compatibility itself.

The rule remains:

> Preserve every property future decisions depend on—but nothing unnecessary.

# 38. Why We Should Not Store Everything

The opposite mistake is also dangerous.

Suppose you store:

```text

count
minimum
maximum
mask
firstIndex
lastIndex
...
```

even though future decisions only depend on:

```text

```

Then:

```text
memory increases

```

Good state design means:

> **Smallest sufficient state.**

Not:

> Maximum possible information.

# 39. A Powerful State-Design Question

When considering whether some metadata is necessary, ask:

> **If I delete this field, can I construct two partial solutions that now look identical but have different legal future continuations?**

If yes:

```text
field is necessary
```

If no:

```text
field may be unnecessary
```

Example:

Delete `count` from LC2035.

Then:

```text
sum = 10 using 1 element
```

and:

```text
sum = 10 using 4 elements
```

become indistinguishable.

But they require different right-side counts.

Therefore:

```text
count is necessary.
```

# 40. Strong Variation — Split Array With Same Average

LeetCode 805 asks whether an array can be divided into two non-empty groups having the same average, with:

```text
nums.length <= 30
```

which makes MITM feasible.

At first this does not look like:

```text
subset sum
```

The valuable lesson is:

> **Sometimes we must transform the mathematics before we even know what state to store.**

# 41. Derive the Average Condition

Let:

```text
N = total number of elements
TOTAL = total sum
```

Suppose chosen subset A has:

```text
k elements
sum = S
```

We require:

```text
average(A)
=
average(entire array)
```

So:

```text
S / k
=
TOTAL / N
```

Cross multiply:

```text
S * N
=
TOTAL * k
```

This is the important equation.

Notice what it depends on:

```text
S
k
```

Again:

```text
sum alone is not enough.
```

# 42. Two Ways to Represent LC805 State

## Representation A — Preserve Count

Store:

```text
(count, sum)
```

For every possible total chosen count:

```text
k
```

we need:

```text
chosenSum =
TOTAL * k / N
```

if that value is integral.

Then combine compatible left/right count buckets.

This strongly matches Pattern 3.

---

## Representation B — Algebraic Transformation

Transform every value:

```text
nums[i]
→
nums[i] * N - TOTAL
```

Now for any subset with `k` elements:

```text
Σ(nums[i] * N - TOTAL)
```

equals:

```text
N * subsetSum
-
k * TOTAL
```

A subset has the same average as the full array exactly when:

```text
N * subsetSum
=
k * TOTAL
```

therefore transformed sum is:

```text
0
```

So the problem becomes:

```text
find a non-empty proper subset
whose transformed sum = 0
```

This is now Pattern 1 exact complement MITM.

The published solution describes this transformation and obtains roughly `O(N·2^(N/2))` time.

---

# 43. Why LC805 Is Such a Valuable Problem

It teaches something deeper than another MITM implementation:

```text
Sometimes metadata can be
encoded algebraically into the state itself.
```

Originally:

```text
state =
(count, sum)
```

After transformation:

```text
state =
transformedSum
```

because count information is implicitly embedded in:

```text
nums[i] * N - TOTAL
```

This is a powerful optimization mindset.

---

# 44. But Be Careful — The Whole Array Is Not Allowed

LC805 requires:

```text
A non-empty
B non-empty
```

Therefore selecting:

```text
all elements
```

as A is invalid.

The transformed total sum of the entire array is automatically:

```text
0
```

because:

```text
N * TOTAL
-
N * TOTAL
=
0
```

So blindly checking:

```text
any zero-sum subset
```

without excluding the complete array gives a false positive.

This is an excellent example of:

> A mathematical transformation can preserve the equation while still requiring original problem constraints to be enforced separately.

# 47. Why Not Use One Giant HashMap?

You could theoretically use:

```text
Map<(count,sum), ...>
```

But when metadata has a tiny discrete domain like:





# 48. Complexity of LC2035-Style MITM

Each half contains:

```text
n <= 15
```

elements.

Number of generated states per half:

```text
2^n
```

All buckets together still contain exactly:

```text
2^n
```

states.

Bucketing does not create extra states.

It only organizes them.

---

## Generation

```text
O(2^n)
```

per half.

---

## Sorting

Across all right buckets:

```text
O(n × 2^n)
```

as a simple upper bound.

---

## Binary Searching

Every left state performs:

```text
O(log 2^n)
=
O(n)
```

search.

Therefore overall:

```text
O(n × 2^n)
```

where the original array size is:

```text
2n
```

Equivalently, in terms of total input length `N = 2n`:

```text
O(
    N × 2^(N/2)
)
```

Space:

```text
O(2^(N/2))
```

The standard MITM solution for LC2035 uses the same grouping-by-cardinality idea.

---

# 49. Why Bucket Sizes Follow Binomial Coefficients

For a half containing:

```text
n
```

elements:

```text
bucket[k]
```

contains:

```text
C(n, k)
```

states.

Example for:

```text
n = 4
```

bucket sizes:

```text
count 0 → C(4,0) = 1

count 1 → C(4,1) = 4

count 2 → C(4,2) = 6

count 3 → C(4,3) = 4

count 4 → C(4,4) = 1
```

Total:

```text
1 + 4 + 6 + 4 + 1
=
16
=
2^4
```

So bucketing doesn't change total enumeration size.

It organizes the search intelligently.

# 50. Common Mistake — Ignoring Metadata

### Mistake

Generate:

```text
all left sums
all right sums
```

and search globally.

### Why It Happens

Pattern 2 is already familiar.

### Failure

Numerically good combinations may violate:

```text
exact chosen count
```

### Prevention Rule

Before generating states, list every global constraint.

Ask:

```text
Can this constraint be verified using
only the state I plan to store?
```

---

# 51. Common Mistake — Searching the Wrong Bucket

Suppose:

```text
required total count = n
```

and left subset contains:

```text
k
```

elements.

Correct:

```java
rightCount = n - k;
```

Common mistakes:

```java
rightCount = k;
```

or:

```java
rightCount = n - k - 1;
```

### Prevention Rule

Write the invariant first:

```text
leftCount + rightCount = n
```

Then rearrange.

---

# 52. Common Mistake — Forgetting Count 0 and Count n

Buckets:

```text
0
...
n
```

are all necessary.

Why?

The selected group might choose:

```text
0 elements from left
+
n from right
```

or:

```text
n from left
+
0 from right
```

Both are perfectly valid.

So allocate:

```java
new ArrayList[n + 1];
```

not:

```java
new ArrayList[n];
```

---

# 53. Common Mistake — Using Positive-Only Pruning

LC2035 allows negative numbers.

Therefore:

```java
if (sum > target) {
    return;
}
```

is generally invalid.

A later negative number may reduce the sum.

Pattern 3 itself gives no pruning guarantee.

---

# 54. Common Mistake — Minimizing the Wrong Expression

The two group sums are:

```text
S
TOTAL - S
```

Difference:

```text
|S - (TOTAL-S)|
```

not:

```text
|S - TOTAL|
```

Correct simplification:

```text
|2S - TOTAL|
```

This should be written before any binary-search logic.

---

# 55. Common Mistake — Using `TOTAL / 2` Carelessly

If:

```text
TOTAL
```

is odd or negative, integer division can shift the boundary.

Safer final comparison:

```java
Math.abs(
    2L * selectedSum - total
)
```

Use half-target reasoning only to locate nearby candidates.

Evaluate the objective exactly with integers.

---

# 56. Common Mistake — Over-Enriching the State

Suppose compatibility depends only on:

```text
count
```

and optimization depends only on:

```text
sum
```

Do not also store:

```text
min
max
indices
```

unless needed.

### Rule

> Store the smallest sufficient state.

# 57. Pattern Boundary — Pattern 2 vs Pattern 3

Pattern 2:

```text
Every right sum is potentially compatible.
```

We simply need the best numerical one.

Pattern 3:

```text
Only a subset of right states is legally compatible.
```

We first restrict the search using metadata.

Then optimize.

# 58. Pattern Boundary — DP State Design

This pattern strongly resembles DP state design.

In DP we ask:

> What information uniquely determines the future?

In MITM Pattern 3 we ask:

> What information determines which opposite-half states this partial solution may combine with?

Same principle.

Different search architecture.

That is why understanding Pattern 3 improves more than MITM.

# 59. Pattern Boundary — Bitmask DP

With:

```text
N <= 20
```

bitmask DP may directly represent the entire selected set.

With:

```text
N around 30–40
```

that may become too expensive.

MITM instead:

```text
splits mask decisions
+
stores compressed partial states
```

Do not choose by topic name.

Choose by state-space size and required transitions.


# 64. Interview Explanation — LC2035

A clean 60–90 second explanation:

> We need to choose exactly half of the elements for one group. If their sum is `S` and the total sum is `T`, the partition difference is `|2S - T|`, so we want a valid `S` as close as possible to `T/2`.
>
> Enumerating all subsets of up to 30 elements is too expensive, so I'll split the array into two halves of at most 15 elements and enumerate all subset states from each.
>
> The important part is that I cannot store only the subset sum, because the final chosen group must contain exactly `n` elements. I'll bucket subset sums by how many elements produced them. A left state using `k` elements may only combine with a right state using `n-k`.
>
> I'll sort each right-count bucket. For every left sum in bucket `k`, I'll binary-search the compatible `n-k` bucket for the right sum that makes the selected total closest to half of the overall sum. Then I'll evaluate the exact difference as `|2 * selectedSum - total|`.

That explanation demonstrates actual understanding.

---

# 65. Interview Explanation — General Pattern

For a generic Pattern 3 problem:

> MITM makes the exponential search manageable by splitting the decisions, but before generating states I need to determine what information a partial solution must preserve. Here, two partial solutions with the same objective value are not equivalent because their compatibility depends on additional metadata. So I'll store states grouped by that metadata, combine only compatible groups, and then apply the appropriate exact or ordered complement search within those groups.

That sentence generalizes very well.

# 69. The One-Line Pattern Memory

> **When two partial solutions with the same obvious value are not interchangeable because future legality depends on additional information, enrich the MITM state with that metadata, group states by compatibility, and only then perform exact or ordered complement matching.**

Code memory:

```java
int rightCount =
    requiredCount - leftCount;

List<Long> candidates =
    right[rightCount];
```

Reasoning memory:

```text
Don't ask only:

"What value did this half produce?"

Also ask:

"What must the other half know
about HOW this value was produced?"
```

That is Pattern 3.
