# Meet in the Middle — Pattern 1

# Exact Complement Matching

> **I can independently generate possible states from two halves, and a valid full solution exists when one state is the exact complement of the other.**

Canonical form:

```text
leftState + rightState = target
```

Therefore:

```text
rightState = target - leftState
```

That transformation is the heart of this pattern.

---

# 1. What This Pattern Actually Is

Strip away all story-specific language.

This pattern is:

> **Generate every feasible partial result from two independent groups, then for each result from one group look for the exact complementary result required from the other group.**

The problem might talk about:

```text
numbers
prices
weights
scores
moves
signed choices
chemical quantities
```

but underneath it may simply be:

```text
L + R = X
```

Once you reach that equation, the story is mostly gone.

---

# 2. Why This Pattern Exists

Suppose we have:

```text
N <= 40
```

numbers and want to determine something about subsets summing to:

```text
target
```

Each element gives:

```text
take
skip
```

So direct enumeration gives:

```text
2^N
```

For:

```text
N = 40
```

that is around:

```text
10^12
```

Too large.

---

## Can ordinary DP solve it?

Maybe.

If:

```text
target
```

is small, a sum-based DP might be excellent.

But suppose values and target are huge.

Then:

```text
dp[sum]
```

may require an impossible state range.

So we have:

```text
Brute force by choices
        ↓
       2^N
        ↓
    too expensive

Sum-based DP
        ↓
huge numeric state space
        ↓
    too expensive
```

But:

```text
N itself is still moderate
```

Now split:

```text
N
↓
N/2 + N/2
```

and enumerate:

```text
2^(N/2)
```

states on each side.

The remaining challenge becomes:

> How do we combine the two state sets without comparing every pair?

For exact target problems, the algebra gives us the answer.

```text
L + R = target
```

Rearrange:

```text
R = target - L
```

We no longer need to scan every right state.

We need an efficient lookup.

That is Pattern 1.

---

# 3. Recognition Signals

When reading an unfamiliar problem, ask these questions.

---

## Q1 — Does the natural brute force enumerate combinations?

Examples:

```text
take / don't take
+ / -
choose one of several options
```

If the search looks like:

```text
2^N
3^N
```

continue investigating.

---

## Q2 — Is the full exponential search too large, while half-search is plausible?

Calculate both.

Example:

```text
N = 40

2^40
≈ 10^12
❌

2^20
≈ 10^6
✅
```

This is a strong signal.

---

## Q3 — Can a full solution be decomposed into two independent contributions?

For subset sum:

```text
totalSum
=
sum(chosen from left)
+
sum(chosen from right)
```

That means:

```text
answer
=
leftState + rightState
```

Good.

---

## Q4 — Does validity reduce to an exact relation?

Examples:

```text
L + R = target

L - R = target

L = R

f(left) = target - g(right)
```

If yes, exact complement matching becomes possible.

---

## Q5 — Can the complement be looked up efficiently?

For:

```text
R = target - L
```

we can organize right-side states using:

```text
HashSet
HashMap
sorting
binary search
two pointers
```

Then MITM actually saves work.

---

# 4. Trigger Words — But Don't Depend on Them

Statements may explicitly contain language like:

```text
subset
exact sum
target
equal sum
number of ways
possible or impossible
choose some elements
```

Those are useful hints.

But do NOT learn:

```text
"exact sum"
→ MITM
```

Because exact sum might instead be solved by:

```text
DP
bitset DP
hash-set DP
simple brute force
```

depending on the constraints.

The real structural trigger is:

> **The solution space is exponential, full enumeration is too large, half enumeration is feasible, and the final condition can be expressed as an exact relationship between independently generated partial states.**

# 5. How This Pattern Can Be Disguised

The statement might never say:

```text
subset
```

Suppose every item has three choices:

```text
ignore it
use value A[i]
use value B[i]
```

Now brute force is:

```text
3^N
```

If:

```text
3^N
```

is enormous but:

```text
3^(N/2)
```

is feasible, and total contribution must equal `K`, we still have:

```text
leftContribution + rightContribution = K
```

Same pattern.

The state-generation method changed.

The join logic did not.

# 6. The Core Invariant

For ordinary subset-sum MITM, after splitting the original array into:

```text
Left Half
Right Half
```

the fundamental invariant is:

> **Every subset of the original array can be represented uniquely as the union of one subset chosen from the left half and one subset chosen from the right half.**

Therefore every original subset has a unique decomposition:

```text
Original Subset
=
Left Part
∪
Right Part
```

and its sum satisfies:

```text
Total
=
Left Sum
+
Right Sum
```

This is why we lose nothing by splitting.

---

## Counting Invariant

If we store:

```text
leftFrequency[s]
```

then it must mean:

> `leftFrequency[s]` equals the number of distinct left-half subsets whose sum is exactly `s`.

For every right-half subset with sum `r`, the only left subsets capable of creating the target are those with:

```text
sum = target - r
```

So we add:

```text
leftFrequency[target - r]
```

to the answer.

That is the complete correctness argument.

---

# 7. Deriving the Algorithm Slowly

Suppose the problem asks:

> How many subsets have sum exactly `X`?

And:

```text
N <= 40
```

with large values.

Do not immediately say:

> MITM.

Walk through the reasoning.

---

## Step 1 — What Is the Brute Force?

Every element has:

```text
take
skip
```

So:

```text
2^N
```

subsets.

---

## Step 2 — Why Is It Too Slow?

At:

```text
N = 40
```

we have roughly:

```text
10^12
```

states.

Not viable.

---

## Step 3 — Can DP Rescue Us?

A sum-indexed DP depends on the numeric range.

If the values/target are huge, the state space may also be huge.

So that direction may be blocked.

---

## Step 4 — What Property Can We Exploit?

`N` is not tiny enough for full brute force.

But half of `N` is.

```text
2^(N/2)
```

is feasible.

So split the decisions.

---

## Step 5 — What Information Does Each Half Need to Produce?

For exact subset sum, we don't care which elements produced a partial result yet.

We only need:

```text
sum
```

So:

```text
LeftStates  = all left subset sums
RightStates = all right subset sums
```

---

## Step 6 — What Does a Valid Pair Look Like?

We need:

```text
leftSum + rightSum = target
```

For a known right sum:

```text
rightSum = r
```

the required left sum is uniquely determined:

```text
requiredLeft = target - r
```

This is the structural observation.

---

## Step 7 — What Operation Repeats?

For every right state:

```text
find how many left states equal target - right
```

The expensive operation would be rescanning all left states every time.

So store left states in a structure supporting exact lookup.

---

## Step 8 — Which Structure Naturally Supports That?

If we only care whether a state exists:

```text
HashSet
```

If we need how many times it occurs:

```text
HashMap<sum, frequency>
```

Alternatively:

```text
sort
+
binary search / two pointers
```

Now the algorithm feels derived rather than memorized.

---

# 8. Why a Frequency Map Is Different From a Set

This distinction is crucial.

Suppose left-half states contain:

```text
[3, 3, 5]
```

There are two different subsets producing sum `3`.

If we store:

```java
HashSet<Long>
```

we only retain:

```text
3 exists
```

but lose:

```text
3 occurs twice
```

That is fine for:

```text
Does a solution exist?
```

but wrong for:

```text
How many solutions exist?
```

For counting, use:

```text
sum → frequency
```

not just:

```text
sum → exists
```

---

# 9. Why Duplicates Must Usually Be Preserved

Suppose the array contains:

```text
[2, 2]
```

These are two different elements at different indices.

The subsets:

```text
take first 2

take second 2
```

are different subsets even though both have sum:

```text
2
```

Therefore:

```text
state values may duplicate
```

and those duplicates can represent genuinely different choices.

Never deduplicate unless the problem explicitly allows it.

---

# 10. Why This Data Structure?

## HashSet

Use when the question is only:

```text
Does any complement exist?
```

Typical operation:

```java
if (seen.contains(target - current)) {
    ...
}
```

---

## HashMap

Use when the question asks:

```text
How many?
```

Typical operation:

```java
answer += freq.getOrDefault(target - current, 0L);
```

---

## Sorted Array

Useful when:

* you want primitive arrays rather than boxed `HashMap<Long, ...>` objects,
* deterministic worst-case behavior matters,
* later variations need ordering,
* duplicate counting can be handled with binary search or two pointers.

---

# 11. Why Not Just Use an Array?

Because the possible sums may be enormous or negative.

For example:

```text
-10^12
...
+10^12
```

You cannot allocate an array indexed across that whole range.

Hashing stores only states that actually occur.

---

# 12. Why Not Sort the Original Input?

Sorting the original numbers does not remove the exponential subset-choice problem.

The difficult part is:

```text
which combination of elements do I choose?
```

not:

```text
what order are the elements in?
```

MITM enumerates **choice states**, not element order.

---

# 13. Why Not Compare All Left and Right States?

Suppose:

```text
|L| = |R| = 2^(N/2)
```

Nested comparison gives:

```text
2^(N/2) × 2^(N/2)
=
2^N
```

which is exactly what we were trying to avoid.

This is the most important implementation trap in MITM.

---

# 14. Core Java Template — Exact Existence

This is the clean conceptual skeleton.

```java
import java.util.*;

class Solution {

    private void generate(long[] nums, int index, int end, long sum, Set<Long> states) {
        if (index == end) {
            states.add(sum);
            return;
        }

        // Skip
        generate(nums, index + 1, end, sum, states);

        // Take
        generate(nums, index + 1, end, sum + nums[index], states);
    }

    public boolean existsSubsetWithSum(long[] nums, long target) {
        int n = nums.length;
        int mid = n / 2;

        Set<Long> leftStates = new HashSet<>();

        generate(nums, 0, mid, 0L, leftStates);

        return searchRight(nums, mid, n, 0L, target, leftStates);
    }

    private boolean searchRight(long[] nums, int index, int end, long sum, long target, Set<Long> leftStates) {
        if (index == end) {
            return leftStates.contains(target - sum);
        }

        if (searchRight(nums, index + 1, end, sum, target, leftStates)) {
            return true;
        }

        return searchRight(nums, index + 1, end, sum + nums[index], target, leftStates);
    }
}
```

The important part is not the recursion syntax.

It is:

```java
leftStates.contains(target - rightSum)
```

That line is the pattern.

# 15. Core Java Template — Exact Counting

If we need the number of subsets:

```java
import java.util.*;

class Solution {

    private void generateLeft(long[] nums, int index, int end, long sum, Map<Long, Long> freq) {
        if (index == end) {
            freq.merge(sum, 1L, Long::sum);
            return;
        }

        generateLeft(nums, index + 1, end, sum, freq);

        generateLeft(nums, index + 1, end, sum + nums[index], freq);
    }

    private long countRight(long[] nums, int index, int end, long sum, long target, Map<Long, Long> leftFreq) {
        if (index == end) {
            long need = target - sum;

            return leftFreq.getOrDefault(need, 0L);
        }

        long skip = countRight(nums, index + 1, end, sum, target, leftFreq);

        long take = countRight(nums, index + 1, end, sum + nums[index], target, leftFreq);

        return skip + take;
    }

    public long countSubsets(long[] nums, long target) {
        int n = nums.length;
        int mid = n / 2;

        Map<Long, Long> leftFreq = new HashMap<>();

        generateLeft(nums, 0, mid, 0L, leftFreq);

        return countRight(nums, mid, n, 0L, target, leftFreq);
    }
}
```

Again, the key line is:

```java
long need = target - sum;
```

followed by:

```java
leftFreq.getOrDefault(need, 0L);
```

    }

# 17. Pattern Boundary — Exact vs Best Compatible State

Do not confuse Pattern 1 with the next MITM pattern.

| Question            | Pattern 1 — Exact Complement   | Pattern 2 — Best Compatible       |
| ------------------- | ------------------------------ | --------------------------------- |
| Required relation   | `L + R == X`                   | `L + R <= X` or closest to `X`    |
| Desired right state | exactly `X - L`                | best state around/below `X - L`   |
| Ordering required?  | not necessarily                | usually yes                       |
| Natural tool        | hash lookup                    | sorting + binary search           |
| Main question       | "Does/count this exact state?" | "Which compatible state is best?" |

This boundary is important.

If the problem says:

```text
maximum subset sum <= X
```

the exact complement may not exist.

Looking only for:

```text
X - L
```

would fail.

We need the **largest value below** that complement.

That is Pattern 2.

---

# 18. Pattern Boundary — MITM vs Sum DP

| Question               | MITM                 | Sum DP                        |
| ---------------------- | -------------------- | ----------------------------- |
| Exploited dimension    | relatively small `N` | relatively small sum/capacity |
| Typical state count    | `2^(N/2)`            | `N × target`                  |
| Good when values huge? | often yes            | often no                      |
| Good when `N` huge?    | usually no           | possibly                      |
| Exact?                 | yes                  | yes                           |

Always inspect constraints before choosing.

# 19. When NOT to Use This Pattern

## Negative Signal 1

```text
N <= 20
```

and straightforward:

```text
2^N
```

enumeration is already comfortably feasible.

Don't complicate the solution.

---

## Negative Signal 2

```text
target
```

is tiny and DP is obviously cheaper.

Example:

```text
N = 100
target = 1000
```

MITM is not the natural first choice.

---

## Negative Signal 3

The final condition is not exact equality.

If the problem asks:

```text
maximum total <= X
```

that belongs to ordered/best-compatible MITM.

---

## Negative Signal 4

The halves require additional compatibility information.

If the final solution requires:

```text

```

then:

```text

```

may be insufficient.

That moves us toward Constraint-Aware MITM.

# 20. Deep Worked Example — CSES 1628: Meet in the Middle

## Problem

Given up to `40` numbers, count how many subsets have sum exactly `x`.

This is our anchor problem because the constraints force the algorithmic decision cleanly.

---

## Step 1 — Strip the Story

We have:

```text
Input:
N numbers

Decision:
each number is either selected or not selected

Output:
number of subsets whose sum equals X
```

Mathematically:

```text
count S ⊆ {0 ... N-1}

such that

Σ nums[i] = X
for i ∈ S
```

---

# Step 2 — Start With Brute Force

For every number:

```text
take
skip
```

So:

```text
2^N
```

possible subsets.

At:

```text
N = 40
```

this is approximately:

```text
10^12
```

Too large.

---

# Step 3 — Consider Sum DP

A traditional subset-sum DP might use:

```text
dp[sum]
```

But the values and target may be extremely large.

A DP whose complexity depends directly on the numeric sum range is not attractive.

So both obvious approaches are blocked.

---

# Step 4 — What Are We Repeatedly Recomptuing?

Every full subset can be decomposed into:

```text
choices among first half

+

choices among second half
```

Suppose:

```text
N = 40
```

Then each side has about:

```text
20
```

elements.

Each side has only:

```text
2^20
≈ 10^6
```

subsets.

That is feasible.

---

# Step 5 — What Information Do We Actually Need to Preserve?

For this problem, from a partial subset we only need:

```text
its sum
```

We do not need:

```text
its exact indices
its ordering
its minimum
its maximum
```

So generate:

```text
LeftSums
RightSums
```

---

# Step 6 — What Relationship Must They Satisfy?

A full subset has sum `X` exactly when:

```text
leftSum + rightSum = X
```

Therefore for a right sum:

```text
r
```

we require:

```text
leftSum = X - r
```

This is the key observation.

---

# Step 7 — Small Dry Run

Use:

```text
nums = [1, 2, 3, 2]

target = 5
```

Split:

```text
Left  = [1, 2]
Right = [3, 2]
```

---

## Generate Left Subset Sums

```text
{}       → 0
{1}      → 1
{2}      → 2
{1,2}    → 3
```

So:

```text
LeftSums =
[0, 1, 2, 3]
```

---

## Generate Right Subset Sums

```text
{}       → 0
{3}      → 3
{2}      → 2
{3,2}    → 5
```

So:

```text
RightSums =
[0, 3, 2, 5]
```

---

## Match Complements

For:

```text
right = 0
```

need:

```text
5 - 0 = 5
```

No left subset sum `5`.

---

For:

```text
right = 3
```

need:

```text
5 - 3 = 2
```

Left contains `2`.

One solution.

---

For:

```text
right = 2
```

need:

```text
5 - 2 = 3
```

Left contains `3`.

Second solution.

---

For:

```text
right = 5
```

need:

```text
5 - 5 = 0
```

Left contains `0`.

Third solution.

So:

```text
answer = 3
```

---

# Step 8 — Why the Empty Subset Matters

Notice the third solution used:

```text
left sum = 0
```

That corresponds to:

```text
choose nothing from the left half
```

Every half-state generation must include:

```text
0
```

because a valid full subset may select all its elements from only one half.

Forgetting the empty subset is a classic MITM bug.

---

# Step 9 — Performance-Friendly Java Solution

For conceptual teaching, a frequency map is extremely clear.

But when we potentially generate around one million states in Java, primitive arrays avoid the overhead of millions of boxed `Long` objects.

So for a performance-oriented implementation we can:

```text
generate all left sums
generate all right sums
sort both
use two pointers
count duplicate groups
```

The underlying pattern remains exact complement matching.

```java
import java.io.*;
import java.util.*;

public class Main {

    static int generateSums(
            long[] nums,
            int index,
            int end,
            long sum,
            long[] output,
            int pos
    ) {
        if (index == end) {
            output[pos] = sum;
            return pos + 1;
        }

        // Skip current element
        pos = generateSums(
                nums,
                index + 1,
                end,
                sum,
                output,
                pos
        );

        // Take current element
        pos = generateSums(nums, index + 1, end, sum + nums[index], output, pos);

        return pos;
    }
}
```

# 21. Why the Two-Pointer Join Works

After sorting:

```text
left ascending
right ascending
```

we start with:

```text
smallest left
+
largest right
```

Suppose:

```text
left[i] + right[j] < target
```

The current left value is too small.

Moving `j` left would only make the right value smaller.

So that cannot help.

We need:

```text
larger left
```

Therefore:

```java
i++;
```

---

Suppose:

```text
left[i] + right[j] > target
```

The sum is too large.

Increasing `i` would make it even larger.

We need:

```text
smaller right
```

Therefore:

```java
j--;
```

---

When:

```text
left[i] + right[j] == target
```

we must count all duplicates on both sides.

If:

```text
leftValue occurs A times
rightValue occurs B times
```

then those states produce:

```text
A × B
```

different subset combinations.

This is why duplicate counting matters.

---

# 22. Complexity of the Worked Solution

Let:

```text
L = 2^(floor(N/2))

R = 2^(ceil(N/2))
```

---

## State Generation

We generate each subset state once.

Approximately:

```text
O(L + R)
```

---

## Sorting

```text
O(L log L + R log R)
```

---

## Two-Pointer Join

Each pointer moves in only one direction.

So:

```text
O(L + R)
```

---

## Overall

Dominated by sorting:

```text
O(N × 2^(N/2))
```

roughly.

---

## Space

We store the two state arrays:

```text
O(2^(N/2))
```

states.

# 23. Interview Explanation — 60–90 Seconds

A good explanation before coding would sound like:

> Each element has a take-or-skip choice, so brute force considers `2^N` subsets. With `N` around `40`, that's roughly `2^40`, which is too large. A sum-indexed DP is also unattractive when the values or target are very large.
>
> But if I split the array into two halves, each side has only around `20` elements, so I can enumerate roughly `2^20` subset sums per half. Every original subset can be represented uniquely as one left subset plus one right subset.
>
> For a left sum `L`, I need a right sum `R = target - L`. So instead of comparing every left state with every right state, I can store or sort one side and look up the required complement efficiently. Since we're counting subsets, I also need to preserve duplicate frequencies rather than just existence.
>
> This reduces the search from about `2^N` to roughly `2^(N/2)` states, with an additional hashing or sorting cost depending on the implementation.

That is enough.

Do not begin by saying:

> "This is Meet in the Middle."

Show why first.

Then name it.

# 24. Common Mistakes

## Mistake 1 — Seeing `N <= 40` and immediately using MITM

### Why it happens

You memorize the constraint instead of the structure.

### Detection

Ask:

```text
Where is the exponential decision space?
```

If you cannot answer that, your MITM suspicion is weak.

### Prevention Rule

```text
Constraint is only evidence.
Search-space structure is the reason.
```

---

## Mistake 2 — Splitting But Using Nested Loops to Join

```java
for (long l : left) {
    for (long r : right) {
        ...
    }
}
```

### Why it happens

You remember the split but forget the purpose.

### Detection

Multiply your half-state counts.

### Prevention Rule

> Before coding the join, explicitly write the compatibility equation.

Example:

```text
R = target - L
```

---

## Mistake 3 — Using a Set for a Counting Problem

### Why it happens

A set feels natural for exact complement lookup.

### Failure

Different subsets producing the same sum collapse into one entry.

### Prevention Rule

Ask:

```text
Do I need existence
or multiplicity?
```

---

## Mistake 4 — Forgetting the Empty Subset

### Why it happens

You start generating states only after selecting something.

### Failure

Solutions entirely contained in one half disappear.

### Prevention Rule

Every half enumeration begins from:

```text
sum = 0
```

---

## Mistake 5 — Using `int` for Generated Sums

### Why it happens

Input elements themselves fit inside `int`.

### Failure

Subset sums overflow.

### Prevention Rule

Compute:

```text
N × maxValue
```

before choosing the type.

When in doubt for MITM sums in Java:

```java
long
```

---

## Mistake 6 — Pruning `sum > target` Without Checking Preconditions

Suppose all values are positive.

Then if:

```text
sum > target
```

that branch may safely be pruned for an exact positive-target problem.

But if negative numbers exist:

```text
sum = 20
target = 10
```

a later:

```text
-10
```

could bring the sum back to the target.

### Prevention Rule

Never copy pruning logic without proving monotonicity.

---

## Mistake 7 — Thinking All Duplicate Sums Are Redundant

For existence:

```text
duplicates may be removable
```

For counting:

```text
duplicates carry multiplicity
```

Know what the problem asks.

---

## Follow-Up 2 — "Return one actual subset."

Now storing only:

```text
sum
```

is insufficient for reconstruction.

We need to preserve something like:

```text
sum → mask
```

or:

```text
(sum, chosenMask)
```

Then after finding the complement, reconstruct choices from both halves.

The MITM structure remains unchanged.

The stored state becomes richer.

---

## Follow-Up 3 — "Values may be negative."

Classical exact complement matching still works.

But pruning such as:

```text
if (sum > target) return;
```

is no longer safe.

The core MITM invariant survives.

The pruning invariant does not.

---

## Follow-Up 4 — "Find the maximum subset sum <= X."

Now:

```text
exact complement lookup
```

is insufficient.

For fixed `L`, we need:

```text
largest R <= X - L
```

That changes the join relation.

This leads directly to:

```text
Pattern 2 — Best Compatible State
```

---

## Follow-Up 5 — "Choose exactly K elements."

Now:

```text
state = sum
```

loses required information.

We need:

```text
state = (countChosen, sum)
```

This leads to:

```text
Pattern 3 — Constraint-Aware MITM
```

---

## Follow-Up 6 — "Each item has three choices."

For example:

```text
skip
take A[i]
take B[i]
```

The search becomes:

```text
3^N
```

Half-enumeration becomes:

```text
3^(N/2)
```

The exact complement join may remain identical.

This teaches an important lesson:

> Pattern 1 is about exact compatible states, not specifically binary subsets.

need = target - partialState;
