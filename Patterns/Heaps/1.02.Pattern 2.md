# Heap Pattern 2: K-Way Merge (One Slot Per Source)

*A focused deep-dive on the second most common heap pattern — what it is, how to tell it apart from Pattern 1, how to derive the approach on an unseen problem, and a curated question list with direct links to build muscle memory.*

---

## 1. What This Pattern Actually Is

Strip away the problem-specific language, and this pattern always reduces to one sentence:

> **"I have `k` sequences that are each already sorted on their own, and I need to combine/compare/traverse across all of them as if they were one single sorted sequence — without ever fully materializing that combined sequence in memory."**

That's the entire pattern. Linked lists, arrays, rows of a matrix, "streams" — the costume changes, but the shape underneath is always: **multiple sorted sources, one combined traversal.**

The reason this deserves a heap: if you dumped everything from all `k` sources into one array and sorted it, that's `O(n log n)` where `n` is the total number of elements across all sources. But since each source is *already* sorted, you're throwing away information by re-sorting from scratch. A heap lets you exploit that existing order and get the job done in `O(n log k)` — and `k` (number of sources) is almost always far smaller than `n` (total elements).

---

## 2. How to Tell This Apart From Pattern 1 (Top-K)

These two patterns are the ones beginners confuse most, because both involve a heap that never grows past roughly size `k`. Here's the actual distinguishing question:

**In Pattern 1 (Top-K):** the heap holds **candidates for your final answer** — every element in the heap is a real contender, and elements get permanently evicted when something better arrives.

**In Pattern 2 (K-Way Merge):** the heap holds **exactly one "current pointer" per source** — never more than one element from any single source at a time. Nothing is "evicted for being worse"; instead, the moment you pop an element, you immediately push the *next* element from that same source to keep the heap topped up. The heap size stays roughly constant at `k` (the number of sources), not because you're filtering for quality, but because you're always representing "the current frontier" of every source.

**The tell-tale sign in the problem statement:** if you see "given `k` sorted arrays/lists," "combine/merge," or "the smallest range that touches every list," you're in Pattern 2. If you see "give me the top/bottom `k` elements," you're in Pattern 1 — even if the number of "things" involved happens to also be called `k` in both cases (this coincidence of naming is exactly why people mix them up).

---

## 3. The Core Idea, Explained Slowly

Say you have `k` sorted arrays and want to merge them into one fully sorted output.

1. Push the **first element of every array** into a min-heap. Each heap entry needs to remember **which source it came from** and **its position within that source** — so store `{value, sourceIndex, elementIndex}`, not just the raw value.
2. Pop the smallest element from the heap. This is guaranteed to be the smallest element across *all* sources right now, because every source's current frontier is represented in the heap, and a min-heap always gives you the global minimum of whatever's inside it.
3. Emit that popped element to your output.
4. Immediately look at the source that popped element came from. If that source has a next element, push it into the heap. This keeps that source's "frontier" represented.
5. Repeat until the heap is empty.

The heap never holds more than `k` elements at once — no matter how large the total data is — because it's a fixed "frontier," one representative per still-active source. That's the entire mechanism, and it generalizes to arrays, linked lists, matrix rows, or literally any pre-sorted collection of sequences.

## 4. The Template

```java
import java.util.*;

public int[] mergeKSortedArrays(int[][] arrays) {
    // heap entries: {value, sourceIndex, elementIndex}
    PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> a[0] - b[0]);

    int totalLength = 0;
    for (int i = 0; i < arrays.length; i++) {
        if (arrays[i].length > 0) {
            pq.offer(new int[]{arrays[i][0], i, 0});
        }
        totalLength += arrays[i].length;
    }

    int[] result = new int[totalLength];
    int idx = 0;

    while (!pq.isEmpty()) {
        int[] top = pq.poll();
        int value = top[0], sourceIdx = top[1], elemIdx = top[2];

        result[idx++] = value;

        // push the NEXT element from the same source, if it exists
        if (elemIdx + 1 < arrays[sourceIdx].length) {
            pq.offer(new int[]{arrays[sourceIdx][elemIdx + 1], sourceIdx, elemIdx + 1});
        }
    }

    return result;
}
```

Notice the fingerprint of this pattern: **every `poll()` is immediately followed by a conditional `offer()` of the *next* element from the *same* source.** If you see this "pop one, push its successor" shape, you're looking at Pattern 2 — contrast this with Pattern 1's "push unconditionally, evict if over budget" shape from the previous post.

## 5. Worked Example: Merge k Sorted Lists

`https://leetcode.com/problems/merge-k-sorted-lists/`

**Problem:** You're given an array of `k` linked lists, each already sorted in ascending order. Merge them all into one sorted linked list.

**Recognizing the pattern:** "`k` sorted lists," "merge... into one sorted list" — this is Pattern 2's signature phrasing almost word-for-word. There's no "give me the top/bottom X elements" language anywhere, which rules out Pattern 1.

**Reasoning to the approach:** each linked list is already sorted, so its **head node** is always its current smallest unconsumed element — that's your natural "frontier" pointer for a linked list, no extra index tracking needed (unlike arrays, where you had to track `elementIndex` manually). Push all `k` heads into a min-heap. Repeatedly pop the smallest head, attach it to your output list, and push in *that node's* `.next` if it exists.

```java
import java.util.*;

class Solution {
    public ListNode mergeKLists(ListNode[] lists) {
        // min-heap ordered by node value
        PriorityQueue<ListNode> pq = new PriorityQueue<>((a, b) -> a.val - b.val);

        for (ListNode head : lists) {
            if (head != null) {
                pq.offer(head);
            }
        }

        ListNode dummy = new ListNode(-1);
        ListNode tail = dummy;

        while (!pq.isEmpty()) {
            ListNode smallest = pq.poll();
            tail.next = smallest;
            tail = tail.next;

            // push the next node from the SAME list, if it exists
            if (smallest.next != null) {
                pq.offer(smallest.next);
            }
        }

        return dummy.next;
    }
}
```

**Complexity:** with `n` total nodes across all lists and `k` lists, this runs in `O(n log k)` — each of the `n` nodes gets pushed and popped exactly once, and each heap operation costs `O(log k)` since the heap never holds more than `k` nodes at a time.

## 6. Common Mistakes Specific to This Pattern

- **Forgetting to track source identity.** If your heap entry is just a raw value with no way to know which source (and which position in that source) it came from, you have no way to push the "next" element — this is the single most common bug in this pattern.
- **Pushing the entire source into the heap upfront.** A very common instinct is to dump *all* elements from all sources into the heap at once. This works, but throws away the entire point of the pattern — you're back to `O(n log n)` heap operations instead of `O(n log k)`. Only ever keep one representative per active source in the heap at a time.
- **Not handling empty/exhausted sources.** If a source is empty from the start, or becomes exhausted partway through, you must skip pushing from it — forgetting this null/bounds check is a very common runtime error, especially with linked lists (`null` heads) or arrays (empty sub-arrays).
- **Confusing this with Pattern 1 because both cap the heap around size `k`.** Re-read Section 2 if this happens — the giveaway is always whether the heap is "candidates competing to survive" (Pattern 1) or "one frontier pointer per source" (Pattern 2).

## 7. Related Questions — Practice These in Order

Work through these without looking at solutions first. Each should take under a minute to identify as Pattern 2 using Section 2's distinguishing question.

1. **Merge k Sorted Lists** — the canonical version, walked through above.
   `https://leetcode.com/problems/merge-k-sorted-lists/`
2. **Kth Smallest Element in a Sorted Matrix** — each row (or column) of the matrix is a sorted source; solve it as a k-way merge this time, even though it can also be solved with a Pattern 1 approach — useful for feeling the difference between the two mindsets on the exact same problem.
   `https://leetcode.com/problems/kth-smallest-element-in-a-sorted-matrix/`
3. **Smallest Range Covering Elements from K Lists** — a genuinely harder variant: you must track the *current max* across all heap tops alongside the min, so you know your current range's width at every step — good stretch practice on maintaining extra state alongside the heap.
   `https://leetcode.com/problems/smallest-range-covering-elements-from-k-lists/`
4. **Find K Pairs with Smallest Sums** — the "sources" here aren't given upfront; you generate candidate pairs from two arrays on the fly, effectively creating `k` virtual sorted sequences as you go — good practice recognizing the pattern when the sources aren't handed to you explicitly.
   `https://leetcode.com/problems/find-k-pairs-with-smallest-sums/`
5. **Employee Free Time** — each employee's schedule is a sorted list of intervals; treat each employee as a "source" in the merge and sweep across the combined frontier to find gaps — a great real-world flavored variant that hides the pattern behind interval logic instead of raw numbers.
   `https://leetcode.com/problems/employee-free-time/`
6. **Ugly Number II** — reframes k-way merge in a sneaky way: instead of `k` given sorted lists, you're merging `k` *implicitly generated* sequences (multiples of 2, 3, and 5) — a great test of whether you can spot the pattern when the "sources" are formulas, not data structures.
   `https://leetcode.com/problems/ugly-number-ii/`
7. **Super Ugly Number** — the general version of the above, with an arbitrary list of prime factors instead of just 2, 3, 5 — forces you to generalize your k-way merge to an arbitrary, input-driven number of implicit sources.
   `https://leetcode.com/problems/super-ugly-number/`
