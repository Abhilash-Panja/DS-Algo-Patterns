# Heap Pattern 7: Scheduling / Interval Problems (Time-Driven Heap Simulation)

*The pattern where "time passing" replaces "array index" as the thing you scan through — and where a single heap often isn't enough, because you need to track both what's busy and what's free. What it is, how to recognize it, how to derive it on an unseen problem, and a curated question list with direct links.*

---

## 1. What This Pattern Actually Is

Strip away the problem-specific language, and this pattern always reduces to one sentence:

> **"Events (meetings, tasks, jobs) have start and end times, and I need to know, at any given moment, what resources are currently busy versus currently free — and assign or count things accordingly."**

The core mechanical shift from every earlier pattern: **the thing driving your scan is time itself**, not array position. You process events in chronological order, and at each point, your first job is always to **free up anything whose end time has already passed** before you can decide what to do with the current event. That "free up expired things first" step, done at the top of every iteration, is the signature move of this entire pattern.

---

## 2. How to Recognize It in an Unseen Problem

**Q1: Does the problem involve meetings, tasks, jobs, CPUs, or servers — each with a start time and either an end time or a duration?**
This is the most direct surface-level signal. Anything phrased around scheduling, booking, or resource allocation over time belongs here.

**Q2: Do I need to know, at various points, how many resources are "currently occupied" versus "currently free"** — whether that's counting rooms needed, assigning the next available server, or figuring out if a task can start yet?
This is what actually requires a heap instead of a simple counter — because "currently occupied" isn't just a running count, it's a *set* of things with different end times, and you need fast access to *which one frees up soonest*.

**Q3: If I sort events by start time and sweep through them in order, would I always need to "release" anything that's finished before I can correctly process the next event?**
This is the operational core of the pattern. If yes, you're not just sorting and scanning — you're maintaining live state (a heap of "currently busy" end times) that needs updating at every step of the sweep, which is exactly what distinguishes this from a simple sort-and-scan.

If Q1 and Q2 fire, and Q3 confirms the "sweep + release expired things" structure, you're in this pattern.

---

## 3. The Core Idea, Explained Slowly

1. **Sort all events by start time.** This gives you the chronological order to sweep through — you always want to process "what happens next" before "what happens after that."
2. **Maintain a min-heap of currently-occupied resources, keyed by end time.** The top of this heap is always "whichever busy resource frees up soonest" — exactly what you need to know at any point in the sweep.
3. **For each event, in start-time order: first pop and release every resource from the busy-heap whose end time is now `≤` the current event's start time.** This step is easy to forget, but it's what keeps your "currently busy" heap accurate as time moves forward — without it, you'd be checking availability against stale, already-finished occupancy.
4. **Now decide what to do with the current event**, using whatever's now available: assign it to a freed-up (or brand new) resource, count how many resources are needed if none are free, etc. — the exact decision depends on the specific problem.
5. **Push the current event into the busy-heap** (keyed by its own end time), since it's now occupying a resource going forward.
6. **Repeat from step 3 for the next event** in your sorted order.

Some problems in this pattern need a **second heap or structure for "currently free" resources** (e.g., when rooms/servers are numbered and you need the specific lowest-numbered or otherwise "best" free one) — in that case, step 3's releases move resources from the busy-heap *into* a free-heap, and step 4 pulls from that free-heap instead of just checking a count.

## 4. The Template

```java
import java.util.*;

public int countResourcesNeeded(int[][] events) {
    // sort by start time
    Arrays.sort(events, (a, b) -> a[0] - b[0]);

    // min-heap of end times for currently-occupied resources
    PriorityQueue<Integer> busy = new PriorityQueue<>();
    int maxConcurrent = 0;

    for (int[] event : events) {
        int start = event[0], end = event[1];

        // Step 3: release everything that's finished by the time this event starts
        while (!busy.isEmpty() && busy.peek() <= start) {
            busy.poll();
        }

        // Step 4/5: this event now occupies a resource
        busy.offer(end);

        // Step 4 (problem-specific): track whatever the problem actually asks for
        maxConcurrent = Math.max(maxConcurrent, busy.size());
    }

    return maxConcurrent;
}
```

Notice the fingerprint of this pattern: **a `while` loop nested inside a `for` loop, where the `while` always runs first and always compares the heap's top against the *current* event's start time.** That "drain expired entries before handling the new one" shape, repeated on every iteration, is what to look for when scanning someone else's code to identify this pattern.

## 5. Worked Example: Meeting Rooms III

`https://leetcode.com/problems/meeting-rooms-iii/`

**Problem:** You have `n` rooms, numbered `0` to `n-1`. Given a list of meetings with `[start, end)` times (all start times unique), each meeting is assigned to the **unused room with the lowest number**; if no room is free, the meeting is **delayed** until a room frees up, keeping its original duration. Return the number of the room that held the most meetings (lowest room number wins ties).

**Recognizing the pattern:** rooms and meetings with start/end times (Q1 fires), you need to know which rooms are busy vs. free at each point (Q2 fires), and processing meetings in order clearly requires releasing rooms that have finished before assigning the next meeting (Q3 fires). Clean match — and the "lowest-numbered free room" detail plus the "delay if none free" rule both signal you'll need **two heaps**, not one.

**Reasoning to the approach:** maintain a min-heap of **free room numbers** (so you always get the lowest-numbered free room) and a min-heap of **occupied rooms keyed by end time** (so you always know which busy room frees up soonest). Sort meetings by start time. For each meeting: first release any occupied rooms whose end time has passed into the free-room heap. Then, if a free room exists, assign the meeting there at its actual start/end time. If not, take the busy room that frees up soonest, and delay this meeting to start exactly when that room frees — preserving its original duration.

```java
import java.util.*;

class Solution {
    public int mostBooked(int n, int[][] meetings) {
        Arrays.sort(meetings, (a, b) -> a[0] - b[0]);

        PriorityQueue<Integer> freeRooms = new PriorityQueue<>(); // lowest room number first
        // occupied rooms: {endTime, roomNumber}, ordered by soonest-to-free
        PriorityQueue<long[]> occupied = new PriorityQueue<>((a, b) ->
            a[0] != b[0] ? Long.compare(a[0], b[0]) : Long.compare(a[1], b[1]));

        for (int i = 0; i < n; i++) freeRooms.offer(i);

        int[] meetingCount = new int[n];

        for (int[] meeting : meetings) {
            long start = meeting[0], end = meeting[1];

            // Step 3: release every room that's finished by this meeting's start
            while (!occupied.isEmpty() && occupied.peek()[0] <= start) {
                freeRooms.offer((int) occupied.poll()[1]);
            }

            if (!freeRooms.isEmpty()) {
                // Step 4: assign the lowest-numbered free room, at the meeting's real time
                int room = freeRooms.poll();
                occupied.offer(new long[]{end, room});
                meetingCount[room]++;
            } else {
                // no free room: delay until the soonest-freeing room, same duration
                long[] soonest = occupied.poll();
                long delayedEnd = soonest[0] + (end - start);
                int room = (int) soonest[1];
                occupied.offer(new long[]{delayedEnd, room});
                meetingCount[room]++;
            }
        }

        int best = 0;
        for (int i = 1; i < n; i++) {
            if (meetingCount[i] > meetingCount[best]) best = i;
        }
        return best;
    }
}
```

This is the clearest example in the whole series of why some problems in this pattern need **two heaps working together** — one heap alone can tell you "what's busy," but answering "which specific free resource should I use" or "which busy resource frees up soonest to delay into" requires the second heap.

## 6. Common Mistakes Specific to This Pattern

- **Forgetting to release expired resources before processing the current event.** This is the single most common bug in this pattern — if you check "is anything free" before draining the busy-heap of finished resources, you'll wrongly conclude nothing is available.
- **Using `<` instead of `<=` (or vice versa) when comparing an end time to the current start time.** Whether a resource freeing up *exactly* when the next event starts counts as "available" depends on the problem's exact wording (closed vs. half-open intervals) — always check this boundary condition explicitly rather than assuming.
- **Only tracking a count of busy resources when the problem actually needs to know *which specific* resource is busy or free.** If room/server identity matters (as in Meeting Rooms III), a single heap of end times isn't enough — you need the second heap or structure to track identities, not just counts.
- **Not re-inserting a "delayed" event with its adjusted end time.** When a resource isn't available and an event has to wait, remember its duration is preserved, but its actual start/end shifts — forgetting to recompute and push the *adjusted* end time (not the original) breaks all future comparisons.

Work through these without looking at solutions first. Each should take under a minute to identify as this pattern using Section 2's checklist.

2. **Single-Threaded CPU** — sort by enqueue time, but the heap is keyed by processing time (and index, for tie-breaking), with a simulated clock instead of a running sum — a good test of adapting the "sweep + release" structure when there's exactly one resource (the CPU) instead of many.
   `https://leetcode.com/problems/single-threaded-cpu/`

   `https://leetcode.com/problems/meeting-rooms-iii/`

   `https://leetcode.com/problems/process-tasks-using-servers/`
