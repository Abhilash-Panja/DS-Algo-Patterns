# Heap Pattern 6: Repeated Extremes / Simulate-and-Rebuild

*The pattern where the heap itself IS the simulation — you pull out the current extreme, transform it, and put it back, over and over, until some stopping condition. What it is, how to recognize it, how to derive it on an unseen problem, and a curated question list with direct links.*

---

## 1. What This Pattern Actually Is

Strip away the problem-specific language, and this pattern always reduces to one sentence:

> **"Repeatedly take the current largest (or smallest) element(s), do something to them, and put the result back in — keep going until some stopping condition is met."**

This is the most literal, direct use of a heap you'll encounter. There's no sorting step beforehand (Pattern 4), no multiple sources to merge (Pattern 2), no balancing two structures (Pattern 3). It's just: **a single heap, repeatedly popped and pushed, simulating a process step by step.**

The giveaway phrase in problem statements is almost always some version of: *"on each turn/step, pick the largest/smallest element(s), combine/reduce/modify them, and continue."* If you can literally circle the words "each turn" or "repeat" in the problem, you're very likely here.

---

## 2. How to Recognize It in an Unseen Problem

**Q1: Does the problem describe a repeated, turn-based process** ("on each turn," "repeat until," "keep doing X until Y") **rather than a one-time selection?**
Patterns 1–5 all eventually settle into one final answer computed after a single pass. This pattern is different — it's explicitly iterative and stateful, where each "turn" changes the data itself, not just your bookkeeping around it.

**Q2: Does each turn require knowing the current largest (or smallest) element(s), and does acting on them change what the new largest/smallest is?**
This is the core mechanic. If the "largest element" after your operation is different from the "largest element" before it, you need a structure that re-exposes the new extreme cheaply after every single change — that's exactly what a heap gives you.

**Q3: Is the heap's size and contents actively changing as part of the simulation itself** (not just growing via straightforward insertion, and not capped at a fixed `k`)?
In this pattern, the heap isn't a fixed-size "top-k" tracker (Pattern 1) or a one-slot-per-source frontier (Pattern 2) — its size and values evolve unpredictably as a direct consequence of the operations you're performing. Sometimes it shrinks by one (two things combine into nothing), sometimes it stays the same size but with a changed value (one thing gets reduced), depending on the problem's rules.

If all three fire, you're in this pattern — and the heap essentially *is* your simulation's state.

---

## 3. The Core Idea, Explained Slowly

1. **Load every element into a heap once**, up front. Use a max-heap if you repeatedly need the largest, min-heap if you repeatedly need the smallest.
2. **Loop until your stopping condition** (heap has ≤1 element left, a fixed number of iterations completed, or some other problem-specific condition).
3. **Each iteration: pop the current extreme (or extremes)** — often just one, sometimes two, depending on what the problem's "turn" requires.
4. **Apply the problem's transformation rule** to whatever you popped — combine two values, reduce one value, etc.
5. **If the transformation produces a result that should re-enter the pool** (the difference between two stones, a halved pile), **push it back into the heap.** If the transformation consumes the value entirely (it's destroyed, used up), don't push anything back for it.
6. **Repeat from step 2** until the stopping condition is met, then read off whatever final answer the problem asks for (often just "what's left in the heap," or a running total you tracked alongside it).

The reason this pattern is comparatively gentle once you've done Patterns 1 and 5: **you already know how to push and pop; the only new skill is trusting the loop to just keep running the same two or three lines until the stopping condition naturally arrives.** There's rarely any clever comparator or extra bookkeeping — the difficulty (when there is any) lives entirely in correctly implementing the problem's specific transformation rule, not in the heap mechanics themselves.

## 4. The Template

```java
import java.util.*;

public int simulateRepeatedExtremes(int[] values) {
    PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());
    for (int v : values) {
        maxHeap.offer(v);
    }

    // Step 2: loop until stopping condition
    while (maxHeap.size() > 1) {
        // Step 3: pop the current extreme(s)
        int first = maxHeap.poll();
        int second = maxHeap.poll();

        // Step 4: apply the problem's transformation rule
        int result = first - second; // example rule: "smash" the two largest together

        // Step 5: push back only if the transformation leaves something behind
        if (result != 0) {
            maxHeap.offer(result);
        }
    }

    // Step 6: read off the final answer
    return maxHeap.isEmpty() ? 0 : maxHeap.poll();
}
```

Notice the fingerprint of this pattern: **the loop condition itself is the stopping rule** (`while heap.size() > 1`, or similar), and **every iteration's body is a self-contained "turn"** that pops, transforms, and conditionally pushes back. If you can point at a `while` loop in a solution and say "each pass through this loop is literally one 'turn' as described in the problem," you're looking at this pattern.

## 5. Worked Example: Last Stone Weight

`https://leetcode.com/problems/last-stone-weight/`

**Problem:** You have a collection of stones with given weights. On each turn, choose the two heaviest stones, smash them together: if they're equal, both are destroyed; if unequal, the lighter is destroyed and the heavier becomes `(heavier - lighter)`. Repeat until at most one stone remains. Return the weight of the last remaining stone, or `0` if none remain.

**Recognizing the pattern:** "on each turn" (Q1 fires immediately), each turn needs the two current heaviest stones and the result of smashing them changes what's heaviest afterward (Q2 fires), and the collection's size shrinks unpredictably each turn — sometimes by two, sometimes staying effectively the same count with a modified value (Q3 fires). Clean match.

**Reasoning to the approach:** load every stone into a max-heap. Each turn, pop the two largest, compute the difference, and push the difference back in if it's nonzero. Stop when at most one stone remains.

```java
import java.util.*;

class Solution {
    public int lastStoneWeight(int[] stones) {
        PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());
        for (int stone : stones) {
            maxHeap.offer(stone);
        }

        while (maxHeap.size() > 1) {
            int heaviest = maxHeap.poll();
            int secondHeaviest = maxHeap.poll();

            if (heaviest != secondHeaviest) {
                maxHeap.offer(heaviest - secondHeaviest);
            }
            // if equal, both are destroyed - push nothing back
        }

        return maxHeap.isEmpty() ? 0 : maxHeap.poll();
    }
}
```

**Complexity:** each turn removes at least one stone permanently (either both are destroyed, or two become one), so there are at most `n` turns, each costing `O(log n)` for the heap operations — `O(n log n)` total, a clear improvement over a naive approach that re-sorts the whole array on every turn (`O(n² log n)`).

## 6. Common Mistakes Specific to This Pattern

- **Re-sorting the array from scratch on every turn**, instead of maintaining a heap. This is the naive `O(n)`-per-turn (or worse) approach that a heap is specifically meant to replace — if you find yourself calling `Arrays.sort()` inside your simulation loop, you've missed the point of the pattern.
- **Forgetting to conditionally push back.** Not every transformation leaves something behind — read the problem's rule carefully for the case where the result should be discarded entirely (e.g., equal stones destroying each other) versus re-inserted.
- **Popping the wrong number of elements per turn.** Some problems in this pattern pop just one element per turn (halve it, push back), others pop two (combine them). Misreading which one the problem actually wants is an easy, high-frequency mistake — re-read the "turn" description carefully before coding.
- **Losing track of a running total that needs to persist across turns**, separate from the heap's contents. Some variants in this pattern ask for a cumulative result (like a running sum of everything removed) rather than just "what's left in the heap" — don't assume the heap's final state alone is always the answer.

## 7. Related Questions — Practice These in Order

Work through these without looking at solutions first. Each should take under a minute to identify as this pattern using Section 2's checklist.

1. **Last Stone Weight** — the cleanest, most direct version; walked through above, solve it again from scratch without peeking.
   `https://leetcode.com/problems/last-stone-weight/`
2. **Remove Stones to Minimize the Total** — pop the current largest pile, halve it (rounding down), push it back, repeat exactly `k` times — a good variant where the turn count is fixed rather than driven by a heap-emptying condition.
   `https://leetcode.com/problems/remove-stones-to-minimize-the-total/`
3. **Minimize Deviation in Array** — every element can be doubled (if even... wait, if odd, double it; if even, it can be halved) — you repeatedly shrink the current max while tracking a running `max - min` as your objective, a good stretch on tracking an *external* running statistic alongside the heap's own state, not just reading off the heap's final contents.
   `https://leetcode.com/problems/minimize-deviation-in-array/`
4. **Reorganize String** — a frequency-based variant: repeatedly place the currently most frequent remaining character (skipping the one just placed, to avoid adjacent duplicates), decrement its count, and push it back if any remain — connects this pattern to greedy string-construction problems.
   `https://leetcode.com/problems/reorganize-string/`
5. **Task Scheduler** — very similar mechanic to Reorganize String, but framed around scheduling CPU tasks with a required cooldown between repeats of the same task — good for recognizing the same "repeatedly place the most frequent remaining item" idea in a different domain.
   `https://leetcode.com/problems/task-scheduler/`
