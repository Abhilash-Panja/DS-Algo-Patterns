# Heap Pattern 4: Sort + Heap + Running Aggregate (Greedy-with-Heap)

*The hardest pattern in this series to compose correctly on a first attempt — because it's really two patterns stacked on top of each other. What it is, how to recognize it, how to derive the approach on an unseen problem, and a curated question list with direct links.*

---

## 1. What This Pattern Actually Is

Strip away the problem-specific language, and this pattern always reduces to one sentence:

> **"My objective mixes a sum/count (easy to track) with a min/max (hard to track), and I can only choose at most `k` items — so I need to neutralize the hard part before I can even think about optimizing the easy part."**

This is the pattern behind LeetCode 1383 (Maximum Performance of a Team), which we broke down in full in an earlier post — if any single step here feels rushed, that post has the complete step-by-step derivation. This post treats it as its own standalone pattern, worth recognizing on sight.

**Why this is harder than Patterns 1–3:** those patterns are each *one* idea (bounded heap, merge frontier, balanced split). This pattern is **two ideas glued together in sequence**: first a sort that pins down the hard part of the objective, *then* a Pattern-1-style bounded heap on what's left. If you don't do the sort step first — or sort in the wrong direction — the heap step alone will silently compute the wrong answer, because it'll be optimizing over a set where the "min" or "max" guarantee no longer holds.

---

## 2. How to Recognize It in an Unseen Problem

Ask these questions the moment you finish reading a problem:

**Q1: Does the objective explicitly multiply or combine a sum/count with a min or max?**
Phrases like "sum of X times the minimum of Y," or "total cost such that the maximum of Z is minimized," are the clearest signal. If the objective is built from *only* sums (no min/max in sight), you're not in this pattern — you're probably in plain Pattern 1.

**Q2: Am I restricted to choosing "at most `k`" or "exactly `k`" items from a larger set?**
This constraint is what makes the "easy" sum-side of the objective a genuine top-k problem once the hard side is dealt with — without a `k` constraint, you might just be looking at a simpler greedy problem with no heap needed at all.

**Q3: Is there a natural attribute I could sort by, such that "everything processed so far, in this sort order" would automatically satisfy some guarantee about the min/max side of the objective?**
This is the question that actually unlocks the solution. If you can answer *yes* — name the attribute and the direction (ascending or descending) — you've found your sort step, and the rest of the problem reduces to something you already know (Pattern 1).

If Q1 and Q2 both fire, you're in this pattern's territory. Q3 is the derivation step that tells you *how* to actually solve it — and if you can't answer Q3 confidently, that's a sign to slow down and reason it through explicitly rather than guessing at code.

---

## 3. The Core Idea, Explained Slowly

1. **Identify the two pieces of the objective.** One piece is a sum or count (call it the "easy" side — it updates cheaply as elements are added or removed). The other is a min or max (the "hard" side — recomputing it after a removal normally requires rescanning).
2. **Sort all elements by the hard-side attribute**, in whichever direction guarantees that everyone processed so far, in this order, has a hard-side value on the correct side of the current element's value. (Descending, if you want the current element to represent a *minimum* over everyone seen so far; ascending, if you want it to represent a *maximum*.)
3. **Scan through the sorted list.** At each step, the *current element's* hard-side value is now guaranteed to be the min/max of any subset chosen from elements seen so far — this is what "pins" the hard part. You never need to recompute it; it's just whatever the current element's value is.
4. **With the hard side pinned, the remaining problem is pure Pattern 1**: maintain a bounded heap (size `k`) on the easy-side attribute, keeping a running sum, evicting the worst element whenever you're over budget.
5. **Evaluate the objective at every step of the scan**, not just at the end — combine the current running sum (easy side) with the current element's value (hard side, now safely pinned) and track the best result seen across the whole scan. You genuinely don't know in advance which point in the scan gives the optimum, since later elements have a "weaker" pinned value but might unlock a much larger sum.

## 4. The Template

```java
import java.util.*;

public long solve(int[][] items, int k) {
    // items[i] = { hardAttribute, easyAttribute }

    // Step 2: sort by the hard attribute (here: descending, to pin a MINIMUM)
    Arrays.sort(items, (a, b) -> b[0] - a[0]);

    PriorityQueue<Integer> minHeap = new PriorityQueue<>(); // Pattern 1, nested inside
    long runningSum = 0;
    long best = 0;

    for (int[] item : items) {
        int hardAttr = item[0];
        int easyAttr = item[1];

        // Pattern 1 logic: admit unconditionally, evict if over budget
        minHeap.offer(easyAttr);
        runningSum += easyAttr;
        if (minHeap.size() > k) {
            runningSum -= minHeap.poll();
        }

        // Step 5: evaluate at every step, since the hard attribute is now pinned
        best = Math.max(best, runningSum * hardAttr);
    }

    return best;
}
```

Notice the fingerprint of this pattern: **a sort call sits immediately before a loop that looks exactly like Pattern 1's template.** If you ever see a `sort` followed by an `offer`/conditional-`poll` loop with a `Math.max` update inside it, you're looking at this pattern — the sort is the tell that separates it from plain Pattern 1.

## 5. Worked Example: Maximum Subsequence Score

`https://leetcode.com/problems/maximum-subsequence-score/`

**Problem:** You're given two integer arrays `nums1` and `nums2`, both of length `n`, and an integer `k`. Choose a subsequence of indices of size exactly `k`. The score of the chosen indices is `(sum of the chosen nums1 values) × (minimum of the chosen nums2 values)`. Return the maximum possible score.

**Recognizing the pattern:** the objective is explicitly `sum × min` (Q1 fires), and there's a hard `size exactly k` constraint (Q2 fires). For Q3: can we sort by `nums2` (the min-side attribute) descending, so that everyone processed so far in that order has a `nums2` value `≥` the current one? Yes — so the current element's `nums2` value is always a safe candidate for "minimum of the chosen set," exactly like in 1383.

**Reasoning to the approach:** pair up each index's `(nums2[i], nums1[i])` value, sort descending by `nums2`, then run the Pattern 1 bounded-heap logic on `nums1`, evaluating `runningSum × current nums2` at every step. This is structurally identical to 1383, just with `nums1`/`nums2` in place of `speed`/`efficiency`, and "exactly `k`" instead of "at most `k`" (which, conveniently, the same template already handles correctly, since the heap only ever evaluates the objective once it's actually holding `k` elements in a meaningful way — though for "exactly k" you should only start comparing to `best` once the heap has reached size `k`).

```java
import java.util.*;

class Solution {
    public long maxScore(int[] nums1, int[] nums2, int k) {
        int n = nums1.length;
        int[][] pairs = new int[n][2];
        for (int i = 0; i < n; i++) {
            pairs[i][0] = nums2[i]; // hard attribute (this is our "min")
            pairs[i][1] = nums1[i]; // easy attribute (this is our "sum")
        }

        Arrays.sort(pairs, (a, b) -> b[0] - a[0]); // descending by nums2

        PriorityQueue<Integer> minHeap = new PriorityQueue<>();
        long runningSum = 0;
        long best = 0;

        for (int[] pair : pairs) {
            int minCandidate = pair[0];
            int sumContribution = pair[1];

            minHeap.offer(sumContribution);
            runningSum += sumContribution;

            if (minHeap.size() > k) {
                runningSum -= minHeap.poll();
            }

            // only evaluate once we actually have exactly k elements
            if (minHeap.size() == k) {
                best = Math.max(best, runningSum * minCandidate);
            }
        }

        return best;
    }
}
```

**The one deliberate difference from the 1383 template**, worth noticing: because this problem requires *exactly* `k` elements (not *at most* `k`), the `best = Math.max(...)` update only happens once `minHeap.size() == k`, rather than on every iteration. This is a good example of why Section 2's "reason it through, don't guess" advice matters — the *shape* of the template is identical, but a small constraint difference changes exactly one line.

## 6. Common Mistakes Specific to This Pattern

- **Sorting in the wrong direction.** If you want the current element to represent a guaranteed *minimum* over everyone processed so far, you must sort **descending** by that attribute. Sorting ascending by mistake silently breaks the entire pinning guarantee — the code still runs, but computes garbage.
- **Forgetting to evaluate at every step (or evaluating at the wrong step for "exactly k" problems).** As shown above, "at most k" problems evaluate at every iteration, while "exactly k" problems must wait until the heap actually reaches size `k`. Mixing these up is an easy off-by-one-flavored bug.
- **Trying to track the min/max incrementally instead of pinning it via sort.** This is the mistake that happens when someone recognizes "there's a sum and a min" but skips straight to coding without asking Section 2's Q3. You end up trying to maintain a live minimum inside a heap that's also being used for the sum — which is possible in principle but far more complex than it needs to be. Always look for the sort-based pinning trick first.
- **Using `int` instead of `long` for the running sum or the final product.** Since this pattern multiplies a sum by another value, results overflow `int` range very easily on larger inputs — a silent, hard-to-debug source of wrong answers.

## 7. Related Questions — Practice These in Order

Work through these without looking at solutions first. Each should take under a minute to identify as Pattern 4 using Section 2's checklist, and each will make you explicitly answer "what's my sort attribute and direction" before writing any heap code.

1. **Maximum Subsequence Score** — the cleanest, most direct version of this pattern; walked through above.
   `https://leetcode.com/problems/maximum-subsequence-score/`
2. **Maximum Performance of a Team** — the canonical, slightly harder version (full derivation in the dedicated 1383 breakdown post); solve it again from scratch here without peeking at that post.
   `https://leetcode.com/problems/maximum-performance-of-a-team/`
3. **Minimum Cost to Hire K Workers** — same skeleton, but *minimizing* instead of maximizing, which flips the heap from a min-heap to a max-heap — a good test of whether you understand *why* the heap type flips, not just that it does.
   `https://leetcode.com/problems/minimum-cost-to-hire-k-workers/`
4. **Course Schedule III** — no explicit `k` this time; the heap's eviction is triggered by a feasibility check (total time exceeding a deadline) instead of a fixed heap size — a good stretch problem for seeing this pattern without its most obvious signal (an explicit `k`) present.
   `https://leetcode.com/problems/course-schedule-iii/`
5. **IPO** — worth revisiting here too: the running aggregate is your unlocked *capital*, not a sum you ever evict from, and there's no sort-to-pin-a-min/max step in the usual sense — a good problem for testing whether you can tell when this pattern's full machinery is needed versus when a simpler, related idea (a plain max-heap of "currently affordable projects") is all that's actually required.
   `https://leetcode.com/problems/ipo/`
