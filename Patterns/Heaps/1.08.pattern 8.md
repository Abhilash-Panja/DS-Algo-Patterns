# Heap Pattern 8: Heap in Graph Algorithms (Lazy Deletion, "Best Frontier Next")

*The final pattern in this series — where heaps meet graphs, and where you learn the one genuinely new trick that didn't show up in Patterns 1–7: lazy deletion. What it is, how to recognize it, how to derive it on an unseen problem, and a curated question list with direct links.*

---

## 1. What This Pattern Actually Is

Strip away the problem-specific language, and this pattern always reduces to one sentence:

> **"I'm exploring a graph (or grid), and at every step I want to expand outward from whichever unvisited node currently has the cheapest known cost — repeating until I've reached my goal or explored everything reachable."**

This is **Dijkstra's algorithm** (shortest path) and **Prim's algorithm** (minimum spanning tree) in disguise, and the "cheapest known cost" idea is really just Pattern 6 (Repeated Extremes) applied to a graph's frontier instead of a flat array. The one thing that's genuinely new here is **lazy deletion** — and it exists because of a problem the earlier patterns never had to deal with: **the same node can end up in the heap more than once, with different costs, and you don't find out which entries are "stale" until you're about to use them.**

---

## 2. How to Recognize It in an Unseen Problem

**Q1: Is the problem about a graph or grid, asking for a shortest path, minimum cost to connect/reach something, or a minimum spanning tree?**
This is the direct surface signal — nodes, edges, weights, "minimum cost to reach," "shortest path," "connect all points."

**Q2: Does the "cost" I'm minimizing accumulate as I move through the graph** (a sum of edge weights, or a running max/min along the path) **rather than being decided all at once?**
This distinguishes graph traversal problems from the earlier patterns — the cost isn't known upfront per element; it's built up step by step as you explore, and can change as you discover better ways to reach a node you'd already seen.

**Q3: Might I reach the same node more than once, via different paths, with different costs — and would I only want to actually process it using the cheapest cost found?**
This is the question that specifically confirms you're in the lazy-deletion sub-case of this pattern. If yes, you'll be pushing the same node into the heap multiple times as you discover cheaper paths to it, and need a way to safely ignore the stale, more expensive entries when they eventually surface.

If Q1 and Q2 both fire, you're in graph-Dijkstra/Prim's territory. If Q3 also fires, you specifically need the lazy-deletion technique described below.

---

## 3. The Core Idea, Explained Slowly

1. **Maintain a min-heap of `{cost, node}` pairs**, representing "candidate next steps" to explore, ordered by cost so far.
2. **Maintain a `visited` (or `finalized`) set** of nodes whose shortest/cheapest cost is already confirmed and won't change.
3. **Push the starting node(s) into the heap** with their known starting cost (often `0`).
4. **Loop: pop the cheapest entry from the heap.**
5. **Lazy deletion check:** if the popped node is **already in the `visited` set**, this entry is stale — it represents an old, more expensive way of reaching a node you've already finalized more cheaply. **Just skip it and continue the loop** — don't process it, don't error, just move on to the next pop.
6. **If the popped node is not yet visited:** this is now its final, confirmed cheapest cost (this is the core guarantee of Dijkstra's algorithm — the *first* time you pop a node from a min-heap ordered by cost, that cost is guaranteed to be the minimum possible). Mark it visited, record its cost, and if this is your target node, you can stop here.
7. **Expand from this node:** for each neighbor, compute the cost of reaching it *through* the current node. If that's a candidate improvement, **push a new `{newCost, neighbor}` entry into the heap** — even if that neighbor already has entries in the heap from before. **Don't bother trying to find and update an old entry for that neighbor** — that's the "lazy" part of lazy deletion: you let outdated entries linger in the heap and simply filter them out later at step 5, rather than paying the cost of removing them immediately.
8. **Repeat from step 4** until the heap is empty or you've reached your target.

The reason "lazy" deletion is preferred over "eager" deletion (immediately finding and removing/updating the old heap entry for a node): **heaps don't support efficient arbitrary-position removal or update** — finding a specific node buried inside a heap and fixing its priority is `O(n)`, not `O(log n)`. It's cheaper, in practice, to just let duplicate/stale entries pile up and pay a small `O(log n)` cost to discard each one when it happens to surface, than to pay `O(n)` every single time a cheaper path is found.

## 4. The Template

```java
import java.util.*;

public int[] dijkstra(int n, List<int[]>[] graph, int start) {
    // graph[u] = list of {neighbor, weight}
    int[] dist = new int[n];
    Arrays.fill(dist, Integer.MAX_VALUE);
    boolean[] visited = new boolean[n];

    PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> a[0] - b[0]); // {cost, node}
    pq.offer(new int[]{0, start});
    dist[start] = 0;

    while (!pq.isEmpty()) {
        int[] top = pq.poll();
        int cost = top[0], node = top[1];

        // Step 5: lazy deletion - skip stale entries
        if (visited[node]) continue;
        visited[node] = true;

        // Step 7: expand to neighbors
        for (int[] edge : graph[node]) {
            int neighbor = edge[0], weight = edge[1];
            int newCost = cost + weight;
            if (newCost < dist[neighbor]) {
                dist[neighbor] = newCost;
                pq.offer(new int[]{newCost, neighbor}); // push, don't bother updating old entries
            }
        }
    }

    return dist;
}
```

Notice the fingerprint of this pattern: **the very first line inside the `while` loop, right after popping, is a `visited` check that just `continue`s if true.** That one-line guard is the entire lazy-deletion technique — if you see it in a solution, alongside a `{cost, node}` heap and a per-node `visited` array, you're looking at this exact pattern.

## 5. Worked Example: Network Delay Time

`https://leetcode.com/problems/network-delay-time/`

**Problem:** You're given a network of `n` nodes and a list of directed edges `(u, v, weight)` representing signal travel time. A signal is sent from node `k`. Return the minimum time for the signal to reach **all** nodes, or `-1` if it's impossible for some node.

**Recognizing the pattern:** graph, edge weights, minimum time to reach nodes (Q1 fires) — the total delay to reach any node accumulates as a sum of edge weights along the path, not known in advance (Q2 fires) — and you can definitely reach the same node via multiple paths with different total costs as you explore (Q3 fires). Full match — this is Dijkstra's algorithm, textbook.

**Reasoning to the approach:** run Dijkstra's from node `k`, tracking the minimum time to reach every node. Once the heap is fully drained, the answer is the **maximum** value among all the finalized distances (since we need the signal to reach *everyone*, the bottleneck is whichever node took longest) — or `-1` if any node was never reached at all.

```java
import java.util.*;

class Solution {
    public int networkDelayTime(int[][] times, int n, int k) {
        List<int[]>[] graph = new List[n + 1];
        for (int i = 1; i <= n; i++) graph[i] = new ArrayList<>();
        for (int[] edge : times) {
            graph[edge[0]].add(new int[]{edge[1], edge[2]}); // {neighbor, weight}
        }

        int[] dist = new int[n + 1];
        Arrays.fill(dist, Integer.MAX_VALUE);
        boolean[] visited = new boolean[n + 1];

        PriorityQueue<int[]> pq = new PriorityQueue<>((a, b) -> a[0] - b[0]); // {cost, node}
        pq.offer(new int[]{0, k});
        dist[k] = 0;

        while (!pq.isEmpty()) {
            int[] top = pq.poll();
            int cost = top[0], node = top[1];

            if (visited[node]) continue; // lazy deletion
            visited[node] = true;

            for (int[] edge : graph[node]) {
                int neighbor = edge[0], weight = edge[1];
                int newCost = cost + weight;
                if (newCost < dist[neighbor]) {
                    dist[neighbor] = newCost;
                    pq.offer(new int[]{newCost, neighbor});
                }
            }
        }

        int maxDist = 0;
        for (int i = 1; i <= n; i++) {
            if (dist[i] == Integer.MAX_VALUE) return -1; // unreachable node
            maxDist = Math.max(maxDist, dist[i]);
        }
        return maxDist;
    }
}
```

Notice this is the exact template from Section 4 with almost no changes — the only problem-specific work was building the adjacency list and computing the final answer (`max` over all distances) from the `dist` array the algorithm fills in.

## 6. Common Mistakes Specific to This Pattern

- **Marking a node visited when you push it, instead of when you pop it.** This is the single most damaging mistake in this pattern — it breaks Dijkstra's correctness guarantee entirely, because you might mark a node visited via an expensive path before ever discovering a cheaper one. Always mark visited **on pop**, never on push.
- **Trying to eagerly update or remove old heap entries.** As explained in Section 3, this is unnecessary and expensive — trust the lazy-deletion `visited` check to filter out stale entries instead of trying to maintain a "clean" heap.
- **Forgetting the `visited` check entirely**, and reprocessing (re-expanding neighbors from) the same node multiple times. This doesn't always produce a *wrong* answer, but it can massively blow up your time complexity and, in some problem variants, does produce wrong answers — always include the check.
- **Assuming the "cost" is always a sum.** Some problems in this pattern (Path with Minimum Effort, Swim in Rising Water) redefine "cost" as the **maximum** value along the path instead of a running sum — the heap and lazy-deletion mechanics are identical, but the update rule in step 7 changes from `cost + weight` to `Math.max(cost, weight)`. Always double check what "cost" means in the specific problem before assuming it's additive.

## 7. Related Questions — Practice These in Order

Work through these without looking at solutions first. Each should take under a minute to identify as this pattern using Section 2's checklist.

1. **Network Delay Time** — the cleanest, most direct exposure to Dijkstra's algorithm with a heap; walked through above, solve it again from scratch without peeking.
   `https://leetcode.com/problems/network-delay-time/`
2. **Path with Minimum Effort** — Dijkstra's, but the "cost" being minimized is the **maximum** absolute height difference along the path, not a sum — practice swapping the update rule from `cost + weight` to `Math.max(cost, weight)` while keeping everything else identical.
   `https://leetcode.com/problems/path-with-minimum-effort/`
3. **Cheapest Flights Within K Stops** — a Dijkstra's variant with an extra constraint (number of stops used) baked directly into the heap's state — forces you to think carefully about what belongs in each heap entry beyond just `{cost, node}`.
   `https://leetcode.com/problems/cheapest-flights-within-k-stops/`
4. **Min Cost to Connect All Points** — Prim's algorithm for building a minimum spanning tree, using the exact same lazy-deletion heap idea, but growing a *tree* that connects everything cheaply, rather than finding a single shortest path.
   `https://leetcode.com/problems/min-cost-to-connect-all-points/`
5. **Swim in Rising Water** — Dijkstra's-style heap on a grid instead of an explicit graph, with the same "minimize the maximum along the path" twist as Path with Minimum Effort — good for practicing graph modeling (turning grid cells into implicit nodes and edges) on top of the core algorithm.
   `https://leetcode.com/problems/swim-in-rising-water/`

- **Pattern 7 (Scheduling):** time-driven sweeps, often needing two heaps for busy vs. free resources.
