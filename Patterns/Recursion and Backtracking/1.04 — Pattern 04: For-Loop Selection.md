# 1.04 — Pattern 04: For-Loop Selection / Combinations

> **Repository:** Recursion and Backtracking  
> **Previous:** [1.03 Binary Choice — Include–Exclude](1.03%20Binary%20Choice%20-%20Include-Exclude%20%28Revised%29.md)  
> **Next:** 1.05 Permutations / Arrangement  
> **Primary language:** Java  
> **Goal:** Derive candidate-selection backtracking, not memorize `for` loops.


## 1. Practical one-line definition

> **For-loop selection:** Build an unordered selection by repeatedly choosing its next candidate from a well-defined range, advancing that range so the same selection is not generated in multiple orders.

**Capability:** Generate, count, or find combinations under size, sum, reuse, and uniqueness constraints while keeping the search state small.

**The core question is not “does this problem have a for loop?”** It is:

> After selecting a candidate, which candidates are still legally available, and how do I ensure the same combination has exactly one representation?

---

## 2. Why this pattern exists — derive from brute force

**Problem:** From `1..4`, choose exactly two distinct numbers; order does not matter.

Naive generation could consider all ordered pairs:

```text
(1,2) (1,3) (1,4)
(2,1) (2,3) (2,4)
(3,1) (3,2) (3,4)
(4,1) (4,2) (4,3)
```

That creates 12 ordered pairs, but only 6 combinations. `(1,2)` and `(2,1)` are the **same** combination.

```text
Brute force: generate candidate sequences
        ↓
Bottleneck: multiple orders describe one result
        ↓
Observation: every combination has a unique increasing-index order
        ↓
Invariant: indices in path strictly increase (when reuse is forbidden)
        ↓
Pattern: choose the next index i >= start; recurse with i + 1
```

For `[1,2,3,4]`, the search becomes:

```text
[]
├── [1]
│   ├── [1,2] ✓
│   ├── [1,3] ✓
│   └── [1,4] ✓
├── [2]
│   ├── [2,3] ✓
│   └── [2,4] ✓
├── [3]
│   └── [3,4] ✓
└── [4]  (cannot finish a pair)
```

The ordering rule removes duplicates **by construction**. We do not need to generate then deduplicate all pairs.

## 3. Recognition signals — diagnostic questions

1. **Does order matter?** If choosing `{2,5}` is the same outcome as `{5,2}`, canonical candidate ordering is useful.
2. **What does a level mean?** Are we selecting the next member of a partial combination, instead of deciding every element's inclusion individually?
3. **Can I restrict the next candidate range?** If earlier candidates should never reappear, keep a `start` index.
4. **Can a candidate be reused?** If yes, the next recursive call may keep `i`; if no, it should move beyond `i`.
5. **Are duplicate values present?** If distinct positions carry equal values, should they produce one unique value-combination or multiple index-distinct selections?
6. **Can a partial state be shown impossible?** Remaining slots, remaining sum, and sorted input may justify pruning.

**Trigger phrases:** “choose `k`,” “combination,” “pick numbers to reach target,” “unique groups,” “select `r` elements.” These are hints, **not proofs**. A problem involving a target sum may instead require DP, two pointers, or a greedy algorithm depending on constraints and objective.

**Disguised wording:** “Select exactly three volunteers from a roster such that total hours equal a quota” is a combination decision even without the word *combination*.

## 4. The state, contract, invariant and progress

Use this mental specification for ordinary combinations:

| Part | Meaning |
|---|---|
| State | `start` and current `path` |
| Contract | `dfs(start)` enumerates valid completions of the current path using permitted indices `>= start` |
| Level | Number of elements already selected (`path.size()`) |
| Choices | Each candidate index `i` from `start` through the remaining range |
| Check | Is this candidate compatible with constraints? |
| Move | Add candidate → recurse → remove candidate |
| Progress | `start` grows when reuse is forbidden, or remaining target/size decreases when reuse is allowed |
| Invariant | Every completed index combination is generated once in increasing-index order |

**Important precondition:** Sorting by values is optional for combinations of *indices* without duplicates. Sorting is useful (and often essential) when we need unique **value-combinations** in a duplicate-valued input.

### A reusable template

```java
void dfs(int start, int[] nums, List<Integer> path,
         List<List<Integer>> ans) {
    if (/* valid complete result */) {
        ans.add(new ArrayList<>(path));
        return;
    }

    for (int i = start; i < nums.length; i++) {
        if (/* impossible candidate */) continue;

        path.add(nums[i]);         // choose
        dfs(i + 1, nums, path, ans); // no reuse: next > i
        path.remove(path.size() - 1); // undo
    }
}
```

This is a **skeleton**, not a universally correct implementation: exact base cases, checks and next index depend on the problem.

## 5. Deep worked example — Combinations (LeetCode 77)

**Problem:** Given integers `n` and `k`, return every combination of `k` numbers from `1..n`.

**Link:** https://leetcode.com/problems/combinations/  
**Difficulty:** Medium  
**Pattern:** For-loop selection, strictly increasing choices  
**Priority:** **MUST SOLVE**

### Step 1 — Strip the story

- Input: positive `n`, requested size `k`.
- Output: all distinct size-`k` subsets of `{1,...,n}`.
- Objective: **enumerate**, not count only.
- Order inside a chosen group does **not** matter.

### Step 2 — Brute force

We could enumerate all `2^n` subsets and keep only those with size `k`. We would test many invalid sizes.

Alternatively, generate ordered `k`-length sequences using different indices, and deduplicate permutations of the same group. That also wastes work.

**Bottleneck:** exploring or retaining representations that do not belong to the final answer.

### Step 3 — Structural observation

Every combination has exactly one increasing representation:

```text
{4,1,3} → [1,3,4]
```

Once we choose `1`, the next choice must be strictly larger; after choosing `3`, the next must be larger than `3`.

### Step 4 — Identify the pattern

Instead of a take/skip decision at every number, the next move is to *select one candidate* from the remaining range.

`start` is the smallest next number allowed, and `path` is strictly increasing.

### Step 5 — Define invariant before code

> At entry to `dfs(start)`, `path` is strictly increasing, contains valid values from `1..n`, and any next selected value must be at least `start`; every completed combination has one unique path through the tree.

### Step 6 — Dry run: n = 4, k = 2

| Active path | `start` | Candidate chosen | Recursive result |
|---|---:|---:|---|
| `[]` | 1 | 1 | Explore `[1]` |
| `[1]` | 2 | 2 | Record `[1,2]` |
| `[1]` | 2 | 3 | Record `[1,3]` |
| `[1]` | 2 | 4 | Record `[1,4]` |
| `[]` | 1 | 2 | Explore `[2]` |
| `[2]` | 3 | 3 | Record `[2,3]` |
| `[2]` | 3 | 4 | Record `[2,4]` |
| `[]` | 1 | 3 | Explore `[3]` |
| `[3]` | 4 | 4 | Record `[3,4]` |

Notice `[2,1]` is impossible to generate: after choosing `2`, we recurse with `start = 3`.

### Step 7 — Clean Java solution

```java
import java.util.*;

class Solution {
    public List<List<Integer>> combine(int n, int k) {
        List<List<Integer>> ans = new ArrayList<>();
        if (k < 0 || k > n) return ans;

        backtrack(1, n, k, new ArrayList<>(), ans);
        return ans;
    }

    private void backtrack(int start, int n, int k,
                           List<Integer> path,
                           List<List<Integer>> ans) {
        if (path.size() == k) {
            ans.add(new ArrayList<>(path));
            return;
        }

        int need = k - path.size();
        int lastStart = n - need + 1; // enough values must remain

        for (int candidate = start; candidate <= lastStart; candidate++) {
            path.add(candidate);
            backtrack(candidate + 1, n, k, path, ans);
            path.remove(path.size() - 1);
        }
    }
}
```

**Why `lastStart = n - need + 1`?** If we need `need` more values and choose `candidate` now, the inclusive range `[candidate, n]` must have at least `need` values:

```text
n - candidate + 1 >= need
candidate <= n - need + 1
```

This is safe pruning, not a heuristic.

### Step 8 — Complexity, justified

- There are `C(n,k)` completed combinations; output size alone is `Θ(k · C(n,k))` integers for `k > 0`.
- Copying each solution takes `O(k)`; the pruned search also visits prefix states. A safe simple upper bound is `O(n · C(n,k))` for `1 <= k <= n`, and the output-writing cost is `Ω(k · C(n,k))`. For this optimized search, one can bound visited partial paths by `O(k · C(n,k))`, giving output-sensitive `O(k · C(n,k))` time for `1 <= k <= n`.
- Auxiliary recursion/path space (excluding output): `O(k)`.
- Result storage: `Θ(k · C(n,k))` for `k > 0`. For `k = 0`, the one answer is the empty combination.

Do **not** casually say `O(2^n)` is tight for all fixed-`k` combination generators.

### Step 9 — 60–90 second interview explanation

> I need unordered groups of size `k`. Generating all ordered picks would repeat the same combination in different orders. I can eliminate this redundancy by building each answer in strictly increasing order. My state is the next allowed number and the current path. At each call, I loop over eligible next values, append one, recurse with `candidate + 1`, then remove it before trying another. The invariant is that the path is strictly increasing, so every valid combination appears exactly once. I stop once the path has `k` elements, and I can prune any candidate that leaves too few remaining values to fill the group. Stack space is `O(k)` excluding stored answers.

## 6. The three index-transition rules you MUST derive

This is the most transferable part of the pattern.

| Situation | Recursive next start | Why |
|---|---|---|
| **Each input position can be used once** | `dfs(i + 1, ...)` | Selected index cannot be reused |
| **Current candidate can be reused** | `dfs(i, ...)` | Current candidate remains eligible |
| **Input contains duplicates; unique value combinations needed** | Usually `dfs(i + 1, ...)` plus sorting and same-depth skip | Multiple positions with the same value must not create identical results |

**A crucial nuance:** `dfs(i)` alone does not ensure termination. With reuse, another state must make progress — for example, the remaining target decreases when all candidates are positive, or the remaining number of picks decreases.

### A. Use once — Combination Sum II

```java
// After sorting:
for (int i = start; i < nums.length; i++) {
    if (i > start && nums[i] == nums[i - 1]) continue;
    if (nums[i] > remain) break; // requires positive/nonnegative sorted values

    path.add(nums[i]);
    dfs(i + 1, remain - nums[i]); // index used at most once
    path.remove(path.size() - 1);
}
```

The `i > start` check is **same-depth** duplicate skipping. It does not prohibit selecting two equal values when both come from distinct positions and the problem allows both.

### B. Reuse allowed — Combination Sum I

```java
// Requires distinct, positive candidates for this canonical version.
for (int i = start; i < nums.length; i++) {
    if (nums[i] > remain) continue; // break only if sorted

    path.add(nums[i]);
    dfs(i, remain - nums[i]); // i remains eligible
    path.remove(path.size() - 1);
}
```

If a candidate were zero or negative, repeatedly reusing it might not decrease `remain`, potentially creating non-terminating or infinite-output behavior. State the positivity precondition.

### C. Exactly k picks from a range — Combinations / Combination Sum III

```java
if (path.size() == k) {
    if (remain == 0) record();
    return;
}
for (int i = start; i <= 9; i++) {
    path.add(i);
    dfs(i + 1, remain - i);
    path.remove(path.size() - 1);
}
```

Here *both* `path.size()` and `remain` are relevant, so reaching zero remaining sum early is not automatically a completed answer unless exactly `k` values were selected.

## 7. Deep variation — Combination Sum (LeetCode 39)

**Problem:** From distinct positive candidates, select values (repetition allowed) that sum to `target`. Return unique combinations, ignoring order.

**Link:** https://leetcode.com/problems/combination-sum/  
**Difficulty:** Medium  
**Priority:** **MUST SOLVE**

### Derive the state

- `start`: minimum allowed candidate index (canonical nondecreasing index order)
- `remain`: sum still needed
- `path`: values chosen so far
- Invariant: candidate indices never decrease, so permutations of the same multiset are not duplicated
- Progress: each chosen positive candidate makes `remain` strictly smaller

### Java (sorted candidates, branch cutoff)

```java
import java.util.*;

class Solution {
    public List<List<Integer>> combinationSum(int[] candidates, int target) {
        Arrays.sort(candidates); // candidates are distinct and positive
        List<List<Integer>> result = new ArrayList<>();
        dfs(0, target, candidates, new ArrayList<>(), result);
        return result;
    }

    private void dfs(int start, int remain, int[] a,
                     List<Integer> path, List<List<Integer>> result) {
        if (remain == 0) {
            result.add(new ArrayList<>(path));
            return;
        }

        for (int i = start; i < a.length; i++) {
            if (a[i] > remain) break; // safe because sorted, all positive

            path.add(a[i]);
            dfs(i, remain - a[i], a, path, result); // reuse allowed
            path.remove(path.size() - 1);
        }
    }
}
```

### Dry run: candidates = [2,3,6,7], target = 7

```text
[] remain 7
├── 2 → [2] remain 5
│   ├── 2 → [2,2] remain 3
│   │   ├── 2 → remain 1 → cannot finish
│   │   └── 3 → [2,2,3] remain 0 ✓
│   └── 3 → remain 2 → cannot finish
├── 3 → remain 4 → 3 leaves 1, larger choices too big
├── 6 → remain 1 → cannot finish
└── 7 → [7] remain 0 ✓
```

Outputs: `[[2,2,3],[7]]` (order may vary).

### Complexity

Let `T` be target and `m` the smallest positive candidate. The recursion depth is at most `⌊T/m⌋`. A loose worst-case search bound is exponential in that depth and candidate count, e.g. `O(n^(T/m) · (T/m))` when accounting for copying output, with `O(T/m)` auxiliary recursion/path space excluding results. This bound is deliberately conservative; actual complexity is strongly dependent on candidate values, reachable sums, and number of generated answers. Avoid claiming a universal `O(2^n)` for unlimited reuse.

### What changed from LeetCode 77?

| Property | Combinations 77 | Combination Sum 39 |
|---|---|---|
| Objective | Exactly `k` distinct numbers | Sum to `target` |
| Candidate reuse | No | Yes |
| Progress | Next value / path length | Remaining positive sum |
| Next start | `i + 1` | `i` |
| Complete state | `path.size() == k` | `remain == 0` |
| Pruning | Not enough elements remain | Chosen value exceeds remaining target (sorted positives) |

## 8. Deep variation — Combination Sum II (LeetCode 40)

**Problem:** Input can contain duplicate values. Use each input element at most once; return unique combinations summing to a target.

**Link:** https://leetcode.com/problems/combination-sum-ii/  
**Difficulty:** Medium  
**Priority:** **MUST SOLVE**

### What new difficulty appears?

Suppose `nums = [1,1,2]` and target `3`.

Choosing the first `1` and then `2` is the same **value-combination** as choosing the second `1` and then `2`. But picking both ones can be legitimate in another target.

So we want to skip **equivalent first choices at the same depth**, not forbid repeated values everywhere.

### Java

```java
import java.util.*;

class Solution {
    public List<List<Integer>> combinationSum2(int[] candidates, int target) {
        Arrays.sort(candidates);
        List<List<Integer>> ans = new ArrayList<>();
        dfs(0, target, candidates, new ArrayList<>(), ans);
        return ans;
    }

    private void dfs(int start, int remain, int[] nums,
                     List<Integer> path, List<List<Integer>> ans) {
        if (remain == 0) {
            ans.add(new ArrayList<>(path));
            return;
        }

        for (int i = start; i < nums.length; i++) {
            if (i > start && nums[i] == nums[i - 1]) continue;
            if (nums[i] > remain) break; // positive sorted input

            path.add(nums[i]);
            dfs(i + 1, remain - nums[i], nums, path, ans);
            path.remove(path.size() - 1);
        }
    }
}
```

### Same-depth skipping, visualized

```text
Sorted values [1a,1b,2] (a,b denote distinct input positions)

At root:
- Choose 1a ✓
- Choose 1b ✗ (same value at same depth)
- Choose 2  ✓

Inside the branch [1a]:
- Choose 1b ✓ (this is a NEW depth, and two ones can be used)
- Choose 2  ✓
```

**Unsafe variant:** `if (i > 0 && nums[i] == nums[i - 1]) continue;` erroneously forbids selecting both copies at different levels.

## 9. Code fingerprints — reverse-engineer unfamiliar solutions

| Code shape | Usually means | Crucial follow-up |
|---|---|---|
| `for (int i=start; ...)` | Select next candidate | What is `start` protecting? |
| `dfs(i+1, ...)` | Each index used once | Does order need to be canonical? |
| `dfs(i, ...)` | Current candidate reusable | What ensures termination? |
| `if(i>start && a[i]==a[i-1]) continue` | Same-depth duplicate skipping | Was input sorted? |
| `if(a[i]>remain) break` | Monotonic feasibility cutoff | Is array sorted and are values positive? |
| `path.add(...); dfs(...); path.remove(...)` | Shared-state backtracking | Is undo guaranteed even on early exit? |
| `if(path.size()==k) record()` | Exact-size selection | Any other terminal constraints? |

**Fingerprint does not prove pattern:** A `for` loop inside DFS could also be permutation generation, neighbor traversal in a graph, or an optimization search. Understand the meaning of candidate availability.

## 10. Pattern boundaries — when NOT to use this representation

### Include–Exclude vs For-Loop Selection vs Permutations

| Question | Include–Exclude (03) | For-Loop Combinations (04) | Permutations (05) |
|---|---|---|---|
| What is a level? | Decide input position | Choose next selected member | Fill next output position |
| Main state | `index` | `start`, constraints | `used[]` / available values |
| Decision | Take or skip | Pick one eligible candidate | Pick any unused eligible candidate |
| Does order matter? | Typically no | No | Yes |
| How avoid equivalent orders? | Decisions fixed by input order | Strict/nondecreasing candidate index | Different order is an actual answer |
| Most revealing fingerprint | Two recursive branches | `for(i=start...)` | `for(i=0...)` + `used[i]` |

**When NOT to use a combination enumerator:**

- Need only **count** and formula/DP is sufficient (`nCr`): do not construct all groups.
- Input has millions of elements and objective is a simple range aggregate: use the appropriate linear/DP method.
- Order matters: prefer permutation-state reasoning.
- Need a shortest path: BFS may be natural; don't force combination recursion.
- Need the K-th combination and branch sizes can be counted: branch skipping may avoid generation (Pattern 02).
- Constraints require online modifications/queries: consider specialized structures rather than rebuilding combinations.

### Choice-boundary test

Ask: *If I reorder the selected values, does it count as a different valid result?*

- **No:** likely a combination; preserve canonical order.
- **Yes:** likely a permutation or sequence construction problem.

This is a structural test, not a keyword rule.

## 11. Pruning: valid, invalid, and conditional

### Safe pruning: insufficient choices

When choosing `k` distinct items, if `need = k - path.size()` and fewer than `need` candidates remain, this branch cannot finish.

```java
if (n - start < need) return; // zero-based array, candidates start..n-1
```

### Safe pruning: sorted positive target sum

```java
if (nums[i] > remain) break;
```

This cutoff requires sorted values and a target-sum model where using more positive values cannot reduce the sum.

### Unsafe pruning: negative values allowed

For `nums = [8,-5]`, target `3`, choosing `8` is not automatically invalid if a later `-5` is allowed. Pruning merely because `8 > 3` loses a solution.

### Unsafe pruning: zero target with additional requirements

In an exact-`k` selection problem, `remain == 0` does **not** necessarily mean done; if fewer than `k` elements have been selected, more choices could be required.

### Beware overflow

For large targets or accumulated sums, use `long` where integer addition/subtraction might overflow. Use index arithmetic carefully at bounds.

## 13. Follow-up training — what breaks when constraints change?

| Interview modification | What fails or changes? | Better state/approach |
|---|---|---|
| Reuse becomes allowed | `i+1` skips repeated uses | `i`, plus a strictly decreasing resource |
| Reuse becomes forbidden | `i` may select same index repeatedly | `i+1` |
| Duplicates added | Same value set generated via different indices | Sort + same-depth skip, if sorting preserves problem semantics |
| Order becomes significant | Canonical increasing-index enumeration loses valid orders | Permutation/sequence state (`used[]` or remaining positions) |
| Exactly `k` choices required | `remain==0` alone is insufficient | Add `path.size()` or `need` |
| Negative candidates allowed | `a[i] > remain` cutoff unsafe; reuse may cycle | Rebuild feasibility bounds, restrict reuse as necessary |
| Only count solutions | Copying lists wastes resources | Return counts, DP when states overlap |
| Return first valid group | Full result collection unnecessary | Boolean DFS and short-circuit safely |
| Need K-th group | Enumeration unnecessarily processes earlier groups | Count completions, then skip branches |
| Input is a stream | Cannot revisit fixed array | Online state model; problem may need redesign |
| Data set much larger | Exponential enumeration infeasible | Check for DP, combinatorics, meet-in-the-middle |

## 14. Mistake library

### Recognition mistakes

**Mistake:** Seeing “sum equals target” and immediately selecting Combination Sum.  
**Why:** A target value is mistaken for the decision structure.  
**Detect:** Ask if values can be reused, if output is combinations or just existence, and what constraints permit.  
**Prevent:** Define objective and choice semantics first.

**Mistake:** Using combinations when order matters.  
**Detect:** Does `[2,3]` differ from `[3,2]`?  
**Prevent:** If yes, changing choice order must be represented.

### Reasoning mistakes

**Mistake:** Treating `start` as merely a speed optimization.  
**Why:** Its role in uniqueness is missed.  
**Prevent:** State the invariant: next candidate index cannot be smaller than the last chosen one.

**Mistake:** Assuming all pruning is safe.  
**Prevent:** Provide a proof using sorted order, positivity, available capacity or exact-size bounds.

### Implementation mistakes

**Mistake:** Calling `dfs(i+1)` for unlimited reuse.  
**Result:** Valid repeated candidate selections are lost.  
**Rule:** Reuse allowed → keep `i` if some other quantity strictly progresses.

**Mistake:** Calling `dfs(i)` when each index can be used once.  
**Result:** Illegal repeated use.  
**Rule:** Move to `i+1` for no reuse.

**Mistake:** Using `i>0` instead of `i>start` for duplicate skipping.  
**Result:** Disallows legitimate equal values at deeper levels.

**Mistake:** Forgetting `path.remove(path.size()-1)`.  
**Result:** Sibling branches inherit incorrect state.  
**Rule:** Choose/recurse/undo symmetry.

**Mistake:** Adding `path` directly to `ans`.  
**Result:** Later backtracking mutates stored answers.  
**Rule:** Copy with `new ArrayList<>(path)`.

### Complexity mistakes

**Mistake:** Saying any combination generator takes exactly `O(2^n)`.  
**Why:** Fixed-size enumeration can be output-sensitive in `C(n,k)`; reusable candidate problems may depend on target.  
**Rule:** Count actual states/output size and cost per generated answer.

### Interview mistakes

**Mistake:** Coding before clarifying duplicates, reuse, order and required length.  
**Rule:** Ask those four questions first; they determine the state transitions.

## 15. Topic-specific unseen-problem framework

```text
1. Strip story → generate, count, decide, or optimize?
2. Does ordering of selected items matter?
   - Yes → inspect permutations/sequence construction.
   - No  → candidate selection may be appropriate.
3. Must every input position be explicitly decided?
   - Yes → include/exclude can be natural.
   - No  → choose next candidate from start..
4. Is an index reusable? → i or i+1?
5. What uniquely describes state? start / remain / need / path?
6. What is the base case? Exactly k? Remaining sum zero? Both?
7. Are equal values distinguishable or must output be unique?
8. Which constraint proves a branch impossible?
9. State canonical-order invariant before code.
10. Trace choose → recurse → undo for a small sample.
```

### Decision tree

```text
Need to construct selections?
│
├── Order matters → Pattern 05 (Permutation/Arrangement) or sequence search
│
└── Order does not matter
    │
    ├── Fixed take/skip per index → Pattern 03
    │
    └── Choose next eligible candidate → Pattern 04
        │
        ├── Index use once → recurse(i + 1)
        ├── Reuse allowed → recurse(i) + guarantee progress
        └── Duplicate values → sort if legal + same-depth skip
```

## 16. Summary sheet

| Pattern | Recognition | Invariant | Main DS | Complexity shape | Confused with |
|---|---|---|---|---|---|
| Exact-`k` combinations | Unordered group of size `k` | Strict increasing indices | `path`, `start` | Output-sensitive `Θ(k C(n,k))` for typical pruned enumeration | Include/exclude |
| Reusable target combinations | Unordered multiset to target | Nondecreasing candidate indices; positive remainder shrinks | `path`, `start`, `remain` | Exponential in depth/output | Unbounded knapsack DP |
| Unique combinations with duplicate inputs | Equal values, one-use indices | No same-depth equal-valued first choices | Sorted array, `path` | Exponential/output-sensitive | Global duplicate bans |
| Size + target constraints | Exactly `k` and prescribed sum | Size, sum, eligibility jointly valid | `path`, `need`, `remain` | Bounded exponential | Count-only DP |

**The three-line fingerprint to reconstruct:**

```java
for (int i = start; i < n; i++) {
    choose(i);
    dfs(reuseAllowed ? i : i + 1);
    undo(i);
}
```

Use this only as a conceptual signature — real Java code needs the complete state and condition.

### U1. Research group

A laboratory has `n` researchers, numbered `1..n`. It wants all different committees of exactly `r` researchers. The internal ordering of committee members is irrelevant. How will you avoid counting two reorderings as different committees?

### U2. Reusable purchase bundles

A shop offers distinct positive package sizes. You may purchase the same package size multiple times. Find every different unordered collection of packages whose total is exactly a target quantity.

### U3. Duplicate catalog labels

A catalog has repeated labels at different positions. You must select each physical item at most once and produce unique lists of selected labels totaling a target. Can you skip every second occurrence of a repeated label globally?

### U4. Mixed signs

A set contains positive and negative integers. You must choose exactly three different positions whose sum is a target. A proposed algorithm sorts the array and stops scanning whenever the current value exceeds the remaining target. Is that cutoff safe? Explain without coding.

### U5. Hidden ordering trap

A keypad has three successive positions, each with its own allowed set of letters. Select exactly one letter per position to form all possible codes. Is this truly an unordered combination task? What state is different?

**Evaluation rule:** Only after you answer should the interviewer reveal the underlying patterns and critique your invariant, pruning, and complexity.

## Final takeaway

> In ordinary combinations, `start` is **not just an implementation variable**. It is the mechanism that gives each unordered selection one canonical construction path. Every follow-up changes the meaning of candidate availability: reuse, one-use, duplicate values, remaining size or remaining sum.

The pattern is mastered when you can derive these transitions from the rules of the problem rather than copying `dfs(i)` or `dfs(i+1)` from memory.
