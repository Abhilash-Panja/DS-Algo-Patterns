## 1. Practical one-line definition

> **I process a sequence of decisions; at each position I either include the current candidate or exclude it, then solve the remaining positions.**

For `n` independent yes/no decisions, the raw search space has `2^n` complete decision sequences. Constraints may prune it; not every task needs to visit all of them.

### Capability

Given items `[a, b, c]`, represent the choice of *any subset of indices* without manually writing combinations of lengths 0, 1, 2, and 3.

```text
Decision for a?  take / skip
Decision for b?  take / skip
Decision for c?  take / skip
                      ↓
                complete selection
```

If input values repeat, different **index selections** can produce the same **value list**. This matters in duplicate-handling variants.

---

## 2. Why this pattern exists — brute force to recursion

**Problem:** Generate every subset of `[1, 2, 3]`.

A first attempt might list all subsets of size 0, then size 1, then size 2, then size 3. But this requires separate enumeration logic by length.

Instead, ask:

1. Does the subset contain `1`? Yes or no.
2. Regardless of that choice, does it contain `2`? Yes or no.
3. Then `3`? Yes or no.

Each decision shrinks the remaining unprocessed suffix by one.

```text
Manual enumeration by subset size
                 ↓
Every element is either chosen or not
                 ↓
One binary decision per index
                 ↓
Recursive traversal of decision tree
```

This representation scales naturally to any number of input elements, although the number of possible subsets still grows exponentially.

## 3. Recognition signals — diagnostic questions

Before naming the pattern, ask:

1. **What is the unit of decision?** Is each input position independently *selected or not selected*?
2. **Must every index be decided exactly once?** If yes, a binary decision per index is natural.
3. **Is the objective a subset of positions rather than an ordering?** If yes, avoid permutation-oriented state.
4. **Can a partial selection be proved invalid?** If so, choose a safe pruning rule, not a guess.
5. **Does the answer demand all subsets, one feasible subset, a count, or a best score?** This determines the return contract and whether to stop early.
6. **Do duplicate values matter?** Distinguish unique selections of indices from unique combinations of values.

### Trigger words, but don't depend on them

Common words: *subsequence*, *subset*, *select some items*, *choose a group*, *partition into two groups*, *possible target sum*.

**Disguised scenario:** "A technician receives several optional upgrades. List each distinct set of upgrades that could be activated." Even without the word *subset*, every upgrade has a yes/no decision.

**Negative clue:** If each step selects one of several *unused elements for an ordered slot*, you are closer to Pattern 05 (Permutations).

## 4. State, contract, invariant, and termination

Take `nums = [1,2,3]`.

| Component | Meaning |
|---|---|
| `index` | Next undecided input position |
| `path` | Items chosen among indices `[0, index)` |
| Base case | `index == nums.length`: all positions decided |
| Choices | Skip `nums[index]`; take `nums[index]` |
| Progress | `index` increases by one |
| Invariant | `path` contains exactly the selected values from processed positions, in original order |

**Function contract:** `dfs(index, path)` explores every decision sequence for indices `index..n-1`, starting from the selections represented by `path`.

### Correctness by induction

- **Base:** At `index == n`, every index has a decision. Copy the completed selection.
- **Step:** Every complete selection either excludes index `i` or includes index `i`. These alternatives are exhaustive and disjoint at the **index-selection** level.
- Recursing under each alternative covers every index-selection exactly once.

This does **not** imply unique value lists when input contains repeated values.

---

### 4.1 The bridge from a mathematical choice to a recursive recurrence: `nCr`

Your newly supplied Recursion Foundation notes derive the number of ways to choose `r` items from `n` distinct items by focusing on **one particular item**:

- **Exclude it:** choose all `r` items from the remaining `n-1` items.
- **Include it:** choose the remaining `r-1` items from the remaining `n-1` items.

Because every selection lies in exactly one of these categories,

\[
C(n,r)=C(n-1,r)+C(n-1,r-1).
\]

The base cases are `C(n,0) = C(n,n) = 1` for `0 <= n`, and `C(n,r)=0` for `r<0` or `r>n`.

```java
// Teaching version: assumes n >= 0; counts may overflow long.
static long chooseCount(int n, int r) {
    if (r < 0 || r > n) return 0L;
    if (r == 0 || r == n) return 1L;

    return chooseCount(n - 1, r)           // exclude a fixed item
         + chooseCount(n - 1, r - 1);      // include that item
}
```

**Contract:** `chooseCount(n,r)` returns the number of index-subsets of size `r` chosen from `n` distinct positions. **Invariant:** each recursive call counts exactly the subsets fitting its remaining size constraint. **Warning:** this straightforward recurrence recomputes `(n,r)` states; if the input is large, consider memoization, Pascal's triangle, or a suitable direct combinatorial formula. It also may overflow `long`.

**Critical distinction:** `nCr` here is **counting** choices, not constructing the selected items. An enumeration variant stores `path` and snapshots completed selections. The invariant changes with the function's contract.

### 4.2 Why the two branches cover the entire answer space

For any index `i`, every valid index-subset **either contains `i` or does not contain `i`**. These cases are mutually exclusive and exhaustive. Each recursively fixes one new decision, so a length-`n` binary decision sequence determines one subset of *indices*.

This is an actual correctness argument—not merely a code pattern. It also explains why duplicate input *values* require care: different index-subsets can still have identical lists of values.

## 5. Deep worked example — Subsets (LeetCode 78)

**Problem:** Given an array of **distinct** integers, return all subsets (the power set).

**Link:** https://leetcode.com/problems/subsets/

### 5.1 Strip the story

- Input: `n` distinct integers.
- Output: every selection of zero or more input indices.
- No ordering among selected subsets required; inside each subset we can preserve input order.

### 5.2 Naive approach

Manually enumerate combinations of each possible size. The total number of subsets is already `2^n`; the real problem is organizing enumeration without omissions and duplicates.

### 5.3 Structural observation

For each index, exactly two outcomes: exclude it or include it.

### 5.4 Connect to pattern

This is binary include/exclude because every position receives precisely one of two decisions, and each decision is final once the recursion advances.

### 5.5 Dry run

```text
                             index 0, []
                         /skip 1     \take 1
                 index 1, []       index 1, [1]
                /        \          /         \
           skip 2      take 2     skip 2      take 2
             []          [2]       [1]        [1,2]
           /   \        /   \     /   \       /   \
        []    [3]     [2] [2,3]  [1] [1,3] [1,2] [1,2,3]
```

Notice the action *after* the include branch: remove what was added, restoring the parent's state.

### 5.6 Java — canonical template

```java
import java.util.*;

class Solution {
    public List<List<Integer>> subsets(int[] nums) {
        List<List<Integer>> ans = new ArrayList<>();
        dfs(0, nums, new ArrayList<>(), ans);
        return ans;
    }

    private void dfs(int i, int[] nums,
                     List<Integer> path,
                     List<List<Integer>> ans) {
        if (i == nums.length) {
            ans.add(new ArrayList<>(path)); // snapshot, not alias
            return;
        }

        // Branch 1: exclude nums[i].
        dfs(i + 1, nums, path, ans);

        // Branch 2: include nums[i].
        path.add(nums[i]);
        dfs(i + 1, nums, path, ans);
        path.remove(path.size() - 1); // restore parent's path
    }
}
```

**Why copy?** `path` is one shared mutable object. `new ArrayList<>(path)` freezes the current contents as an independent result.

**Why undo?** Without removing the last element, the parent's state would still include a choice when the call returns.

### 5.7 Complexity — justify, don't recite

- Exactly `2^n` leaves, since each of `n` indices has two choices.
- Each leaf copies at most `n` selected values.
- **Time:** `O(n · 2^n)` when materializing results.
- **Auxiliary stack + working path:** `O(n)`, excluding stored results.
- **Result storage:** `Θ(n · 2^n)` total elements across all subsets for `n >= 1` (in fact `n · 2^(n-1)` selected elements), plus list overhead.

Two recursive calls do **not** make stack space `O(2^n)`; their executions happen sequentially.

### 5.8 60–90 second interview explanation

> Every input element can independently be excluded or included. I'll define `dfs(i, path)` as exploring all selections for the unprocessed suffix while `path` stores choices made before index `i`. At each index I'll first skip it, then add it, recurse, and remove it so the parent's state is restored. When `i` reaches `n`, I'll add a copy of `path` to the output. Since there are `2^n` subsets and copying each subset can take `O(n)`, the time is `O(n2^n)` and the auxiliary search space is `O(n)` excluding output.

### 5.9 Execution order: work before the call versus after it

Your supplied foundation notes use the pattern `n, n-1, ..., 1, 2, ..., n` to demonstrate what runs **on the way down** and **while the stack unwinds**. The same ordering rule is essential for backtracking:

```java
static void trace(int n) {
    if (n == 0) return;
    System.out.print("enter " + n + " ");  // before deeper call
    trace(n - 1);
    System.out.print("exit " + n + " ");   // after deeper call
}
// trace(2): enter 2 enter 1 exit 1 exit 2
```

For binary-choice enumeration, `path.add(...)` is the **enter/choose** action; `path.remove(...)` is the **exit/undo** action. The action after recursion is not optional housekeeping: it restores the parent's invariant before the next sibling branch can use the same list.

**A subtlety:** The order in which you try skip and take changes *output order*, but not the set of index-subsets produced. If the interviewer requires a particular lexicographic order, the traversal order must be designed deliberately.

### 5.10 Trace one parent frame, not only the final leaves

For `[1,2]`, focus on the call at `index=0, path=[]`:

1. Explore **skip 1**; the parent list stays `[]` throughout this subtree.
2. Add `1` to the same list; now `path=[1]`.
3. Explore **take 1**; deeper calls temporarily add/remove `2`.
4. Remove `1`; when the function returns, `path=[]` again.

The recursion **tree** counts all explored calls, but the **stack** holds only the currently active frames. The stack can be `O(n)` even though the number of complete index-decision sequences is `2^n`.

## 6. The reusable template and its variants

### A. Enumerate all solutions

```java
void dfs(int i) {
    if (i == n) {
        saveSnapshot();
        return;
    }
    dfs(i + 1);    // skip
    choose(i);     // mutate path/state
    dfs(i + 1);    // take
    undo(i);       // restore
}
```

### B. Decide whether at least one solution exists

```java
boolean exists(int i, int remaining) {
    if (i == n) return remaining == 0;

    if (exists(i + 1, remaining)) return true;
    return exists(i + 1, remaining - nums[i]);
}
```

This version uses no shared path: no explicit undo is needed. However, worst-case work remains exponential if no pruning or memoization applies.

### C. Count valid selections

```java
long count(int i, long remaining) {
    if (i == n) return remaining == 0 ? 1L : 0L;

    return count(i + 1, remaining)
         + count(i + 1, remaining - nums[i]);
}
```

Counts may overflow `long`; check the expected range. Overlapping states `(i, remaining)` suggest memoization if feasible.

### D. State accumulator instead of backtracking path

```java
void printSums(int i, int sum) {
    if (i == nums.length) {
        System.out.println(sum);
        return;
    }
    printSums(i + 1, sum);
    printSums(i + 1, sum + nums[i]);
}
```

`sum` is a primitive value passed by value. There is nothing to undo.

---

### E. Count *exactly* `r` chosen elements without constructing subsets

This closely connects the new `nCr` derivation to our ordinary `(index, chosenCount)` state:

```java
static long countSizeR(int index, int chosen, int n, int r) {
    // Valid pruning: can't reach r from this state.
    if (chosen > r || chosen + (n - index) < r) return 0;
    if (index == n) return chosen == r ? 1L : 0L;

    return countSizeR(index + 1, chosen, n, r)       // skip
         + countSizeR(index + 1, chosen + 1, n, r);  // take
}
```

Unlike unsafe sum pruning when negative numbers exist, these count bounds are **provably safe**: the number already chosen cannot decrease, and each remaining position can increase it by at most one. Again, count values may overflow `long`.

**Cross-check:** For `n=4, r=2`, the answer is `6`, matching `C(4,2)`.

## 8. When NOT to use include/exclude

1. **Ordering matters:** Generating all permutations needs an unused-elements/position invariant, not just selected indices.
2. **The next decision has many candidate values:** For-loop selection is often clearer and may avoid duplicate representations.
3. **Only one structured K-th result is needed:** Consider counting and skipping branches (Pattern 02) instead of enumerating.
4. **A contiguous region is required:** Sliding window/two pointers may fit better than arbitrary subsets.
5. **Very large `n` with an optimization objective:** Plain `2^n` traversal may be impossible; seek DP, meet-in-the-middle, greedy proof, or pruning.
6. **Duplicate values must produce unique subsets:** A naive binary tree generates duplicate value lists; sort and apply careful duplicate rules, or use Pattern 04's candidate-loop formulation.

### Pattern boundaries

| Question | Include–Exclude | For-Loop Combinations | Permutations |
|---|---|---|---|
| Decision at level | Take/skip current index | Which next index to pick | Which unused item fills this position |
| Typical state | `i, path` | `start, path` | `used[], path` |
| Advances | Every position decided | Selected indices move forward | Selected element marked used |
| Order of selected values | Original input order | Usually original/sorted order | Arrangement order matters |
| Common strength | Reasoning about every yes/no choice | Natural k-length and de-dup logic | All orderings |

**Important:** Both include/exclude and for-loop selection can enumerate combinations. The choice of template is about **the cleanest invariant**, not about one being universally faster.

## 9. Variations and meaningful new ideas

### 9.1 Target subset sum — extra state

A target-sum variant introduces `remaining` (or `sumSoFar`). At the base case, test whether the completed decision path meets the goal. Your recurrence depends on whether each element may be chosen once, whether values can be negative, and whether you need a boolean, count, or actual selections.

**Pruning caution:** `remaining < 0` is not a valid prune if negative future values can recover the target. With all remaining values non-negative, `remaining < 0` can be safe for non-negative target-sum formulations where you only subtract selections.

### 9.2 Subsequences — preserve order

A subsequence is formed by deleting any number of elements without reordering the rest. Include/exclude applies directly, but its output may include duplicates when the input values repeat.

### 9.3 Equal partition — constrained subset selection

A partition of the entire set into two groups can be represented by take/skip decisions assigning each index to one of two sides. If you need only feasibility, a DP formulation is often significantly more efficient than enumerating all `2^n` assignments.

### 9.4 Count versus generate

If a problem asks for a **count**, don't blindly create a list of every solution. The same state tree may be representable through a recurrence and memoization. Counting changes your function contract; it does not necessarily eliminate exponential time by itself.

### 9.5 Duplicate values — index uniqueness != output uniqueness

With `[1,1]`, two distinct index decisions both output `[1]`. If only unique value-subsets are allowed, sort and prevent duplicate-value outputs using an appropriate dedup strategy. We'll derive the preferred candidate-loop technique in Pattern 04 rather than memorizing a fragile special case here.

## 12. Mistake library

### Recognition mistakes

- **Mistake:** See the word "subset" and assume generating all subsets is mandatory.  
  **Detect:** User asks existence, count, or optimum.  
  **Prevent:** Define output contract first.
- **Mistake:** Use take/skip to generate permutations.  
  **Detect:** The requested order of selected elements matters.  
  **Prevent:** Switch to arrangement/unused-state thinking.

### Reasoning mistakes

- **Mistake:** Claim each value subset appears once even with duplicates.  
  **Why:** Binary decisions uniquely represent index sets, not necessarily value lists.  
  **Prevent:** State uniqueness assumptions explicitly.
- **Mistake:** Prune when a partial sum exceeds target without checking signs.  
  **Detect:** Negative values could later reduce the sum.  
  **Prevent:** Prove that no completion can recover.

### Implementation mistakes

- **Mistake:** Append `path` rather than a copy.  
  **Prevent:** `ans.add(new ArrayList<>(path))`.
- **Mistake:** Forget to undo after include.  
  **Prevent:** Pair each shared mutable `choose` with matching `undo`.
- **Mistake:** Wrong base-case placement leads to duplicate or missing outputs.  
  **Prevent:** Save a selection after all indices are decided in the canonical template.

### Complexity mistakes

- **Mistake:** Say `O(2^n)` for materializing all subsets without accounting for copying.  
  **Prevent:** `2^n` leaves × up to `n` copied values = `O(n2^n)`.
- **Mistake:** Say stack space is exponential because the tree is exponential.  
  **Prevent:** Maximum active depth is `n`.

### Interview mistakes

- **Mistake:** Begin coding before specifying `index` and `path`.  
  **Prevent:** State: `path` holds selected values among processed indices.
- **Mistake:** Treat pruning as obvious.  
  **Prevent:** Give a proof or counterexample involving negatives/duplicates.

### Java stack-depth and tail-position caution

Your second supplied note correctly emphasizes that a recursion tree and the execution stack measure different things. For Java interviews, **do not assume tail-call optimization**. Java does not guarantee elimination of recursive stack frames even if a call is in tail position.

- This pattern typically explores up to `2^n` leaves but reaches only `O(n)` recursive depth.
- `O(n)` depth can still cause `StackOverflowError` for sufficiently large `n`; there is no universal safe threshold.
- If `n` is huge, first ask whether the problem even permits exhaustive enumeration. For a counting/existence task, DP, combinatorial reasoning, iteration, or another optimization may be more appropriate.
- If the output itself contains `2^n` objects, an exponentially large result cannot be made cheap by swapping recursion for iteration.

## 13. Decision tree for unfamiliar problems

```text
Is the output based on decisions about individual input positions?
│
├── No → Likely another pattern family.
└── Yes
    │
    ├── Are choices independent take/skip or two-way labels?
    │   ├── Yes → Binary-choice state (index + relevant metadata)
    │   └── No  → Candidate-loop / permutation / constraints
    │
    └── What is requested?
        ├── All → enumerate leaves and snapshot results
        ├── Any → boolean return and short-circuit
        ├── Count → sum branch counts; consider memoization
        └── Best → carry objective/bounds; optimization search
```

Before exploring, ask: **Is the candidate count small enough? Does a correct prune or reusable state exist?**
