# 1.06 — Pattern 06: Partitioning / Segmentation

> **Pattern family:** Recursion & Backtracking · Pattern 06 of 09  
> **Language:** Java  
> **Primary mental model:** At each boundary, choose **where the next contiguous piece ends**, validate that piece, and recurse on the remaining suffix.  
> **Prior patterns:** [1.03 Include–Exclude](./1.03%20Binary%20Choice%20-%20Include-Exclude%20(Revised).md), [1.04 Combinations](./1.04%20For-Loop%20Selection%20-%20Combinations.md), [1.05 Permutations](./1.05%20Permutations%20-%20Arrangement.md)

---

## 0. Position in the pattern map

We have already learned three search geometries:

- **Include–Exclude:** decide whether to keep each item.
- **Combinations:** choose the next eligible item while keeping selection order canonical.
- **Permutations:** fill the next position with any unused item.

**Partitioning is different:** we must cover the **entire input, in order**, by choosing boundaries between contiguous pieces. We do not reorder elements or omit them.

```text
Input: a a b

Choose contiguous segments:
[a] [a] [b]
[aa] [b]
[a] [ab]
[aab]

Apply a segment-validity rule (e.g. each piece must be palindrome):
[a] [a] [b]  ✓
[aa] [b]     ✓
[a] [ab]     ✗
[aab]        ✗
```

The two valid palindrome partitions above are the answers to the canonical anchor problem.

**Note on your handwritten notes:** Your earlier LCCM (Level → Choice → Check → Move) framework applies directly: **Level** = starting index of the remaining suffix; **Choice** = possible end of the next segment; **Check** = segment validity; **Move** = add segment, recurse from `end + 1`, then undo. The earlier notes established the choice/check/undo reasoning; the variable-length-cut specialization is added here.

---

## 1. Practical one-line definition

> **Partitioning backtracking explores all valid ways to divide an ordered input into nonempty contiguous segments by choosing the next cut position.**

What capability does it give us? It constructs complete segmentations subject to local or global rules, without missing any possible cut arrangement.

### Recognition before code

Ask:

1. **Must every input position be included exactly once?**
2. **Must the original order remain unchanged?**
3. **Do the answers consist of consecutive pieces?**
4. **Can the next piece have several possible lengths?**
5. **Can validity be tested for a proposed piece or partial segmentation?**

If the first three are yes and the fourth is yes, **cut-point recursion** is a strong candidate.

### Trigger language—but not keyword matching

“Split string,” “partition,” “segments,” “valid words,” “palindromic pieces,” “restore addresses,” or “insert separators” may appear. But the problem might be disguised as: *A transmission contains consecutive symbols; recover every legal sequence of packets without changing symbol order.* The structure—not the nouns—is the clue.

## 2. Derive the pattern from brute force

### Step A — Naive thinking: place separators

For an input of length `n`, there are `n - 1` gaps between consecutive elements. Each gap either **has a cut or does not**.

```text
A | B | C | D
  ^   ^   ^
  3 independent gap decisions → 2^3 = 8 partitions
```

Thus the number of segmentations into nonempty contiguous pieces is **`2^(n-1)` for `n >= 1`**, *before filtering for validity*. For `n = 0`, the empty partition is usually represented by one empty list; always check the problem's output convention.

This is a valid include/exclude view, but storing gap decisions is often awkward when each segment must be validated as we construct it.

### Step B — Make one entire segment the decision

Suppose the remaining input begins at `start`. The first piece could end at:

```text
start, start + 1, ..., n - 1
```

Every choice `end` defines exactly one next piece `s[start..end]`.

### Step C — Why does the recursion work?

Once we select `s[start..end]`, the remainder **must start at `end + 1`**. There is no overlap and no skipped character.

```text
Already covered  | Next segment     | Remaining suffix
s[0 .. start-1] | s[start .. end] | s[end+1 .. n-1]
```

Every complete partition has a unique first segment, then a unique partition of the remaining suffix. Hence iterating over every legal `end` is exhaustive and nonredundant for an index-distinguished input.

## 3. The invariant (most important)

> At the beginning of `dfs(start)`, `path` contains valid, consecutive, nonoverlapping segments that cover **exactly** `s[0..start-1]`, and no other characters.

After choosing `end`:

1. Check that `s[start..end]` can be the next piece.
2. Append that piece, so the path covers `s[0..end]`.
3. Recurse with `start = end + 1`.
4. Remove the piece, restoring the parent's exact state.

When `start == s.length()`, every character is covered, so **copy** `path` to the answers.

### Why the data structures fit

- `int start`: first uncovered index; avoids copying the remaining suffix.
- `ArrayList<String> path`: current segments in order; cheap append/remove at end.
- `List<List<String>> result`: saved complete segmentations.
- `boolean[][] palindrome` (optional): supports repeated substring-validity checks in O(1) after O(n²) preprocessing.

Why not a `HashSet`? Ordering and contiguous positions define the solution; set membership does not encode boundaries. Why not sorting? Sorting destroys the original contiguity. Why not a `used[]` array? The next segment always begins at `start`; previously consumed positions cannot become candidates again.

## 4. Minimal Java pattern skeleton

```java
void dfs(int start, String s, List<String> path,
         List<List<String>> ans) {
    if (start == s.length()) {
        ans.add(new ArrayList<>(path)); // snapshot, not shared reference
        return;
    }

    for (int end = start; end < s.length(); end++) {
        if (!validSegment(s, start, end)) continue;

        path.add(s.substring(start, end + 1)); // choose
        dfs(end + 1, s, path, ans);              // explore suffix
        path.remove(path.size() - 1);           // restore
    }
}
```

This is a **schematic helper**, not a standalone compilable class: `validSegment` must be supplied for the specific problem.

### Code fingerprint

```java
for (int end = start; end < n; end++) {
    if (!valid(start, end)) continue;
    path.add(piece(start, end));
    dfs(end + 1);
    path.remove(path.size() - 1);
}
```

If you see **`end` looping from `start`** and the recursive call **`dfs(end + 1)`**, check for a partition/segmentation search. This is a diagnostic shape, not a universal rule.

## 5. Deep worked example — Palindrome Partitioning (LeetCode 131)

**Problem:** Return every possible partition of string `s` such that **every segment is a palindrome**.  
**Link:** https://leetcode.com/problems/palindrome-partitioning/  
**Difficulty:** Medium  
**Priority:** **MUST SOLVE**

### Step 1 — Strip the story

- Input: string `s` of length `n`.
- Output: a list of all sequences of nonempty contiguous substrings that concatenate to `s`.
- Constraint: each substring must equal its reversal.
- Goal: **enumerate all** valid segmentations, not just count them or find one.

### Step 2 — Brute-force baseline

Choose whether to cut at each of the `n - 1` gaps, generate every segmentation, and then test every segment for palindrome validity. There are `2^(n-1)` raw cut configurations for nonempty input. A straightforward implementation may require O(n) work to check a complete candidate if designed efficiently with index ranges and total segment length; more naive substring/reversal handling can be more expensive.

**Bottleneck:** Many complete segmentations contain an obviously invalid segment. Why wait until the entire partition is constructed?

### Step 3 — Structural observation

When trying the next piece `s[start..end]`, we can check whether **that piece** is a palindrome immediately. If not, **do not explore descendants under this specific choice**.

Crucial distinction: failure of `[start..end]` means **skip that `end`**; it does **not** mean `break`, because a longer segment may become a palindrome again (e.g. `"aba"` is palindromic although `"ab"` is not).

### Step 4 — Derive the pattern

- State: `start`, `path`.
- Available choices: all segment ends `end >= start`.
- Feasibility test: `isPalindrome(start, end)`.
- Move: append segment, recurse from `end + 1`, undo.
- Base case: `start == n` records a complete partition.

### Step 5 — Dry run (`s = "aab"`)

```text
dfs(0), path=[]
├── choose s[0..0] = "a"  ✓   path=[a]
│   ├── choose s[1..1] = "a"  ✓  path=[a,a]
│   │   └── choose s[2..2] = "b" ✓ → save [a,a,b]
│   └── choose s[1..2] = "ab" ✗  skip this choice
├── choose s[0..1] = "aa" ✓   path=[aa]
│   └── choose s[2..2] = "b" ✓ → save [aa,b]
└── choose s[0..2] = "aab" ✗  skip this choice
```

| Call/choice | `path` after choose | Next `start` | Result |
|---|---|---:|---|
| `[0..0] = "a"` | `[a]` | 1 | Explore |
| `[1..1] = "a"` | `[a,a]` | 2 | Explore |
| `[2..2] = "b"` | `[a,a,b]` | 3 | Save copy |
| `[1..2] = "ab"` | — | — | Reject |
| `[0..1] = "aa"` | `[aa]` | 2 | Explore |
| `[2..2] = "b"` | `[aa,b]` | 3 | Save copy |

Every return undoes its own last selection. The outer call therefore explores the next possible first segment from a clean state.

### Step 6 — Complete Java solution (straightforward)

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    public List<List<String>> partition(String s) {
        List<List<String>> ans = new ArrayList<>();
        dfs(0, s, new ArrayList<>(), ans);
        return ans;
    }

    private void dfs(int start, String s,
                     List<String> path, List<List<String>> ans) {
        if (start == s.length()) {
            ans.add(new ArrayList<>(path));
            return;
        }

        for (int end = start; end < s.length(); end++) {
            if (!isPalindrome(s, start, end)) continue;

            path.add(s.substring(start, end + 1));
            dfs(end + 1, s, path, ans);
            path.remove(path.size() - 1);
        }
    }

    private boolean isPalindrome(String s, int left, int right) {
        while (left < right) {
            if (s.charAt(left++) != s.charAt(right--)) return false;
        }
        return true;
    }
}
```

`substring(start, end + 1)` uses an **exclusive** ending index. `end` in the DFS loop is **inclusive**.

### Step 7 — Complexity without hand-waving

Let `n = s.length()`.

- There are at most `2^(n-1)` complete cut patterns for nonempty `s`.
- The recursive search can visit exponentially many partial partitions.
- Each palindrome check scans up to O(n) characters; copying a completed path and its string content also incurs work.
- A safe, standard upper bound for this implementation is **O(n² · 2^n)** time (a conservative bound covering repeated palindrome checks and substring work).
- Maximum recursion depth is **O(n)**, the `path` holds at most `n` segments, and substring objects retained along a path may occupy O(n) total characters; excluding stored output, **O(n)** auxiliary state is possible for the DFS plus generated substring contents along a single path (in addition to implementation-level string overhead). The output may use **O(n · 2^n)** characters/items in the worst case.

This pessimistic time bound is not tight for every input. In the all-equal-character case, the number and size of generated answers alone force exponential work.

### Step 8 — Optional improvement: precompute palindrome validity

If the same `s[start..end]` is checked across many recursive paths, preprocess:

```java
boolean[][] pal = new boolean[n][n];
for (int len = 1; len <= n; len++) {
    for (int left = 0; left + len <= n; left++) {
        int right = left + len - 1;
        pal[left][right] = s.charAt(left) == s.charAt(right)
                && (len <= 2 || pal[left + 1][right - 1]);
    }
}
```

- Preprocessing: O(n²) time, O(n²) extra space.
- Lookup: O(1) per candidate segment.
- Overall enumeration with materialized output: **O(n · 2^n + n²)** time as a useful upper bound, since the O(n)-sized representation of each output can dominate.

**Trade-off:** Precomputation makes sense when validation repeats enough to justify O(n²) memory. For small `n`, the simple two-pointer checker is often clearer.

### Step 9 — Interview explanation (60–90 seconds)

> I need all ways to cover the original string using consecutive palindromic pieces. I define `dfs(start)` to explore valid partitions of the suffix beginning at `start`, while `path` contains valid pieces covering the prefix before `start`. I try every possible end index for the next segment; if that substring isn't a palindrome, I skip that particular choice. Otherwise, I append it, recurse from `end + 1`, and remove it on return. At `start == n`, the entire string has been covered and I copy the path. Each possible partition has a unique sequence of cut positions, so this explores all valid answers without reordering or omitting characters. Time is exponential because the output itself can be exponential; I can precompute palindrome checks if repeated validation becomes costly.

## 6. Variation family: What changes in the state?

### A. Enumerate every valid segmentation

- **Example:** Palindrome Partitioning (LC 131).
- **State:** `start`, mutable path.
- **Return/action:** Append copies of complete paths.
- **Invariant:** Path covers exactly the consumed prefix.

### B. Decide whether at least one segmentation exists

- **Example:** Word Break (LC 139).
- **State:** Starting index alone may be sufficient if word membership is fixed and no path-dependent constraints exist.
- **Return:** `boolean`.
- **Observation:** Different partitions can reach the same `start`, so **memoization** can remove repeated exploration.

A boolean decision problem should not automatically enumerate and store every partition.

```java
// Schematic decision recursion:
boolean canBreak(int start) {
    if (start == n) return true;
    if (memo[start] != null) return memo[start];

    for (int end = start; end < n; end++) {
        if (isWord(start, end) && canBreak(end + 1)) {
            return memo[start] = true;
        }
    }
    return memo[start] = false;
}
```

The above snippet assumes `memo`, `n`, and `isWord` are supplied. It illustrates the reusable-state boundary, not a complete standalone implementation.

### C. Count segmentations

- **Example:** count valid partitions with length constraints.
- **State:** index (plus any additional restrictions that affect future choices).
- **Return:** number of valid completions.
- **Transition:** sum counts across legal next segments.

```text
ways(start) = Σ ways(end + 1)
              for every legal segment [start .. end]
ways(n) = 1   // one way to complete an already exhausted suffix
```

Use `long` or modular arithmetic as specified; counts can grow exponentially.

### D. Partition into exactly `k` segments

- **State:** `(start, segmentsLeft)` or `(start, segmentsUsed)`.
- **Invariant:** Exactly the given number of segments remain to be built.
- **Pruning:** If `remainingCharacters < segmentsLeft`, it is impossible to make all future segments nonempty.
- **Base:** Accept only if `start == n && segmentsLeft == 0`.

### E. Global constraints / cross-segment state

- **Examples:** segments must have strictly increasing lengths, unique labels, or compatible adjacent values.
- **State:** add previous segment length/value or any information that future decisions really require.
- **Warning:** Memoizing solely by `start` would be wrong if two paths at the same `start` have different allowed futures.

## 7. Detailed boundary comparison

| Question | Include–Exclude | For-Loop Combinations | Partitioning / Segmentation | Permutations |
|---|---|---|---|---|
| Basic choice | Take or skip current item | Which eligible item next? | Where does the next piece end? | Which unused item fills next slot? |
| Must cover full input? | No | No | **Yes** | Yes, generally |
| Must preserve original order? | Selected indices may preserve order | Usually canonical increasing indices | **Yes, with contiguity** | No |
| Can omit items? | Yes | Often yes | **No** | No, in full permutations |
| Core state | `index` | `start` candidate index | `start` unconsumed position | `used[]` / arrangement position |
| Next call | `index + 1` (both branches) | `i` or `i + 1` | **`end + 1`** | next arrangement position |

### Pattern collision 1: “Partition array into two groups”

If group members may be **noncontiguous**, this is a **subset/assignment** problem, not cut-point segmentation. Example: assign elements to two equal-sum subsets.

### Pattern collision 2: “Divide a string into words”

If words must appear as **consecutive substrings**, segmentation fits. If selected dictionary words may be reordered independently, it is a different search.

### Pattern collision 3: “Minimum number of cuts”

If we only need the optimum, enumerating all partitions may be wasteful. Consider DP over indices or palindrome intervals (e.g. Palindrome Partitioning II, LC 132).

---

## 8. Negative signals — when NOT to force this pattern

1. The output is a set of elements with no contiguous ordering requirement → subset/combination instead.
2. Any unused item can be chosen next → permutation/assignment instead.
3. Only a single numeric optimum is required and the state overlaps heavily → DP or graph shortest-path framing may be better.
4. Segment boundaries are predetermined → direct processing rather than search.
5. A valid segment depends on future global information, so checking only local validity cannot establish completeness → enrich state and postpone only the checks that are not yet safe.

**Important:** `continue` on a failed segment check is generally correct when that segment itself can never appear in a valid result. `break` requires an additional **monotonicity proof** that all longer segments also fail.

## 10. Additional worked variation — Restore IP Addresses

**Goal:** Insert three separators to produce four valid IPv4 components.

Rules for each component:

- 1 to 3 digits;
- numeric value at most 255;
- no leading zero unless the component is exactly `"0"`.

**State:** `(start, piecesUsed)`; `path` stores accepted components.

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    public List<String> restoreIpAddresses(String s) {
        List<String> ans = new ArrayList<>();
        dfs(s, 0, new ArrayList<>(), ans);
        return ans;
    }

    private void dfs(String s, int start, List<String> path,
                     List<String> ans) {
        int piecesLeft = 4 - path.size();
        int charsLeft = s.length() - start;

        if (charsLeft < piecesLeft || charsLeft > 3 * piecesLeft) return;

        if (path.size() == 4) {
            if (start == s.length()) ans.add(String.join(".", path));
            return;
        }

        int value = 0;
        for (int end = start; end < s.length() && end < start + 3; end++) {
            if (end > start && s.charAt(start) == '0') break;

            value = value * 10 + (s.charAt(end) - '0');
            if (value > 255) break;

            path.add(s.substring(start, end + 1));
            dfs(s, end + 1, path, ans);
            path.remove(path.size() - 1);
        }
    }
}
```

**Why `break` is safe here:** For a fixed starting position, appending additional decimal digits cannot make a value above 255 become valid; likewise, a multi-digit component starting with zero is never allowed. This monotonic failure is different from palindrome checking.

**Complexity:** Here the number of pieces is fixed at four and each has length at most three. The search explores a bounded number of states regardless of large `n`, with a quick length check; in practice the valid input length must be 4–12. More generally, when segment count and allowed length are variables, complexity depends on both.

## 11. Mistake library

| Mistake | Why it happens | How to detect | Prevention |
|---|---|---|---|
| `dfs(end)` instead of `dfs(end+1)` | Confuse inclusive vs. exclusive end | Same char reconsidered or no progress | Define next **unconsumed** index |
| Treating segmentation as combinations | Both use a for-loop | Selected pieces fail to cover input | Assert prefix-coverage invariant |
| Saving `path` itself | Shared mutable list reference | Saved answers mutate or all become empty | Save `new ArrayList<>(path)` |
| Missing undo | Branch state leaks | Unexpected extra segments | Pair every choose with restore |
| `break` on failed palindrome | Assume invalidity monotone with length | Miss `"aba"` after `"ab"` | Use `continue` unless proved otherwise |
| Accepting before consuming all input | Confuse local segment validity with global completion | Incomplete answers | Require `start == n` and any count constraints |
| Passing only `start` for global uniqueness | Forget path-dependent legality | Incorrect cached result | Include necessary state, or avoid unsafe memoization |
| Overcounting memory | Confuse output storage with DFS stack | Misreported space | Separate auxiliary and output space |
| Off-by-one substring | Java substring end is exclusive | Missing/extra character | `substring(start,end+1)` |
| Blindly assuming O(2^n) total time | Ignore palindrome checks, substring and output copies | Complexity too optimistic | Count work per state and cost to materialize answers |

## 12. Interview follow-ups — what breaks?

1. **Only one valid segmentation needed?** Switch return contract to `boolean`; stop early and consider memoizing `start` if future legality depends only on suffix.
2. **Count segmentations rather than listing them?** Sum counts of legal next segments; cache states if overlapping.
3. **Exactly `k` parts?** Add part count to state and prune impossible remaining lengths.
4. **Segments must be unique?** Add a path-specific `HashSet`; undo membership after recursion.
5. **Very large strings?** Enumeration may be impossible due to output size; ask for counts/feasibility or a bounded sample.
6. **Minimum cuts?** Explore DP on prefix/suffix states, not exhaustive answer materialization.
7. **Segment checks expensive?** Precompute valid intervals or use incremental checks if available.
8. **Input updated frequently?** Static O(n²) validity tables may be unsuitable; reconsider preprocessing strategy.
9. **Return cut positions instead of substrings?** Store segment intervals `(start,end)` and materialize only when needed.
10. **Maximum segment length `L`?** Bound `end < start + L` to reduce branching.

## 13. Unseen-problem recognition framework (30–90 seconds)

```text
1. Do I have to cover the whole input, in original order?
2. Are the outputs consecutive pieces rather than selected elements?
3. Is the next decision a segment endpoint?
4. What makes one segment legal?
5. Does that legality depend only on the segment, or on earlier pieces?
6. Can I safely reject an individual segment now?
7. Can I safely stop checking longer segments, or only skip this one?
8. Do I need all solutions, one, a count, or an optimum?
9. What exactly does dfs(start, extraState) promise?
10. What is the bound on branches, depth, checking, and output size?
```

### Decision tree

```text
Must every input element appear exactly once and in order?
├── No → check Include–Exclude / Combinations / Permutations
└── Yes
    ├── Is it divided into consecutive segments?
    │   ├── No → another representation or graph/state-search problem
    │   └── Yes
    │       ├── Need all valid partitions? → backtracking over end positions
    │       ├── Need one / feasibility? → boolean DFS, often memoize
    │       ├── Need count? → count recurrence, often DP
    │       └── Need minimum / maximum? → optimization, often DP
    └── Validate that segments are nonempty and progress is guaranteed
```
