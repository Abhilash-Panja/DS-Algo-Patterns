## 1. Practical one-line definition

> **Permutation backtracking:** Build an *ordered arrangement* by filling one position at a time with an eligible candidate while maintaining the invariant that each available input occurrence is used at most once.

**Capability:** Enumerate, find, or count order-sensitive arrangements under uniqueness and placement constraints.

A problem is not automatically a permutation problem because it says “rearrange.” Ask whether each **position** matters and whether a candidate is consumed when selected.

---

## 2. Why the pattern exists — from brute force to state

**Example:** Arrange three distinct people A, B, C into three numbered chairs.

At chair 1, there are 3 choices; after selecting A, there are 2 choices for chair 2; finally one remains.

```text
Chair 1:     A                    B                    C
             / \                  / \                  / \
Chair 2:    B   C                A   C                A   B
            |   |                |   |                |   |
Chair 3:    C   B                C   A                B   A

Answers:   ABC ACB              BAC BCA              CAB CBA
```

**Naive possibility:** Generate length-3 strings by choosing any of 3 items at each position: `3^3 = 27` candidates, then reject repeated elements. This wastes work.

**Observation:** After choosing one item, it is unavailable for remaining positions. Track that fact *during* construction.

```text
Generate every length-n sequence
            ↓
Most sequences repeat items illegally
            ↓
Track used occurrences during construction
            ↓
Only branch to currently unused candidates
            ↓
Every root-to-leaf path becomes one valid arrangement
```

For `n` distinct elements, the number of complete permutations is `n!`. If all must be returned, there is an unavoidable `Ω(n · n!)` output cost when each answer has length `n`.

## 3. Recognition signals: questions, not keywords

1. **Does changing the order change the answer?** `[1,2]` and `[2,1]` must count as different outcomes for a permutation.
2. **Are we filling labeled slots, times, ranks, chairs, or positions?** The `level` is naturally the next slot.
3. **Can a selected candidate appear again?** If not, maintain the remaining/used occurrences.
4. **Does each partial placement affect validity?** If yes, add pruning before recursion (e.g., adjacency or divisibility restrictions).
5. **Are duplicate *values* present?** Distinguish input indices from indistinguishable output values.
6. **Is the task only to find the next or K-th permutation?** Generation may be unnecessary; look for lexicographic successor or branch-counting structure.

**Trigger vocabulary:** arrangement, order, schedule, seat, sequence, assign positions, unique permutation, first/last position.

**Disguised case:** “Find the number of ways to assign unique badges to workers, where badge `x` can be used in a certain position only if a rule holds.” This is position-filling search even if the statement never says “permutation.”

## 4. The invariant and the recursive contract

Define `dfs(path, used)`:

> On entry, `path` is a valid prefix, `used[i]` is `true` **if and only if** input occurrence `i` is already in that prefix, and the function explores all valid completions of precisely that prefix.

**Progress:** `path.size()` grows by one on each descending call; reaching `n` is the base case.

**Branch responsibility:** At depth `d`, try each candidate occurrence with `used[i] == false` exactly once (subject to constraints).

**Restoration:** After exploring a branch, both `path` and `used[]` must equal their values *before choosing that candidate*.

**Correctness, in four statements:**

1. **No invalid repetition:** Marked occurrences cannot be selected again.
2. **Completeness:** Every valid arrangement has some first element; the loop visits it and inductively visits its remaining valid suffix.
3. **Uniqueness for distinct inputs:** Two different root-to-leaf choice sequences differ in at least one position and thus produce different permutations.
4. **Termination:** The number of unfilled positions decreases to zero.

The invariant is more important than the particular Java container.

## 5. Deep worked example — LC 46 Permutations (no solution first)

**Problem:** Given an array of distinct integers, return all arrangements containing each element exactly once.  
Link: https://leetcode.com/problems/permutations/  
Difficulty: Medium.

### Step 1 — Strip the story

- **Input:** `n` distinct integers.
- **Output:** All length-`n` sequences using every input element once.
- **Objective:** Enumerate all order-sensitive completions.
- **Order requirement:** Output list order may be arbitrary; arrangement order itself matters.

### Step 2 — Brute force

Choose any of the `n` elements for every one of `n` slots, then verify uniqueness at the leaf. This considers `n^n` candidate sequences before filtering.

### Step 3 — Identify the bottleneck

We repeatedly construct prefixes containing duplicate occurrences although they can never be repaired into valid permutations.

**Question:** What information would let us reject such a choice *before making it*?

### Step 4 — Structural observation

After placing element `nums[i]` in one position, that input occurrence cannot be used again. So keep a boolean flag per occurrence. Each recursive level fills exactly one next position.

### Step 5 — Name the pattern

This is **position-by-position permutation backtracking** with a `used[]` set of consumed input occurrences.

### Step 6 — Invariant

At depth `d`, `path` contains exactly `d` distinct input occurrences, and the `used[]` flags mark exactly those occurrences.

### Step 7 — Dry run: `[1,2,3]`

| Enter/choice | `path` | `used` (1,2,3) | Action |
|---|---|---|---|
| Start | `[]` | `F F F` | Fill position 0 |
| Choose 1 | `[1]` | `T F F` | Fill position 1 |
| Choose 2 | `[1,2]` | `T T F` | Fill position 2 |
| Choose 3 | `[1,2,3]` | `T T T` | Copy result |
| Undo 3 | `[1,2]` | `T T F` | No other unused choice here |
| Undo 2 | `[1]` | `T F F` | Try 3 instead |
| Choose 3 → 2 | `[1,3,2]` | `T T T` | Copy result |
| Undo to root | `[]` | `F F F` | Try first element 2, then 3 |

Outputs in this loop order: `123, 132, 213, 231, 312, 321`.

### Step 8 — Java implementation

```java
import java.util.*;

class Solution {
    public List<List<Integer>> permute(int[] nums) {
        List<List<Integer>> result = new ArrayList<>();
        boolean[] used = new boolean[nums.length];
        dfs(nums, used, new ArrayList<>(), result);
        return result;
    }

    private void dfs(int[] nums, boolean[] used,
                     List<Integer> path, List<List<Integer>> result) {
        if (path.size() == nums.length) {
            result.add(new ArrayList<>(path)); // snapshot, not alias
            return;
        }

        for (int i = 0; i < nums.length; i++) {
            if (used[i]) continue;

            used[i] = true;             // choose occurrence i
            path.add(nums[i]);
            dfs(nums, used, path, result); // explore
            path.remove(path.size() - 1); // restore exact parent state
            used[i] = false;
        }
    }
}
```

**Why the data structures?** `used[]` gives `O(1)` checking by index, including when values are large or negative. `path` stores the ordered prefix; `result` stores independent snapshots. A `HashSet<Integer>` tracks values rather than occurrences and is wrong when equal input values must remain distinct occurrences during generation.

### Step 9 — Complexity, with the counting behind it

- Search-tree nodes (distinct elements): `Σ_{d=0}^n n!/(n-d)! = Θ(n!)`.
- At each non-leaf node we scan up to `n` candidates, contributing `O(n · n!)` loop work overall.
- There are `n!` outputs and copying each length-`n` path adds `Θ(n · n!)` work.
- **Time:** `Θ(n · n!)`.
- **Auxiliary space excluding saved outputs:** `O(n)` for the recursion stack, flags, and path (each of linear size).
- **Output space:** `Θ(n · n!)`.

### Step 10 — Interview explanation (60–90 seconds)

> I construct the permutation one position at a time. At each position, I can choose any input occurrence that hasn't been used. I maintain a `used` boolean array and a `path` storing the ordered prefix. The invariant is that `path` contains exactly the marked occurrences, each once. Once the path has length `n`, I copy it into the result. After exploring each choice, I pop it and unmark the corresponding occurrence so sibling branches see the original state. This explores all `n!` possible orders. Including path copying, time is `O(n · n!)`; auxiliary space is `O(n)` excluding output.

## 6. Code fingerprints and reusable Java templates

### Fingerprint A — Used-state enumeration

```java
for (int i = 0; i < n; i++) {
    if (used[i]) continue;
    used[i] = true;
    path.add(nums[i]);
    dfs(...);
    path.remove(path.size() - 1);
    used[i] = false;
}
```

**Recognition:** “Choose the next unused occurrence for the next position.” Compare this with combination code `for (int i = start; ...) { dfs(i + 1); }`.

### Fingerprint B — In-place swap representation

```java
void dfs(int pos, int[] a, List<List<Integer>> result) {
    if (pos == a.length) {
        List<Integer> snapshot = new ArrayList<>();
        for (int value : a) snapshot.add(value);
        result.add(snapshot);
        return;
    }
    for (int i = pos; i < a.length; i++) {
        swap(a, pos, i);        // fix one element at pos
        dfs(pos + 1, a, result);
        swap(a, pos, i);        // restore original suffix
    }
}

void swap(int[] a, int i, int j) {
    int temp = a[i];
    a[i] = a[j];
    a[j] = temp;
}
```

**Invariant:** Positions `[0, pos)` are fixed, and positions `[pos, n)` contain exactly the remaining occurrences. No separate `used[]` is needed. Unlike `used[]`, this physically reorders the input during recursion; the second swap is essential. Beware: traversal of swap-based DFS is **not necessarily lexicographic**, even if the input is sorted.

### Template decision

| Requirement | Prefer | Why |
|---|---|---|
| Readable constraints per chosen value | `used[] + path` | Explicit position and value |
| Modify arrangement in place | `swap` | Prefix/suffix representation |
| Return only count under constraints | `used[]` or bitmask | No result copying required |
| Need sorted lexicographic enumeration | Sorted input + `used[]` and ordered loop | Prefix choices visited in ascending order |
| Many duplicate values | Frequency map/array | Choose distinct values with positive remaining count |

## 7. Variation — duplicates and UNIQUE permutations (LC 47)

### The trap

Input `[1,1,2]` has `3! = 6` permutations of *labeled occurrences* (`1a,1b,2`), but only `3!/2! = 3` **distinct value sequences**: `112, 121, 211`.

If you use ordinary `used[]`, it generates duplicates by swapping which identical `1` occurrence was selected first. Deduplicating results at the end works but wastes time and memory.

### Derive a canonical choice

Sort values. If two identical unused occurrences could both be picked as the next element, designate the **earlier unused duplicate** as the only legal representative. That avoids duplicate branches while still permitting both copies later within one path.

The check is:

```java
if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;
```

**Interpretation:** Do not choose occurrence `i` of a repeated value while its immediately preceding equal occurrence remains unused. If the previous copy *is already used on the current path*, using the next copy is allowed.

### Deep mini dry run: `[1a,1b,2]`

- At root: `1a` allowed, `1b` skipped because `1a` unused, `2` allowed.
- After choosing `1a`: `1b` allowed because `1a` is already used.
- This generates `112`, `121`, `211` once each.

```java
import java.util.*;

class Solution {
    public List<List<Integer>> permuteUnique(int[] nums) {
        Arrays.sort(nums);
        List<List<Integer>> result = new ArrayList<>();
        dfs(nums, new boolean[nums.length], new ArrayList<>(), result);
        return result;
    }

    private void dfs(int[] nums, boolean[] used,
                     List<Integer> path, List<List<Integer>> result) {
        if (path.size() == nums.length) {
            result.add(new ArrayList<>(path));
            return;
        }
        for (int i = 0; i < nums.length; i++) {
            if (used[i]) continue;
            if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;

            used[i] = true;
            path.add(nums[i]);
            dfs(nums, used, path, result);
            path.remove(path.size() - 1);
            used[i] = false;
        }
    }
}
```

**Important contrast with Combination Sum II:** Both often sort and skip duplicate choices, but the logical rules differ:

- Combinations: `if (i > start && a[i] == a[i-1]) continue;` — the index range identifies **same-depth siblings**.
- Permutations: `if (i > 0 && a[i] == a[i-1] && !used[i-1]) continue;` — whether a previous equal occurrence was *used in the current prefix* matters.

For multiset counts `c1,c2,...,cm`, the number of distinct permutations is `n!/(c1! c2! ... cm!)`. Printing every unique permutation costs `Ω(n · U)` where `U` is the distinct permutation count. The code above additionally scans `n` candidates per visited node, so `O(n · n!)` is a safe general worst-case bound; do not casually claim its runtime is always exactly `O(n · U)` without analyzing candidate scans.

### Alternative: choose by remaining frequency

If values are repeated heavily, a `TreeMap<Integer,Integer>` or sorted distinct-value array plus counts can represent each distinct next value once. This makes the invariant **remaining frequency for each value**. A `TreeMap` also permits predictable ascending choices (although mutation overhead differs). Use when value counts are more natural than labeled occurrences.

## 8. Variation — count VALID arrangements (Beautiful Arrangement, LC 526)

Problem: Place values `1..n` in positions `1..n`. At one-based position `pos`, a chosen value `x` is allowed only if `x % pos == 0 || pos % x == 0`.

Link: https://leetcode.com/problems/beautiful-arrangement/ (Medium).

```java
class Solution {
    public int countArrangement(int n) {
        return dfs(1, n, new boolean[n + 1]);
    }

    private int dfs(int pos, int n, boolean[] used) {
        if (pos > n) return 1; // one complete valid arrangement
        int count = 0;
        for (int x = 1; x <= n; x++) {
            if (used[x]) continue;
            if (x % pos != 0 && pos % x != 0) continue;
            used[x] = true;
            count += dfs(pos + 1, n, used);
            used[x] = false;
        }
        return count;
    }
}
```

**Invariant:** All filled positions satisfy the divisibility rule, with no reused number. `dfs(pos)` returns the number of valid ways to complete the remaining positions for the *current* `used` state.

**No output list:** The task asks for a count, so base case returns `1`, and sibling counts are added.

**Optimization boundary:** The state can be encoded as an `n`-bit mask. If a subproblem's result depends only on the mask (and `pos`, which equals `bitcount(mask)+1`), memoization yields approximately `O(n · 2^n)` time with `O(2^n)` memo space, moving toward bitmask DP. Do not add memoization to an enumerator that must print every arrangement and expect the output cost to vanish.

## 9. Relation to your K-th permutation notes: COUNT then SKIP

Your handwritten pages 16–18 notice that permutations are grouped by the first selected value when the generation order is lexicographic. For `n` **distinct** available values, each choice of the first position gives `(n-1)!` completions.

Example, sorted numbers `[1,2,3,4]`:

```text
First 1: 6 permutations (ranks 1–6)
First 2: 6 permutations (ranks 7–12)
First 3: 6 permutations (ranks 13–18)
First 4: 6 permutations (ranks 19–24)
```

Rank `k=17` falls in the `3` block. After skipping `12` permutations, the local one-based rank is `5` among `[1,2,4]`. The next block has size `2! = 2`, and local rank 5 falls in the `4` block. Continue likewise to obtain `3412`.

**Check:** Lexicographic order of permutations starting with `3` is `3124 (13), 3142 (14), 3214 (15), 3241 (16), 3412 (17), 3421 (18)`.

For **one-based** `k` use zero-based `rank = k-1`:

```text
blockSize = (remaining-1)!
selectedIndex = rank / blockSize
rank = rank % blockSize
remove selected available number
```

This is **Pattern 02 (structural branch skipping)** composed with permutation structure. Don't solve an ordinary *generate all permutations* task this way; its output necessarily remains factorial.

**Important preconditions:** input distinct, candidates lexicographically ordered, `k` valid, factorial arithmetic fits your numeric type. Duplicates and constrained placements require different branch counts.

## 10. Pattern boundaries — when NOT to use permutation backtracking

| Situation | Better first question or technique |
|---|---|
| Order doesn't matter; `[1,2]` equals `[2,1]` | Combination with `start` / canonical choice order |
| Need all subsequences preserving original input order | Include–Exclude (Pattern 03) |
| Repeat of candidate is allowed without limit | Repetition state / combinations or sequence DP, not `used[]` |
| Only next lexicographic permutation required | In-place successor algorithm (`Next Permutation`, LC 31); not exhaustive backtracking |
| Only K-th lexicographic permutation | Factorial counting / rank selection (Pattern 02) |
| Only check if any valid arrangement exists | Boolean search with early termination; avoid collecting all paths |
| Need count of feasible assignments for larger `n` | Mask DP, matching, or specialized methods may be required |

**Permutation vs. combination vs. subset**

| Question | Include–Exclude | Combinations | Permutations |
|---|---|---|---|
| Main choice | Take/skip index | Choose next eligible item | Fill next *position* |
| State | `index`, optional `path` | `start`, `path` | `used[]`, `path` or permuted suffix |
| Does order matter? | Input subsequence order is fixed | No | Yes |
| Can pick earlier unused index after later one? | Not applicable | Usually no | Yes |
| Typical DFS fingerprint | Two fixed branches | `for (i=start; ...)` | `for (i=0; i<n; ...)` with `used[]` |
| Duplicate rule | Depends on output definition | Skip same-depth equal candidates | Skip equal occurrence when prior copy unused |

**Permutation generator vs. Next Permutation:** LC 31 asks for just the lexicographic *successor* and requires `O(1)` extra memory. Sorting/DFS to enumerate candidates is unnecessary and violates the spirit of that problem. Its useful insight is finding the rightmost ascent, swapping with an appropriate successor, then reversing the suffix. Study it as a *boundary problem*, not another permutation-backtracking template.

## 11. Mistake library — mistake → detection → prevention

### Recognition mistakes

1. **Used `start` in an ordered-arrangement problem.** You only produce increasing-index orders. **Detect:** Does `[2,1]` need to appear? **Prevent:** Use `used[]` or swapping.
2. **Used permutation search for K-th permutation.** Factorial generation becomes infeasible. **Detect:** Single requested rank and ordered blocks. **Prevent:** Count and skip branches if justified.
3. **Assumed a task needs *all* solutions when it only needs existence.** **Detect:** Output is `boolean`. **Prevent:** Return early on first successful leaf.

### Reasoning mistakes

4. **Cannot explain what `used[i]` means.** It marks an input *occurrence*, not a value. **Detect:** Input `[1,1,2]`. **Prevent:** State the invariant explicitly.
5. **Assumed sorted input makes swap DFS lexicographic.** Physical swaps can reorder later suffix candidates. **Detect:** Trace length 3–4. **Prevent:** Use sorted `used[]` DFS for predictable lexicographic output.
6. **Pruned because current partial sum exceeds target when negative future numbers exist.** **Detect:** Can remaining choices reduce the sum? **Prevent:** Prove any bound before pruning.

### Implementation mistakes

7. **Forgot `used[i]=false` or second swap.** Subsequent branches see contaminated state. **Detect:** Print the state before and after every recursive call. **Prevent:** Treat choose/undo as a paired transaction.
8. **Appended `path` directly into results.** All answers reference the same mutable list. **Prevent:** `new ArrayList<>(path)`.
9. **Applied duplicate check without sorting first.** Equal values may be separated. **Prevent:** Sort before adjacent-equality duplicate rule.
10. **Used `used[i-1]` instead of `!used[i-1]` in LC 47.** Rejects legitimate reuse of the next equal occurrence in one path. **Prevent:** Explain `1a` then `1b` verbally.
11. **Mixed zero-based and one-based indexing.** Fatal for position constraints and K-th ranks. **Prevent:** Write index convention next to contract.
12. **Returned a count at leaf but forgot to add child counts.** **Prevent:** `count += dfs(nextPosition)` when counting.

### Complexity mistakes

13. **Said `O(n!)` to return all permutations.** Copying length-`n` outputs costs `Θ(n · n!)`. **Prevent:** Count output materialization.
14. **Said auxiliary space is `O(n · n!)`.** That's total *output* storage, not working state. **Prevent:** Report both separately.
15. **Assumed duplicates always reduce runtime to `O(n·U)` with `used[]`.** Even skipped branches require iteration and checks. **Prevent:** Count state visits and loop scans.

### Interview mistakes

16. **Started coding before clarifying duplicates/order.** **Prevent:** Ask “Are values distinct? Is order significant? Generate/count/find? Any positional constraints?”
17. **Couldn't justify restoration.** **Prevent:** Say “After a child finishes, every sibling must receive the identical parent state.”

## 13. Interview follow-ups: what state or invariant breaks?

| Follow-up | What changes? | Likely adaptation |
|---|---|---|
| Values repeat | Occurrence order produces duplicate value sequences | Sorted skip rule or frequency counts |
| Return only a count | Don't store `path` snapshots | Integer count; perhaps bitmask DP |
| Return first valid arrangement | Enumerating every leaf wastes time | Boolean DFS and early return |
| Certain values forbidden in positions | Not every unused candidate is valid | `isAllowed(pos, value)` before choosing |
| Adjacent values must satisfy a rule | Legality depends on preceding value | Check `path.get(path.size()-1)` |
| Need lexicographic output | Traversal order becomes part of contract | Sort candidates; used-state DFS or frequency map |
| Need K-th in sorted order | Generating earlier leaves is wasteful | Branch sizes, rank adjustment; Pattern 02 |
| Need next permutation only | Full generation unnecessary | In-place lexicographic successor |
| `n` is too large to enumerate all | Factorial output cannot fit | Change task to count/find; use constraints, DP or combinatorics |
| Streaming solutions | Can't hold all outputs | Consumer/callback pattern, but total work persists |

## 14. Approach an unseen arrangement problem in 30–90 seconds

Ask **before coding**:

1. What's the objective: **generate, count, find one, optimize, next, or K-th**?
2. Are different **orders** of the same chosen elements different answers?
3. Am I choosing *which elements* or assigning *which element goes in the next position*?
4. Can each input occurrence be used once, reused, or not used at all?
5. Are duplicates present, and is output uniqueness defined by **value** or **occurrence**?
6. Which constraints can be checked for a *partial* arrangement?
7. What is the minimal state: `pos`, `used[]`, previous value, counts, sum, etc.?
8. Define the invariant: exactly which elements/occurrences have been fixed?
9. Does restoring the state after each trial keep siblings independent?
10. Can the task be solved without enumeration (counting blocks, lexicographic successor, DP)?

**One-minute decision tree**

```text
Does output depend on order?
├── No → Combination / subset family (Patterns 03–04)
└── Yes
    ├── Only NEXT lexicographic arrangement? → Next-permutation algorithm
    ├── Only K-TH lexicographic arrangement? → Branch-count skipping (Pattern 02)
    └── Need search over actual arrangements
        ├── All distinct occurrences? → used[] or swap DFS
        ├── Repeated values; unique outputs? → sorted used[] / frequency DFS
        └── Position/adjacency restrictions? → add partial feasibility check
            ├── Count only? → increment/return counts, consider mask DP
            └── Find one/all? → stop early / record each complete path
```

## 20. Compact review card

```text
NEED ORDER?           → Yes: consider arrangement search
LEVEL                 → Next position
CHOICES               → All unused occurrences
STATE                 → path + used[]  OR  fixed prefix + remaining suffix
INVARIANT             → Every filled position uses one eligible occurrence
CORE                  → choose → recurse → undo
DUPLICATES            → Sort; skip equal value if previous equal occurrence unused
COUNT ONLY            → Return 1 at valid leaf; sum child counts
K-TH ONLY             → Count/skip blocks, when branch sizes provable
NEXT ONLY             → Lexicographic successor, not DFS
TIME (ALL DISTINCT)   → Θ(n · n!) including output
EXTRA SPACE           → O(n) excluding results
```

**Final takeaway:** A combination asks *which elements belong together?* A permutation asks *which unused element belongs in this next position?* Once the function contract and invariant are clear, `used[]`, swapping, duplicate rules, and pruning follow naturally.
