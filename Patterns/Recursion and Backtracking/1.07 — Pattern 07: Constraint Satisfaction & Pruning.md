## 0. Where this fits in your handwritten notes

Your handwritten **N-Queens** work (approximately pages 4–7) begins with placing queens and checking rows, columns and diagonals. Your **Cryptarithmetic** work (approximately pages 9–12) separates a **generator** (candidate digit assignments) from a **checker** (whether an equation is satisfied). These are excellent starting observations. This chapter turns them into one reusable design method without treating N-Queens and cryptarithmetic as separate algorithms.

**What you already know:** model choices, apply validity tests, construct a solution recursively, and identify why exhaustive candidates can be expensive.  
**What this chapter adds:** choose a good variable ordering; distinguish *local* checks from checks involving future assignments; formalize a safe prune; maintain O(1) constraint state; and exploit carries/propagation rather than checking only complete assignments.

**Technical correction:** “If a partial answer fails a check, stop” is valid **only** if the failed condition cannot be repaired by any future assignment. A partial arithmetic sum not yet equal to the target is *not* proof that the branch is impossible.

## 1. Practical one-line definition

> **Constraint-satisfaction backtracking incrementally assigns values to variables, maintains the conditions that every partial assignment must obey, and abandons a branch the moment no completion can be valid.**

The goal is not simply to recurse over all possibilities. It is to make the search tree as small as correctness allows.

```text
All complete assignments
       ↓
Most violate constraints
       ↓
Can we detect violations while assignments are still partial?
       ↓
Choose → check → recurse → undo
       ↓
Visit only feasible prefixes
```

### Capability this gives you

Instead of generating an enormous collection and filtering at the end, you can **build valid configurations directly**, reusing compact state to check whether the next move is legal.

### Typical applications

- Place objects on a board while avoiding conflicts.
- Assign unique values subject to relationships.
- Fill rows/cells under structural rules.
- Count valid configurations without storing them.
- Return the first valid configuration, all configurations, or their count.

**Do not decide from trigger words alone.** A problem containing “arrange,” “unique,” or “valid” might also admit greedy, matching, bitmask DP, SAT, or mathematical counting.

## 2. Derive the technique from brute force

### Step A — Generator and checker (from your cryptarithmetic notes)

Imagine `d` distinct letters must receive distinct digits. A straightforward approach is:

```text
generate complete digit assignment
              ↓
check uniqueness, leading zero, equation
              ↓
accept or reject
```

Ignoring leading-zero restrictions, there are `10! / (10-d)!` assignments for `0 ≤ d ≤ 10`. Checking only at the end wastes work when a conflict becomes apparent much earlier.

### Step B — Enforce constraints incrementally

Suppose the first two letters have received the same digit. If uniqueness is mandatory, **no later assignment can fix that**. Immediately reject the branch.

```text
assign next variable
       ↓
check conditions already determined by assigned variables
       ├─ impossible → undo / try next candidate
       └─ feasible → assign another variable
```

### Step C — Maintain fast bookkeeping

Checking each new queen against all earlier queens repeatedly costs time. Instead, maintain occupied columns/diagonals in boolean arrays or sets so that each placement can be tested in O(1).

### Step D — Formalize the proof obligation

Before pruning state `S`, show:

> There is **no complete solution extending S**.

This is stronger than “S does not yet satisfy the final objective.” A prefix may be incomplete and still feasible.

## 4. LCCM refined for constraints

Your LCCM model maps naturally:

| LCCM | Constraint-search meaning | N-Queens example | Cryptarithmetic example |
|---|---|---|---|
| **Level** | Which variable to assign now | Row | Letter or digit column |
| **Choice** | Candidate value | Column `c` | Digit `d` |
| **Check** | Can the partial assignment still extend to a solution? | No occupied column/diagonal | Unique digit, nonzero leading letter, carry consistency |
| **Move** | Apply → recurse → undo | Mark/unmark attacks | Assign/unassign digit and used flag |

### Central invariant

> **At entry to each recursive call, every variable before the current level has exactly one assignment, and all constraints involving only those assigned variables are satisfied.**

Additionally, all bookkeeping must describe those assignments exactly.

**Separate two kinds of state:**

- **Path/assignment state:** which variables currently have what values.
- **Constraint state:** which values/columns/diagonals are unavailable and any derived information (e.g., carry).

Both must agree before and after each branch.

## 5. Generic Java skeleton

```java
void dfs(int level) {
    if (level == totalVariables) {
        recordCompleteValidAssignment();
        return;
    }

    int variable = chooseVariable(level);
    for (int value : availableCandidates(variable)) {
        if (!canExtend(variable, value)) continue;

        assign(variable, value);      // choose + update constraints
        dfs(level + 1);               // explore
        unassign(variable, value);    // restore *all* changed state
    }
}
```

This is a **conceptual skeleton**, not compilable Java: the placeholder methods depend on the problem.

### Code fingerprint

```java
if (!isSafe(choice)) continue;
mark(choice);
dfs(next);
unmark(choice);
```

If you see this shape, you are likely looking at **search over a constraint-constrained partial configuration**.

### Why these data structures?

- **`boolean[]`:** bounded integral domain, constant-time membership, fast undo.
- **`HashSet`:** sparse or unbounded keys, flexible but higher overhead.
- **`int[]` assignment:** position-to-value mapping; use `-1` to represent unassigned when safe.
- **Bitmask:** compact fixed-size domain; useful after the boolean-array invariant is already understood.
- **Board `char[][]`:** useful for producing output, but not necessarily for fast checks.

A sorted array, `TreeSet`, or priority queue is *not* automatically useful: our dominant operation is typically **membership under reversible updates**, not sorted-order retrieval.

## 6. Deep worked example — N-Queens (LeetCode 51)

**Problem:** Put `n` queens on an `n × n` board so none attack each other; return all boards.

Link: https://leetcode.com/problems/n-queens/

### Step 1 — Strip the story

- **Input:** board size `n`.
- **Output:** every legal placement of `n` queens.
- **Constraints:** queens cannot share a row, column, or either diagonal.
- **Mathematical model:** choose one column `c[r]` for each row `r` subject to `c[r1] != c[r2]` and `|r1-r2| != |c[r1]-c[r2]|`.

### Step 2 — Brute force

Try arbitrary selections of `n` cells among `n²` cells, then validate full boards. This creates many states that violate the obvious one-per-row condition.

### Step 3 — Exploit the structure

Since each valid board needs exactly one queen per row, **assign one row per recursion level**. Row conflicts disappear *by construction*.

Now ask: when assigning `(row, col)`, which existing placements could attack it?

1. Same column.
2. Same `row-col` diagonal.
3. Same `row+col` diagonal.

Earlier rows already contain exactly one queen each, so no separate row check is necessary.

### Step 4 — Make diagonals indexable

```text
Column index:              col                in [0, n-1]
Main diagonal identifier:   row - col + n - 1  in [0, 2n-2]
Other diagonal identifier:  row + col          in [0, 2n-2]
```

Use `boolean[n]` for columns and two `boolean[2*n-1]` arrays for diagonals.

### Step 5 — State and invariant

At entry to `place(row)`:

1. Exactly `row` queens occupy rows `0 ... row-1`.
2. No two placed queens attack one another.
3. `columns`, `diagDown`, and `diagUp` **exactly** reflect those queens.
4. `placement[r]` stores the chosen column in each processed row.

A new queen can be added only if all three occupancy checks are false.

### Step 6 — Dry run for `n = 4`

Try rows in order and columns from left to right:

```text
row 0: choose col 0
row 1: col 0 blocked (column), col 1 blocked (diagonal)
       choose col 2
row 2: no legal column → backtrack row 1
row 1: try col 3
row 2: choose col 1
row 3: no legal column → backtrack further
...
row 0: choose col 1
row 1: choose col 3
row 2: choose col 0
row 3: choose col 2
→ valid board [1,3,0,2]
```

That board is:

```text
.Q..
...Q
Q...
..Q.
```

A second solution is `[2,0,3,1]`.

### Step 7 — Clean complete Java solution

```java
import java.util.*;

class Solution {
    public List<List<String>> solveNQueens(int n) {
        List<List<String>> results = new ArrayList<>();
        if (n <= 0) return results;

        boolean[] columns = new boolean[n];
        boolean[] diagDown = new boolean[2 * n - 1];
        boolean[] diagUp = new boolean[2 * n - 1];
        int[] placement = new int[n];

        place(0, n, columns, diagDown, diagUp, placement, results);
        return results;
    }

    private void place(int row, int n, boolean[] columns,
                       boolean[] diagDown, boolean[] diagUp,
                       int[] placement, List<List<String>> results) {
        if (row == n) {
            results.add(toBoard(placement, n));
            return;
        }

        for (int col = 0; col < n; col++) {
            int d1 = row - col + n - 1;
            int d2 = row + col;
            if (columns[col] || diagDown[d1] || diagUp[d2]) {
                continue;
            }

            placement[row] = col;
            columns[col] = true;
            diagDown[d1] = true;
            diagUp[d2] = true;

            place(row + 1, n, columns, diagDown, diagUp,
                  placement, results);

            columns[col] = false;
            diagDown[d1] = false;
            diagUp[d2] = false;
        }
    }

    private List<String> toBoard(int[] placement, int n) {
        List<String> board = new ArrayList<>();
        for (int row = 0; row < n; row++) {
            char[] line = new char[n];
            Arrays.fill(line, '.');
            line[placement[row]] = 'Q';
            board.add(new String(line));
        }
        return board;
    }
}
```

### Step 8 — Why this works (correctness)

- **No invalid output:** each queen is placed only when it attacks none of the previous queens; one queen per row is enforced by the recursion.
- **No missing valid boards:** any valid board has exactly one queen in each row; its column at each row is legal with respect to earlier rows, so the search follows that branch.
- **No duplicate boards:** a full ordered sequence of row-column choices identifies exactly one board and is visited once.
- **Restoration:** the three occupancy markers are cleared after the child returns; a sibling sees exactly the parent's state.

### Step 9 — Complexity

- At most `n!` row-by-row candidate arrangements are explored, with `O(1)` constraint checking per attempted placement.
- A loose time upper bound for enumeration with output construction is `O(n · n! + S · n²)`, where `S` is the number of returned solutions; `n · n!` accounts for candidate checks, while each solution board costs `O(n²)` to materialize. It is common to summarize the search bound as `O(n · n!)`, excluding output costs.
- Auxiliary search state: `O(n)` for recursion, placement, and occupancy arrays, **excluding** collected output.
- Output storage: `O(S · n²)` characters, ignoring representation overhead.

Do not claim the algorithm is polynomial just because a placement check is constant time.

### Step 10 — 60–90 second interview explanation

> I'll place exactly one queen per row, so row conflicts are eliminated by the recursion structure. For each column in the current row, I check whether its column or either diagonal is already occupied. Three boolean arrays give constant-time checks. If the placement is safe, I mark those constraints, recurse to the next row, and undo the marks before trying the next column. At `row == n`, the placement is a valid complete board. This enumerates all legal boards without generating obviously invalid prefixes, though the search is still factorial in the worst-case bound.

## 7. Variation A — Count, don't materialize (LeetCode 52)

Link: https://leetcode.com/problems/n-queens-ii/

If only the count is needed, preserve the same invariant but change the contract:

> `count(row)` returns the number of valid complete boards extending the current legal placement.

```java
private int count(int row, int n, boolean[] col,
                  boolean[] d1, boolean[] d2) {
    if (row == n) return 1;

    int ways = 0;
    for (int c = 0; c < n; c++) {
        int x = row - c + n - 1, y = row + c;
        if (col[c] || d1[x] || d2[y]) continue;

        col[c] = d1[x] = d2[y] = true;
        ways += count(row + 1, n, col, d1, d2);
        col[c] = d1[x] = d2[y] = false;
    }
    return ways;
}
```

Here, `1` at a complete state represents **one valid completion**, not a queen count. Changing the output requirement should change the return contract, not the search invariant.

## 8. Variation B — Sudoku: multiple constraint sets

Link: https://leetcode.com/problems/sudoku-solver/

Variables are empty cells. Domains are digits 1–9. Each placement must satisfy **row, column, and 3×3 box** constraints.

### Natural state

```text
rowUsed[row][digit]
colUsed[col][digit]
boxUsed[(row/3)*3 + col/3][digit]
```

**Important change from N-Queens:** A Sudoku cell may have several candidate digits, and some cells are much more constrained than others. Rather than always choosing the next cell in reading order, an optional heuristic chooses the empty cell with the **fewest currently legal values** (MRV: minimum remaining values). This can fail earlier when a branch is impossible.

### Pruning versus heuristics

- **Pruning:** proves that an assignment or branch cannot be part of a solution.
- **Variable ordering (MRV):** changes which decision is made first; it may improve speed but does *not* by itself prove a branch impossible.
- **Forward checking:** detects when some unassigned variable has an empty legal domain after a move; this provides a valid prune.

These are related but distinct improvements.

## 9. Variation C — Cryptarithmetic: from generator/checker to carry constraints

Reference from your handwritten notes: **generator → checker** and uniqueness of letter-to-digit assignments.

### Problem model

For an alphametic addition such as:

```text
  SEND
+ MORE
------
 MONEY
```

each distinct letter represents one distinct digit; leading letters cannot be zero; the arithmetic equation must hold.

### Baseline strategy

1. Collect distinct letters (`d`).
2. If `d > 10`, there is no solution using distinct decimal digits.
3. Assign unused digits to letters, enforcing leading-zero restrictions.
4. Check the sum at the leaf.

This is valid, but may explore up to `10! / (10-d)!` digit assignments before leading-zero and arithmetic filtering.

### Stronger idea: solve column by column

Addition provides constraints for each column, starting from the units column:

```text
sum(digits of addends in column) + carryIn
    = resultDigit + 10 * carryOut
```

When enough digits in a column are known, the result digit and carry are **forced**; reject any inconsistent assignment immediately.

For two addends, each column has:

```text
x + y + carryIn = z + 10 * carryOut
```

If `x`, `y`, and `carryIn` are known, then `z = (x+y+carryIn) % 10` and `carryOut = (x+y+carryIn)/10`. If `z` belongs to an unassigned letter, it can be assigned (subject to uniqueness and nonzero-leading constraints); otherwise, it must match its existing assigned digit.

### A useful column-wise state

```text
column index
carry in
letter → digit mapping
used digits
```

### Core invariant

> All columns strictly to the right of the current column satisfy the addition equation, and the incoming carry is exactly the carry produced by those solved columns.

### When is pruning safe?

**Safe:** Two distinct letters receive the same digit; a leading letter gets zero; a completed column's result digit/carry is inconsistent.

**Unsafe:** Reject a partially assigned equation because its current numeric total is not yet the target. Unknown letters can still affect that total.

### Key insight from this example

A powerful constraint can come from **mathematical structure**, not only from a `used[]` array. This is the same kind of derivation that made your Euclidean GCD example memorable: use a true property to reduce work.

**Scope note:** A fully optimized, general alphametic solver is an extension exercise. This section establishes the reusable column/carry invariant instead of burying the pattern under problem-specific implementation.

## 10. Choosing a good variable order

Not all variable orders explore the same number of states.

### Fixed natural order

- N-Queens: row 0, row 1, ... (already removes row conflicts).
- Structured arithmetic: rightmost digit column first (carry flows right-to-left).

### Most-constrained-first (MRV)

Choose the variable with the fewest remaining legal candidates. This can surface dead ends sooner in Sudoku and general assignment problems.

**Why it may help:** if one variable has 1 candidate and another has 8, trying the 1-candidate variable first may expose contradiction before exploring many combinations of the other variable.

**Important:** MRV is a *heuristic for order*, not a correctness invariant. The invariant remains that selected assignments are valid and the search still covers every candidate that might complete a solution.

## 11. Why not another pattern?

| Confused with | What is different? | Decision test |
|---|---|---|
| **Combinations (1.04)** | Order is suppressed by `start`; usually selection-focused | Are assignments linked by conflicts between variables? |
| **Permutations (1.05)** | `used[]` enforces uniqueness, but may have no additional feasibility rules | Is validity more than “use each index once”? |
| **Grid path (1.08)** | Decisions move through neighboring locations; visited-state semantics depend on paths | Is adjacency/movement the main structure? |
| **DP** | Solves/reuses subproblem answers, often over overlapping states | Can future outcomes be summarized by a smaller reusable state? |
| **Greedy** | Makes an irreversible locally optimal choice only with proof | Can one locally attractive assignment exclude valid solutions? |
| **Matching/flow** | Specialized polynomial algorithms for certain assignment constraints | Do constraints form a known bipartite assignment/capacity structure? |

**Negative signals:** A problem is not automatically constraint backtracking just because it has multiple conditions or needs a valid result. Seek a structure-specific efficient algorithm when possible.

## 12. Pruning safety audit

| Proposed check | Safe? | Explanation |
|---|---|---|
| Reuse a digit already assigned to another letter | Yes | Violates a permanent uniqueness rule |
| Two N-Queens share a diagonal | Yes | Later queens cannot move earlier queens |
| A completed arithmetic column has wrong carry | Yes | Future columns cannot change that lower column |
| A partial sum is less than a target | **Not automatically** | Later positive choices may increase it |
| A partial sum exceeds target | Depends | Safe if future contributions are all nonnegative and cannot decrease the sum |
| Sudoku empty cell has zero legal candidates | Yes | No completion is possible |
| A branch looks unlikely to succeed | No | Probability is not a correctness proof |

A sound prune is a theorem about *all possible completions* of the current state.

## 14. Mistake library

### Recognition mistakes

| Mistake | Why it happens | Prevent it |
|---|---|---|
| Treat every assignment problem as permutations | Both involve choosing values | Ask what non-uniqueness constraints can be checked incrementally |
| Skip the state definition | Focus on code first | Write `variable`, `domain`, `constraints`, `level` |
| Confuse fixed ordering with required output order | Assumes all orders must be explored | Determine whether different assignment orderings represent the same outcome |

### Reasoning mistakes

| Mistake | Why it happens | Prevent it |
|---|---|---|
| Prune incomplete states simply for not meeting final equality | Final validity confused with partial feasibility | Prove no completion can repair the state |
| Assume MRV changes correctness | Heuristic confused with invariant | Separate branch ordering from completeness |
| Fail to prove coverage | Only happy-path testing | Explain why each valid solution has a unique path through the decisions |

### Implementation mistakes

| Mistake | Consequence | Prevention |
|---|---|---|
| Wrong diagonal index | Out-of-bounds / incorrect conflicts | Use `r-c+n-1`, `r+c`, length `2n-1` |
| Unmark only some occupied state | Later branches falsely rejected | Apply/undo exactly the same components |
| Store mutable board reference without copying | Results change after backtracking | Deep-copy each completed representation |
| Forget leading-zero restriction | Invalid alphametic assignments accepted | Track leading letters explicitly |
| Count `row == n` as 0 | Under-counts solutions | Return `1` for one completed valid assignment |

### Complexity mistakes

- `O(1)` is the **cost of a check**, not the total search.
- Pruning reduces practical nodes visited but may not improve a simple worst-case factorial/exponential bound.
- Enumeration time includes the cost of constructing/copying each answer.
- A recursive boolean-array solution still consumes `O(depth)` stack space.

### Interview mistakes

- Starting with diagonal formulas without explaining why one queen per row is sufficient.
- Giving a heuristic as if it proves correctness.
- Missing the contract distinction: find one vs count vs enumerate all.
- Claiming “we skip because it is invalid” without identifying the permanent violated constraint.

## 15. Interview follow-ups: what breaks?

| Modification | Broken assumption | Adaptation |
|---|---|---|
| Return only one board | Need to visit every solution | Use `boolean` early termination and preserve cleanup |
| Count only | Board serialization needed | Replace collection with count-returning contract |
| Blocked cells on board | All columns available for a row | Skip blocked candidates before occupancy test |
| Pre-placed queens | All rows initially empty | Validate initial placements and seed occupancy state |
| `n` increases | Boolean search can still be large | Consider symmetry, bitmasks, stronger pruning; evaluate constraints |
| Sudoku has many empty cells | Fixed order may be inefficient | Try MRV and forward checking |
| Values can repeat | Unique-value assumption disappears | Update used-state semantics, do not apply old duplicate restrictions blindly |
| Constraint depends on future choices | Immediate failure check unsafe | Derive bounds or defer until sufficiently assigned |
| Stream one answer at a time | Keeping all outputs expensive | Use callback/iterator-like consumption where feasible |

### Test A — Conference room assignments

### Test B — Colored exhibition layout

### Test C — Four equal crates

### Test D — Hidden-digit addition

### Test E — Board with blocked squares
