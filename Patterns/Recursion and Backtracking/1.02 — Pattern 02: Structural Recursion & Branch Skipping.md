# 1.02 — Pattern 02: Structural Recursion & Branch Skipping

> **Pattern family:** Locate a requested result inside a recursively structured sequence **without constructing all preceding results**.
>
> **Core invariant:** At every step, the retained subproblem contains the requested rank, and the rank is interpreted relative to that subproblem.

**Prerequisite:** [1.01 Recursive Decomposition & Return-Value Reasoning](./1.01%20Recursive%20Decomposition%20%26%20Return-Value%20Reasoning.md) — especially recursive contracts, return values, mathematical invariants, and GCD's *prove reduction first* philosophy.

**Handwritten-notes connections:** pp. 13–15 (K-th Tower of Hanoi move and its recurrence), pp. 16–18 (lexicographic K-th permutation, grouping by first element), pp. 19–22 (K-th Symbol in Grammar, doubling lengths, tracking halves and child relationships). Your notes repeatedly ask: *If only the K-th answer is needed, why generate everything before it?* That observation drives this chapter. Some details below are mathematical corrections and expansions rather than claims made in the handwriting.

---

## 1. What this pattern actually is

> I am asked for a particular position in a huge, ordered, recursively generated sequence. I can determine which branch contains that position, then recurse **only into that branch**, adjusting the position when needed.

This is more specific than “use recursion.” We need **structure plus a way to locate the requested position**.

```text
Naive: generate results 1, 2, 3, ... K → retrieve K-th
                         ↓
Bottleneck: constructing answers we will discard
                         ↓
Observation: results are grouped by recursive structure
                         ↓
Find: parent relationship, branch lengths, or block counts
                         ↓
Skip whole irrelevant groups; recurse into one group
```

**Capabilities:**
- Directly retrieve one element from an exponentially/factorially large implicit sequence.
- Compute an indexed move, symbol, or permutation without materializing its predecessors.
- Convert an index `k` into *the state of the relevant recursive branch*.

**Not a universal K-th trick:** This requires a **defined order** and **proven branch structure/counts**. Having `k` in a problem does not imply it works.

---

## 2. The three mechanisms — keep them distinct

| Mechanism | Why skipping is possible | Where your notes use it | Example |
|---|---|---|---|
| **Parent/child reduction** | Each output position has a small, known parent state | Grammar, pp. 19–22 | `parentIndex = (k + 1)/2` (1-based) |
| **Recursive section lengths** | A recursive output splits into known-length sections and a middle event | Hanoi, pp. 13–15 | left: `2^(n-1)-1`, middle: `2^(n-1)` |
| **Combinatorial block counts** | Every fixed prefix has a count of completions | Permutations, pp. 16–18 | `(n-1)!` permutations per first element |

All three share **preserve the correct requested position** but not the same formula or code template.

### State contract for indexed recursion

`locate(problemState, k)` returns the **k-th result of the ordered output generated by `problemState`**.

Specify up front:
1. What the sequence contains and in what order.
2. Whether `k` is **1-based or 0-based**.
3. How many results each part produces (or how child indices map to parents).
4. How `k` changes after skipping a prefix.
5. What base case returns a direct answer.

---

## 3. Recognition signals and disguised versions

Before deciding on this pattern ask:

1. **Only one rank?** Do I need the K-th item rather than the entire list?
2. **Enormous conceptual output?** Is explicit generation much more expensive than computing one result?
3. **Structured ordering?** Are items produced in a precise recursive or lexicographic order?
4. **Branch sizes known or computable cheaply?** Can I prove how many items a subtree contributes?
5. **A smaller indexed problem?** After skipping a group, can I translate `k` into that group's local index?
6. **Dependencies on earlier outputs?** Does the K-th item actually require knowing all prior elements, or is the dependency structural?

**Trigger language:** “K-th move,” “symbol at position K,” “K-th permutation,” “indexed generated string,” “find a character after many transformations.”

**Disguise:** A virtual printer would output an impossibly long file, but a monitor asks for the character at one address. The problem may not say “K-th” or “recursion”; the crucial property is that an address can be mapped into a recursively described block.

---

## 4. Why a naive generator fails

Consider all permutations of `1..9` in lexicographic order. There are `9! = 362880` results, and you need one. A complete generator takes at least `Θ(n · n!)` time if it outputs every permutation of length `n`.

For a grammar row with `n` levels, its length is `2^(n-1)`; explicitly constructing the row takes exponential space in `n` even if the requested position has a short ancestor chain.

For Tower of Hanoi with `n` disks, the optimal sequence contains `2^n - 1` moves. Generating all moves is intrinsically exponential, but locating a single move can be linear in `n` once section sizes are known.

**Always ask:** *What does the generator know about an entire branch before entering it?* Its count, its relation to a parent, or its position is often enough to skip it.

# 5. Deep Worked Example A — K-th Symbol in Grammar

**Canonical problem:** [LeetCode 779 — K-th Symbol in Grammar](https://leetcode.com/problems/k-th-symbol-in-grammar/)

**Statement distilled:** Row 1 is `0`. Each `0` becomes `01`, each `1` becomes `10`. Return position `k` (1-based) in row `n`.

```text
row 1: 0
row 2: 01
row 3: 0110
row 4: 01101001
```

**Your notes (pp. 19–22):** You noticed row length doubles; a symbol's expansion is tied to its parent; the row has related halves. Those are two valid avenues. Here we derive the simpler parent-child rule first, and then show the half-based rule.

## 5.1 First think brute force

Build row `n-1`, replace each bit with two bits, then return `row[k-1]`.

- Time: `Θ(2^(n-1))` to generate the final row (up to constant factors).
- Space: `Θ(2^(n-1))` if the row is stored.
- Bottleneck: most generated bits will never be queried.

## 5.2 Structural observation

Each parent emits two children:

| Parent | Left child | Right child |
|---|---|---|
| `0` | `0` | `1` |
| `1` | `1` | `0` |

Therefore:
- Left child **equals** parent.
- Right child **flips** parent.

For a **1-based** child position `k`, its parent's 1-based position is `ceil(k / 2)` — in integer arithmetic, `(k + 1) / 2`.

- Odd `k` → left child → same bit.
- Even `k` → right child → flipped bit.

So the recurrence is:

```text
symbol(1, 1) = 0
parent = symbol(n-1, (k+1)/2)
symbol(n,k) = parent                  if k is odd
symbol(n,k) = 1 - parent              if k is even
```

### Invariant

`symbol(n,k)` returns exactly position `k` of row `n`. The parent index locates the group of two children that produced it; child's parity determines whether to copy or flip the parent.

## 5.3 Dry run — row 4, k = 5

```text
symbol(4,5)     k odd → copy parent at (5+1)/2 = 3
    symbol(3,3) k odd → copy parent at 2
        symbol(2,2) k even → flip parent at 1
            symbol(1,1) = 0
        symbol(2,2) = 1
    symbol(3,3) = 1
symbol(4,5) = 1
```

Check row 4: `01101001` → its 5th character is `1`.

## 5.4 Java — directly derived

```java
class Solution {
    public int kthGrammar(int n, int k) {
        if (n < 1 || k < 1 || k > (1L << (n - 1))) {
            throw new IllegalArgumentException("Invalid row or position");
        }
        return find(n, k);
    }

    private int find(int n, int k) {
        if (n == 1) return 0;
        int parent = find(n - 1, (k + 1) / 2);
        return (k % 2 == 1) ? parent : 1 - parent;
    }
}
```

**Precondition for this exact Java check:** `1 <= n <= 30` as in the original problem; for much larger `n`, validate bounds without shifting past the width of `long`. The code uses `1L` to avoid 32-bit overflow.

**Complexity:** `O(n)` time (one recursive call per row), `O(n)` auxiliary stack space, `O(1)` other memory.

**Code fingerprint:**

```java
parent = find(n - 1, (k + 1) / 2);
return (k % 2 == 1) ? parent : 1 - parent;
```

This indicates **parent-position recursion**, not exhaustive generation.

## 5.5 Alternative observation from your notes: halves

Row `n` consists of row `n-1` followed by its bitwise complement:

```text
row 3: 0110
row 4: 0110 | 1001
```

If the row length is `L = 2^(n-1)`, its half-length is `H = L/2`:

```text
if k <= H: answer is row(n-1)[k]
else:      answer is the complement of row(n-1)[k-H]
```

That is another correct recursive reduction, but it uses **half selection**, not the immediate parent's two-child index. Do not mix the two index transformations.

## 5.6 When NOT to use this version

- Arbitrary rewrite rules may not have a simple parity-dependent child relation.
- If queries ask for the whole row, direct generation may be appropriate.
- If there are many queries, consider direct bitwise formulas or preprocessing as appropriate.
- Do not apply the parity rule to a different grammar without proving it.

**60-second interview explanation:** “I don't build the exponentially long row. Each parent emits two children: left equals the parent and right is its opposite. The parent of 1-based position `k` is `(k+1)/2`; odd positions copy, even positions flip. I recursively retrieve the parent's value and apply that one change. The row number decreases every time, so the algorithm terminates in `O(n)` time with `O(n)` stack space.”

# 6. Deep Worked Example B — K-th Move of Tower of Hanoi

**From your handwritten notes:** pp. 13–15 begin by counting moves, notice a middle move, and derive the repeated relationship `T(n) = 2T(n-1) + 1`. We now turn that observation into a precise K-th-move algorithm.

**Task:** Move `n` disks from peg `A` to peg `C`, using peg `B` as temporary storage, under standard Hanoi rules. Return only the **k-th move** (1-based) of the usual optimal recursive solution.

## 6.1 Why not generate?

The standard algorithm:

```text
1. Move n-1 disks A → B using C
2. Move largest disk A → C
3. Move n-1 disks B → C using A
```

If `T(n)` is the number of moves:

```text
T(0) = 0
T(n) = T(n-1) + 1 + T(n-1)
     = 2*T(n-1) + 1
     = 2^n - 1
```

Generating all moves is `Θ(2^n)`; even for a small `k`, a generator may do unnecessary work (and for large `k`, nearly all the work).

## 6.2 Split the output into three sections

For `n` disks:

```text
Left recursive section:  2^(n-1) - 1 moves
Middle move:             1 move
Right recursive section: 2^(n-1) - 1 moves
```

The middle move occupies exactly rank `2^(n-1)`.

- If `k < 2^(n-1)`, the requested move is in the **left** recursion.
- If `k == 2^(n-1)`, it is the **largest-disk move**.
- If `k > 2^(n-1)`, it is in the **right** recursion with local rank `k - 2^(n-1)`.

Why subtract `2^(n-1)`, not `2^(n-1)-1`? The prefix we skip includes **the left section AND the middle move**. Total skipped `= (2^(n-1)-1)+1 = 2^(n-1)`.

## 6.3 State and invariant

`kthMove(n, from, aux, to, k)` returns the k-th move in the standard optimal schedule for moving `n` disks `from → to` via `aux`.

**Invariant:** The requested `k` remains valid **relative to the current subproblem**, and the peg roles are permuted to match the chosen recursive section.

## 6.4 Full dry run — n = 3, k = 5

Top-level `middle = 2^(3-1) = 4`.

```text
k = 5 > 4 → right section
right subproblem: move 2 disks from B → C using A
local k = 5 - 4 = 1

n = 2, middle = 2
k = 1 < 2 → left section
left subproblem: move 1 disk from B → A using C
local k = 1

n = 1, middle = 1
k = 1 → move disk 1 from B to A
```

Full standard 3-disk schedule (shown only as a verification):

```text
1. disk 1: A → C
2. disk 2: A → B
3. disk 1: C → B
4. disk 3: A → C
5. disk 1: B → A   ← requested
6. disk 2: B → C
7. disk 1: A → C
```

## 6.5 Java — direct position lookup

```java
public class HanoiKthMove {
    record Move(int disk, char from, char to) {}

    // Assumes 1 <= n <= 62, 1 <= k <= 2^n - 1.
    public static Move kthMove(int n, long k) {
        if (n < 1 || n > 62 || k < 1 || k > (1L << n) - 1) {
            throw new IllegalArgumentException("Invalid n or k");
        }
        return locate(n, 'A', 'B', 'C', k);
    }

    private static Move locate(int n, char from, char aux, char to, long k) {
        long middle = 1L << (n - 1);

        if (k == middle) {
            return new Move(n, from, to);
        }
        if (k < middle) {
            // Move n-1 disks: from → aux (using to).
            return locate(n - 1, from, to, aux, k);
        }
        // Move n-1 disks: aux → to (using from).
        return locate(n - 1, aux, from, to, k - middle);
    }
}
```

**Why the `n <= 62` bound?** We count moves in signed `long`, and `2^n - 1` must fit. A different large-integer representation would be needed beyond this limit.

**Complexity:** `O(n)` time, `O(n)` stack space. Only one of the two recursive Hanoi sections is entered per level.

**Code fingerprint:**

```java
long middle = 1L << (n - 1);
if (k == middle) return largestDiskMove;
if (k < middle) return left(k);
return right(k - middle);
```

This reveals **recursive section selection**.

## 6.6 Negative signals

- The order must be the **specified Hanoi move order**, not an arbitrary valid solution.
- If the task asks for **all moves**, we cannot skip them and still output them.
- If extra legal moves or different objectives are allowed, the classic `2^n - 1` structure may not apply.
- The exact disk and peg roles matter; obtaining just the disk number is not enough when the task asks for the full move.

**60-second interview explanation:** “The optimal Hanoi output for `n` disks has a left subproblem, one largest-disk move, and a right subproblem. Each side contributes `2^(n-1)-1` moves, so the middle move is at rank `2^(n-1)`. Comparing `k` with this rank identifies the only relevant section. For the right section I subtract all preceding moves and update peg roles. I repeat until I land on the middle move, taking `O(n)` time rather than generating `2^n-1` moves.”

# 7. Deep Worked Example C — K-th Lexicographic Permutation

**Canonical problem:** [LeetCode 60 — Permutation Sequence](https://leetcode.com/problems/permutation-sequence/)

**From your handwritten notes:** pp. 16–18 list the six permutations of `1,2,3`, notice how the first digit remains fixed for a block, then the second digit changes, and propose jumping to the requested permutation without generating previous ones. That is the right structural insight.

## 7.1 Start with brute force

Generate all `n!` permutations in lexicographic order and stop at the k-th; potentially `Θ(n·n!)` time if full permutations are materialized and `Θ(n)` search stack space excluding output.

## 7.2 Group permutations by the first digit

For distinct sorted values `[1,2,3]`:

```text
Starts with 1: 123, 132  [2! = 2 items]
Starts with 2: 213, 231  [2! = 2 items]
Starts with 3: 312, 321  [2! = 2 items]
```

Each fixed prefix with `m` remaining **distinct** digits has exactly `m!` completions.

When selecting the next digit from `m` available digits, every option contributes a block of `(m-1)!` permutations.

## 7.3 Index conversion — the crucial trap

Problem rank `k` is **1-based**. Array indices are **0-based**.

Convert once:

```text
rank = k - 1
block = (m-1)!
choiceIndex = rank / block
newRank = rank % block
```

`choiceIndex` selects the next smallest remaining candidate. Remove it, then continue.

## 7.4 Dry run: n = 3, k = 4

```text
available = [1,2,3]
k = 4 → rank = 3 (zero-based)

m = 3, block = 2! = 2
choiceIndex = 3 / 2 = 1 → select 2
remaining = [1,3]
rank = 3 % 2 = 1

m = 2, block = 1! = 1
choiceIndex = 1 / 1 = 1 → select 3
remaining = [1]
rank = 1 % 1 = 0

m = 1, block = 0! = 1
choiceIndex = 0 → select 1
answer = 231
```

Compare the fourth item in the complete ordering: `123,132,213,231,312,321`.

## 7.5 Java — simple and interview-friendly

```java
import java.util.ArrayList;
import java.util.List;

class Solution {
    // LeetCode 60 constraints: 1 <= n <= 9; 1 <= k <= n!.
    public String getPermutation(int n, int k) {
        int[] factorial = new int[n + 1];
        factorial[0] = 1;
        for (int i = 1; i <= n; i++) {
            factorial[i] = factorial[i - 1] * i;
        }
        if (k < 1 || k > factorial[n]) {
            throw new IllegalArgumentException("Invalid rank");
        }

        List<Integer> available = new ArrayList<>();
        for (int value = 1; value <= n; value++) {
            available.add(value);
        }

        int rank = k - 1; // Switch to zero-based indexing once.
        StringBuilder answer = new StringBuilder();

        for (int remaining = n; remaining >= 1; remaining--) {
            int block = factorial[remaining - 1];
            int choiceIndex = rank / block;
            answer.append(available.remove(choiceIndex));
            rank %= block;
        }
        return answer.toString();
    }
}
```

**Complexity:** `O(n^2)` time with `ArrayList.remove(index)` (shifts elements), `O(n)` auxiliary space. Factorial arithmetic fits `int` for `n <= 9`; for larger `n`, use suitable integer types and careful overflow/rank bounds. The method only builds one permutation, not all `n!`.

**Why not HashMap/Heap?** The problem requires ordering remaining candidates and direct selection by rank, not frequency lookup or repeatedly extracting minimum. A sorted list is sufficient at this scale; an order-statistics data structure could reduce selection/removal cost if `n` were large and rank arithmetic were feasible.

**Code fingerprint:**

```java
int block = factorial[remaining - 1];
int choiceIndex = rank / block;
answer.append(available.remove(choiceIndex));
rank %= block;
```

This indicates **factorial block indexing / unranking**.

## 7.6 Boundaries

- **Distinct values:** Standard equal-size factorial blocks assume all elements are distinct. With duplicates, block sizes depend on frequency counts: `m! / (f1! f2! ...)`.
- **Lexicographic order:** If the problem specifies a different enumeration order, factorial selection must be adapted or discarded.
- **Return all permutations:** Ordinary permutation backtracking (Pattern 05) is appropriate; skipping cannot avoid required output.
- **Rank outside `1..n!`:** Reject it before indexing.

**60-second interview explanation:** “In sorted lexicographic order, all permutations starting with the same first element form a contiguous block. With `m` distinct values remaining, each candidate first element owns `(m-1)!` completions. I convert `k` to zero-based rank, divide it by block size to select the next value, and use remainder to find the rank inside that chosen block. Repeating yields the answer without generating earlier permutations.”

## 8. Pattern boundaries — do not conflate these with other techniques

| Question | Structural branch skipping | Backtracking generation | Binary search on answer | Memoization/DP |
|---|---|---|---|---|
| Need | One specific indexed result | All/some feasible candidates | Smallest/largest feasible scalar | Repeated subproblem values |
| Why progress? | Index maps into known block/parent | Build another partial candidate | Monotone predicate halves range | Cached state avoids recomputation |
| State | `(substructure, localRank)` | Partial path + choices | Candidate threshold/range | Reusable subproblem key |
| What gets skipped? | Whole known sections | Infeasible branches | Numeric intervals | Repeated computations |
| Must prove | Rank and block correspondence | Completeness and safe pruning | Feasibility monotonicity | State sufficiency |

**False positives:** “K-th largest element” is often a heap/selection question; “K-th smallest in sorted matrix” may call for heap or binary search; “K-th shortest path” usually needs other graph algorithms. Rank alone is **not** evidence of recursive block structure.

### The distinction that matters most

**Pruning** discards a branch because it **cannot contain any valid/better answer**.

**Branch skipping** discards a branch because the required **rank lies somewhere else**, even though the skipped branch can contain perfectly valid answers.

This is why your K-th examples deserve a separate pattern from N-Queens pruning.

## 9. Reusable template (not a copy-paste solution)

```java
// Conceptual pseudocode: sizes and state transitions depend on the problem.
Result locate(State state, long k) {     // k is 1-based
    if (isAtomic(state)) {
        return atomicResult(state, k);
    }

    for (Branch branch : orderedBranches(state)) {
        long count = countResults(branch); // Must be correct and cheap.
        if (k > count) {
            k -= count;                    // Skip entire earlier branch.
        } else {
            return locate(branch.nextState(), k);
        }
    }
    throw new IllegalArgumentException("Rank outside sequence");
}
```

Not every instance is a list of branches: grammar has parent-index reduction; Hanoi includes a middle event. Use the generic template to guide reasoning, then derive a problem-specific recurrence.

### How to prove correctness

1. **Ordering:** Branches concatenate in the stated output order.
2. **Count:** Every skipped branch contributes exactly `count` results.
3. **Conservation:** Subtracting skipped counts maps original `k` to the same desired item in the retained suffix.
4. **Progress:** The retained subproblem becomes smaller or has fewer unfilled choices.
5. **Base case:** A singleton or atomic section returns its sole requested item.

## 12. Mistake library

### Recognition mistakes

- **Mistake:** See “K-th” and immediately use this pattern. **Why:** Pattern name is mistaken for a trigger. **Detect:** Cannot name/count ordered branches. **Prevent:** Prove the block structure first.
- **Mistake:** Treat pruning and skipping as synonyms. **Why:** Both avoid branches. **Detect:** Skipped branches contain valid earlier answers. **Prevent:** Prune for infeasibility; skip for rank location.

### Reasoning mistakes

- **Mistake:** Apply factorial counts with duplicate elements. **Detect:** Distinct permutations per prefix differ. **Prevent:** Use frequency-aware multinomial counts.
- **Mistake:** Subtract the wrong prefix length in Hanoi. **Detect:** K-th position off by one around the middle. **Prevent:** Count *all* earlier output, including the middle event.
- **Mistake:** Mix grammar half-indexing with parent-child indexing. **Detect:** Parent references wrong row position. **Prevent:** Choose one derivation and document its state contract.

### Implementation mistakes

- **Mistake:** Convert 1-based and 0-based ranks repeatedly. **Prevent:** Convert once; write index conventions above the function.
- **Mistake:** Use `1 << n` for large counts. **Prevent:** Use `1L << n` with explicit safe bounds, or a wider representation.
- **Mistake:** Fail to update Hanoi peg roles. **Prevent:** Trace `from`, `aux`, `to` as part of state, not comments.
- **Mistake:** Remove candidate without preserving lexicographic ordering. **Prevent:** Keep the available candidate list sorted.

### Complexity mistakes

- **Mistake:** Claim permutation unranking is `O(n)` for the given ArrayList code. **Prevent:** Account for `remove(index)`, which may shift `O(n)` elements; total `O(n²)`.
- **Mistake:** Describe Hanoi K-th lookup as `O(2^n)`. **Prevent:** Count visited recursion nodes, not conceptual output size.

### Interview mistakes

- **Mistake:** Start with a remembered formula and fail to justify it. **Prevent:** First show a tiny complete output and mark exact block boundaries.
- **Mistake:** Never state the output order. **Prevent:** Define it before the recurrence; K-th has no meaning without ordering.

## 13. Pattern decision tree

```text
Need a specific position K in a huge conceptual output?
|
+-- No → Do not force this pattern.
|
+-- Yes → Is output order well-defined?
          |
          +-- No → Clarify/derive ordering first.
          |
          +-- Yes → Can requested position map to one parent position?
                    |
                    +-- Yes → Parent/child structural reduction (Grammar).
                    |
                    +-- No → Are recursive section lengths known?
                              |
                              +-- Yes → Select section + adjust K (Hanoi).
                              |
                              +-- No → Can counts of completions be computed
                                        for each ordered prefix?
                                        |
                                        +-- Yes → Block unranking (Permutation).
                                        +-- No  → Seek other selection/search method.
```

## 14. Compact comparison / revision sheet

| Subpattern | Recognition signal | Core invariant | State | Core calculation | Complexity |
|---|---|---|---|---|---|
| Parent/child | Each output element comes from a small parent expansion | Ancestor position preserved | `row, k` | `(k+1)/2`, parity | Grammar: `O(n)` time/stack |
| Recursive section | Sequence = left + middle + right | Local rank in selected section | `n, pegs, k` | Middle `2^(n-1)` | Hanoi: `O(n)` time/stack |
| Factorial blocks | Ordered prefixes have equal completion counts | Rank retained inside selected prefix | `available, rank` | `rank / (m-1)!`, `%` | `O(n²)` ArrayList, `O(n)` space |

**Code fingerprints to reconstruct:**

```text
Grammar:      parent = f(n-1,(k+1)/2); odd copy / even flip
Hanoi:        mid = 2^(n-1); compare k with mid; skip prefix if right
Permutation:  idx = rank / factorial[m-1]; rank %= factorial[m-1]
```
