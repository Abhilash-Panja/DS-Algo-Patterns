# Pattern 4 - Same-Direction Read-Write Pointers

## 1. What This Pattern Actually Is

> Scan the input with a read pointer and build the required result in a prefix controlled by a write pointer.

This pattern is the missing companion to the handwritten forms. It is still a two-pointer technique, but the pointers do different jobs:

- read explores every input position;
- write marks where the next accepted or transformed value belongs.

## 2. Why This Pattern Exists

Creating a second array is easy, but many interview problems ask for in-place modification or O(1) extra space.

~~~text
Build a filtered result in a new array
        ↓
Uses O(n) extra space
        ↓
Observe that the already-written prefix is the answer so far
        ↓
Overwrite positions that no longer matter
        ↓
O(1) extra space
~~~

## 3. Recognition Signals

Ask:

1. Must the result be produced in the same array?
2. Does the problem say remove, compact, move, partition, or overwrite?
3. Can processed values be summarized by a prefix?
4. Does the order of accepted values need to remain stable?
5. Is the write position always at or behind the read position?

## 4. Trigger Words - But Do Not Depend On Them

"Remove duplicates in-place", "move zeroes", "keep only valid entries", "partition", and "stable compaction" are common signals. A story about cleaning records or moving active items can hide the same structure.

## 5. The Invariant

> Before processing read, the prefix [0, write) contains exactly the accepted output for all input positions before read, in the required order.

The unread region begins at read. Writing at write is safe because write never passes read when the algorithm only compacts or moves accepted items.

## 6. Derive the Algorithm Slowly

1. Set write to the beginning of the output prefix.
2. Scan each item with read.
3. Decide whether the item is accepted, moved, or discarded.
4. If accepted, write it at write and advance write.
5. After the scan, the first write positions contain the answer.
6. For stable move-to-end problems, fill the remaining positions with the default value.

## 7. Why This Data Structure?

The array itself is the data structure. A second array is unnecessary because discarded or already-read positions can be overwritten. Use a separate buffer only when the original values must be preserved or when in-place mutation violates the problem contract.

## 8. Core Java Templates

### Stable compaction

~~~java
static int removeIf(int[] nums, int forbidden) {
    int write = 0;

    for (int read = 0; read < nums.length; read++) {
        if (nums[read] != forbidden) {
            nums[write++] = nums[read];
        }
    }

    return write; // valid output is nums[0..write)
}
~~~

### Move zeroes while preserving nonzero order

~~~java
static void moveZeroes(int[] nums) {
    int write = 0;

    for (int read = 0; read < nums.length; read++) {
        if (nums[read] != 0) {
            nums[write++] = nums[read];
        }
    }

    while (write < nums.length) {
        nums[write++] = 0;
    }
}
~~~

## 9. Code Fingerprint

~~~text
write = 0
for read from 0 to n - 1:
    if nums[read] belongs in output:
        nums[write] = nums[read]
        write++
fill or ignore the suffix
~~~

## 10. When Not to Use It

- You need to preserve every original value and cannot overwrite.
- Accepted values depend on future information that cannot be summarized by the prefix.
- The output order is not stable and a different partition algorithm is more appropriate.
- The problem is about comparing two independent sorted sources rather than filtering one source.

## 11. Similar Pattern Comparison

| Question | Read/write compaction | Opposite-direction partition |
| --- | --- | --- |
| Pointer direction | both move forward | often one from each end |
| Output order | usually stable | may be unstable |
| Invariant | processed prefix is final output | regions satisfy classifications |
| Example | move zeroes | sort colors or partition negatives |

## 12. Deep Worked Example - Move Zeroes

Problem: Move every zero to the end of the array while preserving the relative order of nonzero values.

### Strip the story

- Input: one mutable array.
- Output: same array, nonzero values first in original order, zeroes after them.
- Space requirement: O(1) extra space.

### Brute force

Build a second array containing all nonzero values, then append zeroes. Correct, but uses O(n) extra space.

### Structural observation

Only the nonzero prefix matters while scanning. Every nonzero value can be written at the next available output position.

### Invariant

Before read is processed, nums[0..write) contains exactly the nonzero values seen so far, in their original order.

### Dry run

For [0, 1, 0, 3, 12]:

~~~text
read 0: ignore
read 1: write 1 at index 0 → [1, 1, 0, 3, 12]
read 0: ignore
read 3: write 3 at index 1 → [1, 3, 0, 3, 12]
read 12: write 12 at index 2 → [1, 3, 12, 3, 12]
fill suffix with zeroes → [1, 3, 12, 0, 0]
~~~

### Complexity

Each value is read once and each output position is written at most once. Time is O(n), extra space is O(1).

### Interview explanation

> I maintain a write pointer for the next nonzero position. The read pointer scans every value, and every nonzero is copied to write, preserving order. After the scan, the unused suffix is filled with zeroes. The processed prefix invariant guarantees correctness, and the algorithm uses linear time and constant extra space.

## 14. Follow-Up Training

- If order does not matter, swaps from both ends may reduce writes.
- If values have three categories, maintain three regions rather than one output prefix.
- If the array is immutable, return a new array or use a stream/buffer.
- If the result requires the original indices, store them before overwriting.
- If accepted values depend on a window condition, combine read/write with a separate window state only after proving both invariants.
