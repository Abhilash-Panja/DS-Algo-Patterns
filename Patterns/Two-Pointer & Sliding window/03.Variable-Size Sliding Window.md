# Pattern 2 - Variable-Size Sliding Window

## 1. What This Pattern Actually Is

> Expand the right boundary to include more input, and move the left boundary whenever the current region violates or satisfies a monotonic condition needed by the objective.

The window length is not known in advance. The algorithm discovers it while preserving a feasibility invariant.

## 2. Why This Pattern Exists

Enumerating all subarrays is quadratic. But if adding an element can only move the condition in one direction, and removing elements can reliably restore it, each boundary can move forward at most n times.

~~~text
Try every left/right pair
        ↓
Repeatedly recompute validity
        ↓
O(n²)
        ↓
Maintain validity while boundaries move monotonically
        ↓
O(n)
~~~

## 3. Recognition Signals

Ask:

1. Is the candidate a contiguous subarray or substring?
2. Does the statement ask for longest, shortest, or number of windows satisfying a condition?
3. Can I update the condition when one value enters or leaves?
4. If the window is invalid, can moving left only help?
5. If the window is valid, can moving right only make it larger or reveal more candidates?

The last two questions are the precondition. Without that monotonicity, the template is unsafe.

## 4. Trigger Words - But Do Not Depend On Them

Common signals include "longest substring", "minimum length", "at most K", "no repeated characters", and "smallest window". The story may instead describe a continuous time interval, a stretch of network traffic, or a basket that can hold only a limited number of categories.

## 5. The Invariant

> At the point where the answer is evaluated, the window state correctly represents [left, right], and the algorithm knows whether that window is feasible for the current objective.

The exact invariant differs by problem:

~~~text
sum <= target
frequency of every character is within its limit
number of distinct values <= k
~~~

## 6. Derive the Algorithm Slowly

There are two common objectives.

### Longest feasible window

1. Expand right and add its value.
2. While the window is invalid, remove left and advance left.
3. The restored window is feasible; update the maximum length.

### Shortest feasible window

1. Expand right and add its value.
2. While the window is feasible, record the answer.
3. Remove left and advance left to search for a shorter feasible window.

The handwritten "snake game" intuition is useful: the right side grows the snake, and the left side cuts its tail. The formal rule is more important than the metaphor: every removal must preserve the ability to reason about the next window.

## 7. Why a Data Structure?

Choose the smallest state that makes the validity check cheap:

- running sum for positive-number sum constraints;
- int[] frequency array for a small alphabet;
- HashMap for arbitrary values or at-most-k distinct counts;
- monotonic deque when the condition depends on a window maximum/minimum.

Do not use a variable window for exact sum with negative numbers. Removing the left value may increase or decrease the sum unpredictably, so "invalid now" does not prove that all smaller windows are safe or that a future expansion is monotonic.

## 8. Core Java Templates

### Longest feasible window

~~~java
int left = 0;
for (int right = 0; right < nums.length; right++) {
    add(nums[right]);

    while (!feasible()) {
        remove(nums[left]);
        left++;
    }

    best = Math.max(best, right - left + 1);
}
~~~

### Shortest feasible window

~~~java
int left = 0;
for (int right = 0; right < nums.length; right++) {
    add(nums[right]);

    while (feasible()) {
        best = Math.min(best, right - left + 1);
        remove(nums[left]);
        left++;
    }
}
~~~

The while loop is the key. A single if often misses multiple valid shrink steps.

## 9. Code Fingerprint

~~~text
for each right:
    add right
    while condition is broken or satisfied:
        remove left
        left++
    update answer
~~~

If both left and right only move forward, the apparent nested loop is still O(n): each element enters once and leaves once.

## 10. When Not to Use It

- Negative values destroy the required monotonicity for a sum condition.
- The condition depends on an order statistic that cannot be maintained cheaply.
- The answer is not restricted to contiguous elements.
- Moving left can discard a candidate that may become optimal after future expansion.
- A substring condition requires remembering positions or transitions that the proposed state does not capture.

## 11. Similar Pattern Comparison

| Question | Variable sliding window | Prefix sum + hashmap |
| --- | --- | --- |
| Contiguous? | yes | yes |
| Main condition | monotone under expansion/shrinking | exact relation between two prefix sums |
| Negative values | often unsafe for sum conditions | naturally supported |
| State | live window aggregate/frequencies | prefix sum frequencies |
| Typical shape | expand, shrink, update | scan and look up prefix - target |

## 12. Deep Worked Example - Minimum Size Subarray Sum

Problem: Given positive integers and target, return the minimum length of a contiguous subarray whose sum is at least target.

### Strip the story

- Input: positive array nums, target T.
- Output: minimum length of a contiguous region with sum >= T.
- Crucial precondition: every number is positive.

### Brute force

Try every starting point and extend every ending point, computing sums. This costs O(n²).

### Bottleneck

Once a window sum reaches T, checking a longer window is not useful for the minimum-length objective. We should shrink from the left while the condition remains true.

### Structural observation

Because values are positive:

- expanding right never decreases the sum;
- removing from the left never increases the sum.

That is exactly the monotonic behavior required by the variable-window pattern.

### Invariant

Before each answer update, sum >= T, and the current window is a candidate. After the shrinking loop ends, the window is the shortest feasible suffix ending at right.

### Dry run

For nums = [2, 3, 1, 2, 4, 3], T = 7:

~~~text
add 2 → sum 2
add 3 → sum 5
add 1 → sum 6
add 2 → sum 8 → record length 4; remove 2 → sum 6
add 4 → sum 10 → record length 3; remove 3 → sum 7
                 record length 2; remove 1 → sum 6
add 3 → sum 9 → record length 2; remove 2 → sum 7
                 record length 1; remove 4 → sum 3
~~~

The answer is 2.

### Java code

~~~java
static int minSubArrayLen(int target, int[] nums) {
    int left = 0;
    long sum = 0;
    int best = Integer.MAX_VALUE;

    for (int right = 0; right < nums.length; right++) {
        sum += nums[right];

        while (sum >= target) {
            best = Math.min(best, right - left + 1);
            sum -= nums[left];
            left++;
        }
    }

    return best == Integer.MAX_VALUE ? 0 : best;
}
~~~

### Complexity

Right advances n times and left also advances at most n times. Total time is O(n) and extra space is O(1).

### Interview explanation

> Since all values are positive, the window sum increases when I expand right and decreases when I remove from left. I expand until the sum reaches the target, then shrink as much as possible while remaining feasible, recording every candidate length. Each boundary moves only forward, so the total work is linear.

## 14. Follow-Up Training

- If negative values are introduced, re-check monotonicity before changing code.
- If the condition is exactly equal rather than at least or at most, consider prefix sums.
- If the alphabet is fixed and small, replace a hashmap with an array.
- If the window maximum or minimum controls validity, consider a monotonic deque.
- If the stream is unbounded, decide whether old state can be discarded safely.
