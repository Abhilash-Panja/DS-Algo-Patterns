# Pattern 1 - Fixed-Size Sliding Window

## 1. What This Pattern Actually Is

> Maintain exactly k contiguous elements while updating the answer from the element entering on the right and the element leaving on the left.

The window is [left, right] with right - left + 1 = k, or [left, right) with right - left = k.

## 2. Why This Pattern Exists

Suppose we need the maximum sum of every length-k subarray.

~~~text
Brute force: calculate every length-k sum from scratch
        ↓
O(nk) work
        ↓
Adjacent windows overlap in k - 1 elements
        ↓
Reuse the previous sum
        ↓
O(n) scan
~~~

For the next window, only two values change:

~~~text
nextSum = currentSum - nums[left] + nums[right + 1]
~~~

## 3. Recognition Signals

Ask:

1. Is the problem about a contiguous subarray or substring?
2. Is the length exactly k or fixed by the statement?
3. Does the aggregate change predictably when one item leaves and one enters?
4. Do I need an answer for every length-k region?

Typical signals include "every window of size k", "average of k consecutive values", "maximum sum of k consecutive elements", or a fixed-length substring condition.

## 4. Trigger Words - But Do Not Depend On Them

Words such as k, consecutive, contiguous, substring, and every block are useful hints. A problem may hide the same structure behind a story about sensors, transactions, packets, or daily activity. Strip away the story and check whether the selected region always has exactly k positions.

## 5. The Invariant

> Before evaluating the answer, the maintained state describes exactly the elements in the current length-k window.

For a running sum:

~~~text
sum = nums[left] + ... + nums[right]
right - left + 1 = k
~~~

## 6. Derive the Algorithm Slowly

1. The first window is indices 0 through k - 1.
2. Compute its state once.
3. Record its contribution to the answer.
4. Move the window one position right.
5. Remove the old leftmost value.
6. Add the new rightmost value.
7. Evaluate again.

The important insight from your handwritten example [3, -1, -1, 0, 1], k = 3 is that the second window is not recomputed from scratch. The old 3 leaves and 0 enters.

## 7. Why This State Instead of Prefix Sum?

A prefix sum also solves fixed-range sums, usually in O(1) per query after O(n) preprocessing. A running sum is simpler when the windows are processed in order and only one window is active. Use prefix sums when you need arbitrary ranges or random queries.

Do not use a hashmap or a sorted structure unless the window condition specifically requires frequencies, order statistics, or another non-additive state.

## 8. Core Java Template

~~~java
static long maxFixedWindowSum(int[] nums, int k) {
    if (k <= 0 || k > nums.length) {
        throw new IllegalArgumentException("invalid window size");
    }

    long sum = 0;
    for (int i = 0; i < k; i++) {
        sum += nums[i];
    }

    long best = sum;
    for (int right = k; right < nums.length; right++) {
        int left = right - k;
        sum += nums[right];
        sum -= nums[left]; // invariant restored: exactly k values remain
        best = Math.max(best, sum);
    }

    return best;
}
~~~

For a frequency-based substring, replace sum with a frequency map and perform the same remove/add boundary updates.

## 9. Code Fingerprint

~~~text
initialize the first k elements
for right = k to n - 1:
    add nums[right]
    remove nums[right - k]
    updateAnswer()
~~~

If you see one entering value and one leaving value on every iteration, it is probably a fixed-size window.

## 10. When Not to Use It

- The required window length changes according to a condition.
- The problem asks for an arbitrary range rather than all length-k ranges.
- The problem asks for a subsequence; selected elements need not be adjacent.
- The state cannot be updated cheaply when one element enters or leaves.

## 11. Similar Pattern Comparison

| Question | Fixed-size window | Variable-size window |
| --- | --- | --- |
| Window length | always k | changes with feasibility |
| Main update | one add and one remove | expand, then possibly many removes |
| Typical proof | all windows have equal length | shrinking preserves or restores feasibility |
| Common failure | off-by-one | using a non-monotone condition |

## 12. Deep Worked Example - Maximum Average Subarray I

Problem: Given an integer array and k, return the maximum average among all contiguous subarrays of length k.

### Strip the story

- Input: nums and integer k.
- Output: maximum value of sum(window) / k.
- Constraint: every candidate has the same length.

### Brute force

Compute each length-k sum independently. This repeats k - 1 additions between adjacent windows and costs O(nk).

### Bottleneck and observation

Adjacent windows overlap. The only changes are the leaving and entering values. Since k is fixed, maximizing average is equivalent to maximizing sum.

### Invariant

At each evaluation, sum is the sum of exactly k contiguous elements.

### Dry run

For [3, -1, -1, 0, 1], k = 3:

~~~text
[3, -1, -1] sum = 1
[-1, -1, 0] sum = -2   (remove 3, add 0)
[-1, 0, 1] sum = 0     (remove -1, add 1)
~~~

The best sum is 1, so the best average is 1 / 3.

### Complexity

The first window costs O(k) and each remaining position costs O(1), for O(n) time and O(1) extra space.

### Interview explanation

> Every candidate has the same fixed length, so I only need to compare their sums. I compute the first window once, then slide it across the array. Each slide subtracts the value leaving on the left and adds the value entering on the right, so every element is processed a constant number of times. The complexity is O(n) time and O(1) space.

## 14. Follow-Up Training

- If k changes for every query, precompute prefix sums or use another query structure.
- If the window maximum is needed, a running sum is insufficient; use a monotonic deque.
- If the data arrives as a stream, maintain the window state incrementally and decide how to discard old values.
- If k > n, define whether the answer is invalid, empty, or a problem-specific default.
