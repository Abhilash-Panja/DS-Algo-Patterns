# Pattern 3 - Sorted Opposite-Direction Pointers

## 1. What This Pattern Actually Is

> Use a left pointer and a right pointer on sorted data; after comparing the two boundary values, move the side whose movement can eliminate an entire set of impossible pairs.

The pointers usually start at opposite ends and move inward. Sorting is not the answer by itself; sorting creates the monotonic structure that makes pointer movement provably safe.

## 2. Why This Pattern Exists

For a target pair sum, checking every pair costs O(n²).

~~~text
Try every i, j pair
        ↓
O(n²)
        ↓
Sort the values so increasing an index increases the value
        ↓
One comparison eliminates a whole row or column of pairs
        ↓
O(n log n) for sorting + O(n) scan
~~~

For an ascending array:

- if nums[left] + nums[right] is too small, every pair using this left with an index at or before right is too small, so left can be discarded;
- if the sum is too large, every pair using this right with an index at or after left is too large, so right can be discarded.

## 3. Recognition Signals

Ask:

1. Is the input already sorted, or may I sort it without destroying required information?
2. Do I need a pair, triple, closest pair, or a boundary-based optimum?
3. Does moving one index monotonically increase or decrease the relevant value?
4. Can one comparison eliminate many candidate pairs?
5. Is the objective based on the two current boundary values?

If original indices are required, store value-index pairs before sorting.

## 4. Trigger Words - But Do Not Depend On Them

Common signals include "two numbers", "target sum", "closest", "sorted array", and "maximum area". A problem may disguise the same structure as choosing two days, two locations, or two sorted event streams. The structural clue is ordered candidates plus a safe direction for eliminating possibilities.

## 5. The Invariant

> Every pair that has not been eliminated remains inside the current pointer interval, and the pointer movement has discarded only pairs proven incapable of satisfying or improving the objective.

For sorted two-sum, the active search space is all pairs with left <= i < j <= right.

## 6. Derive the Algorithm Slowly

1. Put left at the smallest candidate and right at the largest.
2. Evaluate the current pair.
3. If it is too small, increase left because keeping this left cannot help with any smaller right.
4. If it is too large, decrease right because keeping this right cannot help with any larger left.
5. If it matches, return or record it.
6. Stop when the pointers cross.

For 3Sum:

1. Sort the array.
2. Fix one index i.
3. Run the same two-pointer search on the suffix after i for target - nums[i].
4. Skip equal fixed values and equal pointer values when unique triplets are required.

## 7. Why Sorting and Two Pointers Instead of a Hashmap?

A hashmap gives expected O(n) for one unsorted Two Sum query and preserves original positions. Sorting plus two pointers gives O(n log n), but it provides:

- an ordered search space;
- easy duplicate handling for 3Sum;
- a direct proof for closest or boundary objectives;
- predictable memory behavior.

Choose the hashmap when the array must remain in original order or when many independent lookup queries make sorting inconvenient.

## 8. Core Java Template

~~~java
static int[] twoSumSorted(int[] nums, int target) {
    int left = 0;
    int right = nums.length - 1;

    while (left < right) {
        long sum = (long) nums[left] + nums[right];

        if (sum < target) {
            left++;
        } else if (sum > target) {
            right--;
        } else {
            return new int[] {left, right};
        }
    }

    return new int[] {-1, -1};
}
~~~

If sorting is allowed but original indices matter, sort pairs such as value plus original index, or use a separate index array.

## 9. Code Fingerprint

~~~text
left = 0
right = n - 1
while left < right:
    compare value(left) + value(right)
    move exactly one side based on monotonicity
~~~

The important fingerprint is not merely two indexes. It is the proof that one side can be discarded after the comparison.

## 10. When Not to Use It

- The data is unsorted and sorting would destroy required order or indices.
- The objective is not monotonic under pointer movement.
- You need all pairs with multiplicity and have not designed duplicate handling.
- The values can move in both directions unpredictably after sorting.
- A hashmap gives a simpler O(n) solution for a single exact lookup.

## 12. Deep Worked Example - Two Sum II

Problem: Given a nondecreasing array, return the 1-based positions of two values that sum to target. Exactly one solution exists.

### Strip the story

- Input: sorted array nums and target.
- Output: indices i < j such that nums[i] + nums[j] = target.
- Constraint: the array is already sorted.

### Brute force

Try every pair. This is O(n²).

### Bottleneck

The sorted order tells us how the sum changes:

- increasing left increases the sum;
- decreasing right decreases the sum.

### Structural observation

Start with the smallest and largest candidates. If their sum is too small, the smallest value cannot form the target with any value at or before right. If their sum is too large, the largest value cannot form the target with any value at or after left.

### Invariant

All uneliminated solutions lie inside [left, right].

### Dry run

For nums = [2, 7, 11, 15], target = 9:

~~~text
left = 2, right = 15 → sum 17, too large → move right
left = 2, right = 11 → sum 13, too large → move right
left = 2, right = 7  → sum 9, found
~~~

### Complexity

The array is already sorted, so the scan is O(n) time and O(1) extra space. If sorting were required, total time would be O(n log n).

### Interview explanation

> Because the array is sorted, I can use the smallest and largest remaining values. If their sum is too small, the left value must increase; if it is too large, the right value must decrease. Each move eliminates all pairs involving one boundary that cannot work, so every index moves at most once and the scan is linear.

## 13. 3Sum Composition

A 3Sum solution is not a new pointer pattern:

~~~java
Arrays.sort(nums);

for (int i = 0; i < nums.length - 2; i++) {
    if (i > 0 && nums[i] == nums[i - 1]) {
        continue; // avoid duplicate fixed values
    }

    int left = i + 1;
    int right = nums.length - 1;

    while (left < right) {
        long sum = (long) nums[i] + nums[left] + nums[right];

        if (sum < 0) {
            left++;
        } else if (sum > 0) {
            right--;
        } else {
            // record triplet
            while (left < right && nums[left] == nums[left + 1]) left++;
            while (left < right && nums[right] == nums[right - 1]) right--;
            left++;
            right--;
        }
    }
}
~~~

The duplicate skips are part of correctness, not an optional optimization.

## 15. Follow-Up Training

- If the array becomes unsorted, decide between sorting with index retention and a hashmap.
- If all unique pairs are required, define whether duplicate values represent one pair or multiple occurrences.
- If the target changes for every query, preprocessing or a different data structure may be needed.
- If the problem asks for a closest value, replace equality with a best-distance invariant.
- If a third or fourth value is added, fix one or more values and reuse the inner search only when the resulting complexity fits.
